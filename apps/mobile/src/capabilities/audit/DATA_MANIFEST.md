# Data Manifest — Audit / Explainability (mobile client)

Per `docs/CONSTITUTION.md` Art. 8 (privacy is the default; minimum data,
documented purpose) and `docs/capabilities/audit-explainability.charter.md`
§4 ("a documented purpose per event field... no collection of content
beyond what's needed to explain an action").

This directory (`apps/mobile/src/capabilities/audit/`) is a thin HTTP
client for the real Audit / Explainability capability implemented in
`services/api/internal/audit` — the authoritative manifest for what is
*collected and stored server-side* is that package's own
`DATA_MANIFEST.md` (if present) / charter §4. This client-side manifest
documents the narrower question that one doesn't cover: what does *this
module* transmit, and why — every field below is already documented, with
the same purpose, on the server side; nothing here is new collection.

This module wraps three of Audit's four RPCs (`Query`, `Explain`,
`ExportAuditTrail`) — see `index.ts`'s header for why `Emit` is
deliberately not wrapped here (it is the internal, capability-to-capability
call every other backend capability's mutating operation makes in-process;
mobile has no legitimate reason to construct and emit an arbitrary audit
event on another capability's behalf).

## Fields sent

- `subject` (on `query`) / `identityRef` (on `exportAuditTrail`)
  Purpose: server-issued opaque identity-reference string (Identity's
  format), sent so the server knows whose trail to query or export. Always
  the caller's own `identityRef` in this pass's UI (`ActivityScreen.tsx`
  always passes the signed-in identity) — the server independently rejects
  any other value it isn't authorized to see (fail-closed
  `PermissionChecker`, `services/api/internal/audit/service.go`'s
  `denyAllChecker` default). Not generated, resolved, or interpreted by
  this module.

- `resourceTypeFilter` / `resourceIdFilter` / `actionFilter` / `sinceUnix` /
  `untilUnix` (on `query`)
  Purpose: optional narrowing of the caller's own trail, entirely
  user-chosen in the Activity screen's filter controls (charter §3's
  QueryRequest fields: "queryable by resource, time range, or action
  type"). None is required — an unfiltered query returns the caller's full
  trail (charter §4/Art. 1: "always visible to them"). This module does
  not interpret these values beyond passing them through as query-string
  parameters.

- `eventId` (on `explain`)
  Purpose: identifies which already-fetched event (from a prior `query`
  call) the caller wants a plain-language rationale for. Server-issued,
  opaque, never generated by this module.

## Fields received (not sent)

- `eventId` / `actor` / `action` / `resource` (`resourceType` +
  `resourceId`) / `ruleReference` / `metadata` / `occurredAtUnix` (via
  `query`'s `AuditEvent` rows)
  Purpose: display only — lets the Activity screen show exactly what the
  server-side Audit charter's own Art. 8 manifest documents for each field
  (§4: actor/action/resource/rule_reference identify what happened, to
  what, and by what rule; metadata may only ever describe *that* an action
  happened, never sensitive content; the timestamp orders the trail). This
  module never interprets, resolves, or hydrates `actor`/`resource` beyond
  displaying the raw opaque strings the server returns — resolving an
  `actor` reference to a display-ready identity is explicitly Identity's
  job, done lazily, not this module's (charter §3) — this pass's UI does
  not attempt that resolution either, matching Permissions' own client
  precedent for `grantor`/`subject`.

- `humanReadableRationale` (via `explain`)
  Purpose: display only — the plain-language "why/when/by-what-rule"
  answer this capability exists to provide (charter §1/§3). Synthesized
  server-side from the event's own already-audited fields; this module
  neither generates nor transforms it.

- `exportBlob` / `formatVersion` (via `exportAuditTrail`)
  Purpose: the user's full, hash-chained activity history, as a portable,
  versioned, independently-verifiable document (Art. 9). This module
  writes the raw response bytes through unmodified to the caller
  (`features/activity/screens/ActivityScreen.tsx`) — it never inspects or
  transforms the export document's contents. Unlike Identity's/
  Permissions' export RPCs, the response body is not a JSON envelope
  around a base64 field; it is the export bundle itself (raw bytes), with
  `formatVersion` carried in a response header — see `types.ts`'s header
  comment for the verified wire-shape difference.

## Fields held locally by this module

None. This module is stateless — it shapes a request, calls the real
backend, and returns a parsed response; it does not itself persist
anything to `SecureLocalStore` or any other store. Any local caching of
`AuditEvent`/rationale data for UI purposes (loading state, list display,
which row's explanation is currently expanded) is owned by the calling
screen layer (`apps/mobile/src/features/activity/`), not this module.

## Explicitly out of scope (not collected)

- No display-ready identity for `actor` — this module does not call
  Identity's `resolveIdentity` on `query`'s/`explain`'s results to hydrate
  a name; charter §3's lazy-resolution design leaves that to a future,
  separately-scoped pass if ever needed, matching Permissions' own
  `grantor`/`subject` precedent (raw opaque strings, no hydration).
- No `Emit` path — this module cannot be used to construct or send an
  arbitrary audit event; see `index.ts`'s header for why that RPC is
  deliberately not wrapped here.
- No device/hardware fingerprint, IP address, or geolocation.
- No caching or duplication of a prior `query` response's contents beyond
  what the calling screen holds in ordinary React state for the current
  session — nothing is written to any persistent local store by this
  module.

## Notes

- The client-side `logAuditEvent` call in `audit.ts`/`index.ts` is a local
  dev-visibility and mechanical-CI-convention stub, not a second audit
  trail of record — Audit IS the trail of record; see `audit.ts`'s header
  comment for why this still exists (mirrors every sibling capability's own
  `audit.ts`). `query`/`explain` are plain reads with no client-side stub
  call (matching `listGrantsForSubject`/`listFileObjects` precedent) and
  are not marked `// ascend:mutates` here.
