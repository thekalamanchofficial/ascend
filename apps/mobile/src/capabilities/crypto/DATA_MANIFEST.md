# Data Manifest — Cryptography & Keys

Per `docs/CONSTITUTION.md` Art. 8 (privacy is the default; minimum data,
documented purpose) and `docs/capabilities/cryptography-and-keys.charter.md`
§4: "the data manifest for this capability documents exactly zero collected
fields beyond public keys."

This capability is implemented entirely on-device
(`apps/mobile/src/capabilities/crypto/`) and has no server component and no
network client of any kind (see `index.ts`'s own header comment). There is
no database and nothing is "collected" in the usual sense this manifest
format assumes for a backend capability. The relevant boundary here is
different but the same in spirit: what does this module ever hand *out* —
to its callers (other capabilities), and from there potentially onward to
the rest of the platform, including a server? That crossing point is what
this manifest documents.

## Fields

- `public_key`
  Purpose: the only cryptographic material this capability ever exposes
  beyond its own boundary. `GenerateIdentityKeyMaterial`, `GenerateKeyPair`,
  and `RestoreFromRecoveryPhrase` all return a public key to their caller
  so other capabilities (Identity, Messaging, etc.) and other users can
  address this device/identity, verify its signatures (`Sign`), and
  encrypt to it (`Encrypt`). Public keys are not secret by construction —
  this is the capability's one intended, documented crossing point, not an
  incidental leak.

- **Added 2026-08-20 (responder-side prekey completion amendment —
  `docs/capabilities/cryptography-and-keys.charter.md` §3/§4, gated
  2026-08-19):** `signed_prekey.public_key` / `.signature` / `.created_at_unix`
  (returned by `GeneratePrekeyBundle`) and each `one_time_prekey.public_key`
  — same category as `public_key` above (public key material), not a new
  one. Purpose: lets another identity's device asynchronously establish an
  E2E session with this device without requiring it to be online at
  handshake time (charter §3/§7). `signed_prekey.signature` specifically
  exists so an initiator can verify the signed prekey was genuinely
  generated by this identity's own long-term signing key before using it
  (charter §6 "Signed-prekey substitution") — a compromised or malicious
  server must not be able to substitute a different one undetected.

- **Added 2026-08-20:** `signed_prekey.prekey_id` and each
  `one_time_prekey.prekey_id` — named as their own manifest entry, not
  folded into "public key material," which they aren't (Constitution
  Warden gate finding, charter amendment round 1). Purpose: an opaque
  identifier, not key material itself, that `CompleteSharedSecret`
  (`my_signed_prekey_id`/`my_one_time_prekey_id`) uses to locate the
  corresponding locally-stored private prekey — and, for the one-time
  prekey specifically, to atomically consume and permanently delete it
  immediately after use (see "Explicitly out of scope" below and
  `prekeyStore.ts`). This capability never transmits `prekey_id` anywhere
  itself; it is generated locally (`GeneratePrekeyBundle`) and returned to
  the caller for whatever capability publishes it (Identity's own
  companion amendment — out of scope here).

- **Added 2026-08-21 (key-separation fix, `docs/DECISION_LOG.md`'s
  "Key-separation fix" series; charter §3, rounds 2/3):**
  `identity_dh_public_key` (returned by `GeneratePrekeyBundle`) — same
  category as `public_key` above (public key material, not a new one):
  the device's genuinely separate, DH-only X25519 identity public key,
  deterministically derived from the same recovery-phrase seed via
  `dhKey.ts`'s domain-separated KDF, distinct from the Ed25519
  `public_key` this module has always returned. Purpose: lets an
  initiator complete X3DH's `DH2 = DH(EK_A, IK_B)` term against this
  device without ever reusing its Ed25519 signing key for DH. Alongside
  it, `identity_dh_public_key_signature` — the identical key-material
  category, not a distinct one, but named separately per Constitution
  Warden's round-3 finding that this sibling field needed its own
  manifest entry, not an assumed inheritance from the field it signs.
  Purpose: lets an initiator verify `identity_dh_public_key` was
  genuinely generated by this identity's own long-term signing key
  before using it in any DH term (charter §6 "`identity_dh_public_key`
  substitution") — the identical substitution-defense purpose
  `signed_prekey.signature` already serves above, applied to this
  second published key.

- **Added 2026-08-23 ("the ongoing-ratchet exposure gap" amendment —
  `docs/capabilities/cryptography-and-keys.charter.md` §3/§4, Constitution
  Warden gate round 2 finding: every prior amendment stated this reasoning
  even when the conclusion was "no new category," this one's first draft
  didn't):** `EncryptMessage`/`DecryptMessage` and the `RatchetState`
  persistence fix introduce no new manifest entry — reasoned through
  explicitly, not left silent. Purpose: `shared_secret_handle` is an
  opaque, process-local reference used so `EncryptMessage`/`DecryptMessage`
  can locate an already-established session's key material without that
  material ever crossing this module's boundary — the same
  never-transmitted, never-logged category as `private_key_handle`
  (already covered by this manifest's
  "Explicitly out of scope" section below). The new opaque per-message
  envelope (`EncryptMessage`'s return value / `DecryptMessage`'s input,
  see `messageEnvelope.ts`) exists so a caller (e.g. Conversations) has a
  single self-describing byte string to relay — the same category as
  `Encrypt`'s existing `ciphertext` output above, itself never logged or
  separately manifested. `receivingChainKey` (the new `RatchetState` field)
  exists purely to hold the receiving-direction chain key this module's own
  ongoing ratchet needs — it never leaves this module in any form, exactly
  like `sendingChainKey` already didn't.
  **Persisting `RatchetState` via `SecureLocalStore` (the charter §3
  persistence fix, `keyRegistry.ts`) does not change this** — it moves
  *where* this already-never-transmitted material is stored at rest, not
  *whether* it is collected, transmitted, or logged; the same "encrypted
  local store, never plaintext on disk" discipline this manifest's opening
  section already requires for all key material governs it identically.

## Explicitly out of scope (structurally never collected — not merely "not currently collected")

- **No private key material of any kind ever leaves this module in
  plaintext.** `GenerateIdentityKeyMaterial`, `GenerateKeyPair`, and
  `RestoreFromRecoveryPhrase` return only an opaque `KeyHandle` (`{ handle:
  string }`) alongside the public key — never the private key bytes
  themselves (`keyRegistry.ts` is the only place private key bytes are
  held, in an in-memory, non-exported map). The one narrow, deliberate
  exception is `ExportKeyMaterial`: an explicit, user-confirmed operation
  (Art. 9) whose entire purpose is letting the user take their own private
  key material with them. Even there, the recipient is the user themselves
  via a direct return value, never a network call, and the operation
  refuses to run at all without `user_confirmation: true` (and now audits
  the refusal — see docs/DECISION_LOG.md, 2026-07-16 "Fix: audit
  rejected/failed attempts, not just successes").
- **No plaintext of anything this capability encrypts or decrypts is ever
  retained** after an `Encrypt`/`Decrypt` call returns. There is no
  plaintext-holding field, cache, or store anywhere in this module.
- **No recovery phrase is ever persisted or logged, in any form.**
  `generateRecoveryPhrase()`'s output is returned once, directly, to the
  immediate caller of `GenerateIdentityKeyMaterial`, and is never written
  to `SecureLocalStore`, never included in `ExportKeyMaterial`'s blob (see
  that function's own doc comment in `index.ts`), and never passed to
  `logAuditEvent` — `audit.ts`'s own doc comment states this as a hard
  rule for every call site in this module, present and future.
  `RestoreFromRecoveryPhrase` takes a phrase as input and derives key
  material from it in memory; the phrase itself is not retained after the
  call returns.
- No email, phone number, device hardware fingerprint, IP address, or
  geolocation — this capability has no concept of any of those. It
  operates purely on caller-supplied key handles, purpose strings, and
  byte buffers.
- **Added 2026-08-20: no PRIVATE signed-prekey or one-time-prekey material
  ever leaves this module.** `GeneratePrekeyBundle` returns only public
  halves + signature (matching `GeneratePrekeyBundleResponse` exactly);
  the private halves are held only via `SecureLocalStore`
  (`prekeyStore.ts`), indexed by `prekey_id`, under the identical
  never-plaintext-at-rest guarantee `SecureLocalStore`'s own manifest note
  already documents below. A consumed one-time prekey's private key is
  permanently deleted (not merely marked consumed) immediately upon use by
  `CompleteSharedSecret` — retaining it after use would be data collection
  with no documented purpose, the forward-secrecy-defeating exact failure
  charter §6 exists to prevent.
- Nothing in this module makes a network call of any kind, so "collected
  by the server" is not merely minimized here, it is structurally
  impossible for this capability's own code to cause it.
- **Added 2026-08-23: no `RatchetState` (chain keys, DH ratchet keypair,
  root key) is ever held in plaintext at rest.** `keyRegistry.ts`'s
  `registerRatchetSession`/`getRatchetSession`/`updateRatchetSession` hold
  it only via `SecureLocalStore`, keyed by `"ascend.crypto.ratchetSession." + handle`,
  under the identical never-plaintext-at-rest guarantee `SecureLocalStore`'s
  own manifest note below already documents. `EncryptMessage`/
  `DecryptMessage` never return or log `RatchetState` or any chain key —
  only the opaque per-message envelope (ciphertext) crosses this module's
  boundary.

## Notes

- Audit metadata (the `logAuditEvent` calls throughout `index.ts`, each
  marked `// ascend:mutates` on the function that emits it) is a
  companion to this manifest, not a second, undocumented collection
  surface: it is documented in `audit.ts` as never carrying key material,
  plaintext, or the recovery phrase — only opaque handle strings,
  purposes, outcomes, and truncated SHA-256 fingerprints
  (`auditHash.ts`'s `auditFingerprint`) of otherwise-sensitive values such
  as a `SecureLocalStore` key name (see docs/DECISION_LOG.md, 2026-07-16
  "Fix: hash SecureLocalStore key names before they reach audit
  metadata").
- `SecureLocalStore`/`SecureLocalRetrieve` (`secureStore.ts`) hold
  arbitrary caller-supplied `value` bytes at another capability's request
  (e.g. a capability storing its own encrypted local state). This
  capability does not inspect, interpret, or document the *content* of
  those values — it has no visibility into what they represent — and only
  guarantees they are never held in plaintext at rest (OS Keychain/
  Keystore via `expo-secure-store`, or an encrypted software-vault
  fallback; see docs/DECISION_LOG.md, 2026-07-16 "SecureLocalStore/
  Retrieve: OS keychain primary, in-memory-by-default software vault
  fallback, pluggable key-provider hook"). Documenting the purpose of
  whatever a *caller* chooses to store there is that caller capability's
  own Art. 8 obligation, not this one's.
