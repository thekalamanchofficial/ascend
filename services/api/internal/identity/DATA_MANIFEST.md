# Data Manifest — Identity

Per `docs/CONSTITUTION.md` Art. 8 (privacy is the default; minimum data,
documented purpose) and `docs/capabilities/identity.charter.md` §4. This is
the exhaustive list of fields this capability collects and stores. No other
field is collected at this layer — unrelated profile data belongs to a
future profile-composition capability, not Identity.

## Fields

- `display_name`
  Purpose: shown to other users so they know who they're communicating
  with; user-editable, not derived from any other source.

- `public_key` (identity root key, and one per bound device)
  Purpose: the cryptographic material needed to verify device-binding
  authorization proofs and to let other capabilities/users address this
  identity's devices. No corresponding private key material ever reaches
  this service — private keys are generated and held exclusively by
  Cryptography & Keys, on-device.

- `device.name`
  Purpose: lets the user tell their own devices apart on a Devices screen.

- `device.added_at`
  Purpose: powers the Art. 5 "when was this device added" answer, surfaced
  via `ListDevices` and `ExportIdentity`.

- `device.last_seen`
  Purpose: lets the user spot a device they no longer recognize or use, as
  a security signal (charter §6 threat model — device spoofing/lost
  device awareness).

- `created_at_unix` (identity-level)
  Purpose: powers the Art. 5 "when was this identity created" answer,
  surfaced via `ExportIdentity`; also the reference point a user can use
  to reason about their own account history. Persisted on `IdentityRecord`
  and exported by `ExportIdentityRecord` (Constitution Warden merge-gate
  finding, 2026-07-16 — previously persisted/exported but undocumented
  here; fixed in this pass).

- `epoch` (identity-level)
  Purpose: NOT user-supplied data — a server-generated, monotonically
  increasing device-topology version counter, incremented on every
  successful `BindDevice`/`RevokeDevice`. It is the anti-replay input
  bound into every `BindDevice` `authorization_proof` (see `sign.go`),
  closing the replay vulnerability found at the 2026-07-16 Security
  Steward merge-gate veto: without it, a captured, previously-valid
  `authorization_proof` for a device that has since been revoked would
  remain valid forever and could silently re-add that device. Documented
  here per the same "every persisted/exported field is listed" discipline
  applied to `created_at_unix` above, even though it is not a piece of
  data collected *about* the user in the Art. 8 sense.

- `device.signed_prekey.public_key` / `.signature` / `.created_at_unix` / `.prekey_id`
  (added 2026-08-20, prekey bundle publish/fetch amendment — charter §4)
  Purpose: identical category and purpose to Cryptography & Keys' own
  manifest entry for the same material — lets another identity's device
  asynchronously establish an E2E session with this device
  (`PublishPrekeyBundle`/`FetchPrekeyBundle`). Already-public, already-signed
  bytes generated by Cryptography & Keys — this service stores/relays the
  signature byte-for-byte and never regenerates, re-signs, or reformats it
  (charter §6, "Signature integrity in storage"). Persisted in
  `identity_signed_prekeys` (`internal/platform/migrations/
  0009_identity_prekeys.up.sql`), one row per (identity_ref, device_id),
  rotated (replaced) on every `PublishPrekeyBundle` call for that device —
  never accumulates history.

- `device.one_time_prekeys[].public_key` / `.prekey_id`
  (added 2026-08-20, same amendment)
  Purpose: same as above, plural — a consumable pool rather than a single
  value. Persisted in `identity_one_time_prekeys`, additively appended by
  `PublishPrekeyBundle`. **Consumed one-time prekeys are deleted from this
  pool on fetch, not retained with a "consumed" marker** — once used, the
  public key serves no further purpose (its corresponding private key is
  independently, atomically deleted client-side per Cryptography & Keys'
  own amendment), and retaining it would be data collection with no
  documented purpose. The atomic claim-and-delete is a single SQL statement
  (`postgres_prekey_store.go`'s `ClaimOneOneTimePrekey`) — see that file's
  doc comment for why this is the specific mechanism that makes the
  anti-retention property hold even under concurrent claims.

- `device.identity_dh_public_key` / `device.identity_dh_public_key_signature`
  (added 2026-08-21, key-separation fix — charter §3/§6, identity.proto's
  `PublishPrekeyBundleRequest` fields 5/6 / `FetchPrekeyBundleResponse`
  fields 6/7)
  Purpose: the device's genuinely separate, DH-only X25519 public key and
  its Ed25519 signature over that key — lets another identity's device
  perform the DH computation needed to establish an E2E session with this
  device, and verify the key wasn't substituted by a compromised relay.
  Already-public, already-signed bytes generated by Cryptography & Keys —
  this service stores/relays both byte-for-byte and never generates,
  signs, or verifies them (charter §6, same "signature integrity in
  storage" discipline as `device.signed_prekey.signature` above).
  Genuinely distinct from `public_key` (identity-level, above) — that is
  the identity's Ed25519 *signing* key, this is the device's DH-only key;
  the two are never interchangeable and never the same bytes. Persisted
  as two additional columns on `identity_signed_prekeys`
  (`internal/platform/migrations/0010_identity_prekeys_dh_key.up.sql`), in
  the SAME row as the signed prekey's own columns — stable/non-rotating
  per device, but re-upserted on every `PublishPrekeyBundle` call
  alongside the rotatable signed-prekey fields regardless, since this
  service cannot derive them independently. Excluded from
  `ExportIdentity`'s output for the exact same reason the rest of this
  amendment's prekey state is (see the note below this list) — this is
  additional server-published *routing* material for the same ephemeral
  category, not a new kind of durable user data.

- `device.unconsumed_one_time_prekey_count`
  (added 2026-08-20, same amendment — Security Steward gate finding, round 1)
  Purpose: a self-only, count-only passive signal — never per-fetch, never
  per-fetcher — letting a device's own owner notice abnormal prekey
  depletion (the "Prekey exhaustion as an abuse vector" mitigation, charter
  §6), the same "security signal" purpose already established for
  `device.last_seen` above. **This is a derived count, not a new persisted
  field** — it is computed fresh on every `ListDevices` call from the same
  `identity_one_time_prekeys` pool the entry above already covers (see
  `service.go`'s `ListDevices` and `types.go`'s `Device` doc comments for
  why the field exists on the Go struct but is never itself written with a
  real value to the `identities` table's JSONB `devices` column).

**Prekey state is deliberately excluded from `ExportIdentity`'s output**
(charter §4, Art. 9) — unconsumed one-time-prekey counts and the current
signed prekey are ephemeral, automatically-regenerating routing
infrastructure, not data whose loss would harm a leaving user; a device
that rejoins or a fresh device that binds simply regenerates and
republishes on next launch. Stated explicitly here, and in `export.go`'s
`exportedDevice` doc comment and `0009_identity_prekeys.up.sql`'s own doc
comment, rather than left as a silent gap.

## Explicitly out of scope (not collected)

- No email, phone number, or other contact identifier.
- No IP address, geolocation, or device hardware fingerprint.
- No private key material of any kind — Identity only ever stores public
  keys handed to it by an already-authenticated client action.

## Notes on `device.last_seen`

This pass's implementation sets `last_seen_unix` at bind time and does not
yet update it on subsequent activity (no session/heartbeat mechanism
exists in this capability's frozen contract — `identity.proto` has no RPC
for "touch device last-seen"). This is a known, documented limitation, not
silent scope creep: the field is reserved and exported correctly today,
and a future contract addition (or a composition-layer call from whichever
capability terminates authenticated sessions) would be required to keep it
live. Flagged for the Chief Architect rather than worked around by adding
an out-of-contract RPC.
