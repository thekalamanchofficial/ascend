# Data Manifest — Storage

Per `docs/CONSTITUTION.md` Art. 8 (privacy is the default; minimum data
necessary, every collected field has a documented purpose) and the Storage
charter §4. This is the exhaustive list of fields this capability collects
and stores, on `BlobRecord` (`types.go`, marked `// ascend:persisted`).

Storage never sees, collects, or stores actual blob **content** as
plaintext — every blob it receives via `StoreBlob` is already end-to-end
encrypted by the caller before it ever reaches this service (charter §3).
The bytes Storage persists (further wrapped under its own operational key —
see "Not collected / not a data field" below) are opaque ciphertext from
this capability's point of view, for every policy, at every point.

## Fields

- `owner`
  Purpose: identifies whose data this blob is, for `ExportAllBlobs` (Art. 9)
  and to attribute audit events for store/move/delete operations (Art. 5).
  An opaque identity-reference string (Identity's format, by convention) —
  never resolved to a real name or other personal-identity attribute here.

- `blob_ref`
  Purpose: the opaque handle returned by `StoreBlob` and used by every
  other operation to address this specific blob — the minimum needed to
  let a caller (or the owner) refer to one exact piece of data without
  exposing any internal storage detail (e.g. a filesystem path) as the
  identifier itself.

- `policy_id`
  Purpose: records which storage policy (location choice) this blob is
  currently under — the field that makes "where is my data" (Art. 1, Art.
  15) a queryable fact rather than an assumption, and what `MoveBlob`
  changes.

- `size_bytes`
  Purpose: powers a "how much data do I have, and where" experience
  without requiring a caller to re-read blob content just to learn its
  size; also surfaced in `StoreBlob`'s audit metadata (Art. 5).

- `created_at_unix`
  Purpose: powers the Art. 5 "when was this stored" answer and gives
  `ExportAllBlobs` a stable ordering/reference point for a user's own
  history.

- `location`
  Purpose: the literal human-readable answer `GetStorageLocation` returns
  — this is the field that directly satisfies Art. 15 ("no data in a
  location the user cannot query and understand"). For a filesystem
  backend this is a `local-filesystem:<path>` string; for a future
  S3-compatible backend it would be that backend's own equivalent.

- `deleted` / `deleted_at_unix` / `deletion_mechanism`
  Purpose: once a blob is deleted, its `BlobRecord` is retained as a
  tombstone (no recoverable content) rather than removed outright, so
  `GetStorageLocation` and `ExportAllBlobs` can still honestly answer "what
  happened to this blob, and how" instead of returning a bare "not found"
  that erases the fact a deletion occurred. `deletion_mechanism` records
  which of the two deletion paths (`physical_delete` or `crypto_shred`) was
  actually used for this specific blob — required by this capability's
  spawn brief and Art. 15 so the deletion mechanism is inspectable later,
  never a hidden implementation detail.

## Not collected / not a data field

- No blob content is ever collected as plaintext — see the note above this
  table.
- The per-blob **outer wrapping key** generated by `StoreBlob` (`wrap.go`)
  is deliberately **not** part of `BlobRecord` and is never exported,
  logged, or otherwise disclosed. It is Storage's own operational
  deletion-guarantee mechanism (crypto-shred fallback), not a piece of data
  about the user and not a second layer of end-to-end encryption — see
  `wrap.go`'s doc comment and `docs/DECISION_LOG.md`, 2026-07-17. Keeping it
  in a separate, non-exported map (`store.go`) is a deliberate structural
  safeguard against a future change accidentally leaking it through an
  export path.
- No display name, contact information, or other personal-identity
  attribute is collected — `owner`/`requesting_subject` are opaque
  identity-reference strings this package never resolves.
- No IP address, device fingerprint, or access-pattern telemetry beyond
  what `storage.retrieve_blob`/`storage.retrieve_blob_denied` audit events
  (emitted via the injected `AuditEmitter`, not stored by this package)
  already carry.

## Retention

A `BlobRecord` (including its tombstone form after deletion) is retained
for as long as its owner's account exists, mirroring Permissions'
`Grant`/`HistoryEntry` retention policy. **Known gap, not yet wired,**
identical in shape to the one Permissions already flagged: no
account-deletion signal exists yet from any capability for this package to
subscribe to, so full-owner purge on account deletion is not yet
implemented. Tracked as a follow-up integration point — see
`docs/DECISION_LOG.md`.
