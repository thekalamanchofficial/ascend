### 2026-07-06 — Contracts source of truth: Protocol Buffers (via Buf)

**Decision:** `packages/contracts` defines capability interfaces in Protocol Buffers, with Buf for linting, breaking-change detection, and codegen to Go, TypeScript, and Python.

**Rationale:** Ascend has three consumer languages (Go backend, TypeScript mobile client, Python AI service), not two, and the stack already calls for "internal domain events" alongside request/response APIs. Protobuf gives one schema language that covers both RPC-shaped capability interfaces and event payloads, with mature codegen to all three target languages and Buf's breaking-change detection giving Article 10 (modularity — capabilities depend only on published contracts) a mechanical backstop. OpenAPI was considered but is REST/HTTP-shaped only, would need a second schema system for domain events, and Python codegen tooling is comparatively weaker than Go/TS.

**Article(s) invoked:** Art. 10 (modularity — contracts are the only cross-capability dependency surface).

**Made by:** Chief Architect.

### 2026-07-06 — Go HTTP routing: Chi over Gin

**Decision:** `services/api` uses `go-chi/chi` for HTTP routing rather than Gin.

**Rationale:** Chi is a thin, idiomatic layer directly on `net/http` — no framework-specific context type, no bundled ORM/rendering opinions. **Article(s) invoked:** Art. 10 (modularity).

**Made by:** Chief Architect.

### 2026-07-06 — Recovery mechanism: deterministic key derivation, no server escrow

**Decision:** The lost-all-devices recovery mechanism (Identity + Cryptography & Keys) works by deriving a user's identity key material deterministically from a client-side-generated recovery phrase. There is exactly one root secret with two representations (on-device key handle, human-writable phrase) — never a second, server-held encrypted key backup that the phrase merely unlocks. A new device binds itself via a self-signed assertion derived from the phrase; the server only relays and audit-logs that assertion and has no verification or override authority over it. If the phrase is lost together with every bound device, identity recovery is permanently and intentionally impossible — no support-mediated fallback exists, because any such fallback would itself be the disguised server override Article 7 forbids.

**Rationale:** Security Steward vetoed both the Identity and Cryptography & Keys charters because the original "recovery phrase" language was compatible with two designs — deterministic derivation (no server involvement possible) or an encrypted-backup-unlocked-by-phrase model (which, to survive total device loss, would need a durable copy somewhere, and the only realistic "somewhere" is the server — i.e. exactly the escrow Article 7 forbids). Committing explicitly to deterministic derivation closes that ambiguity and makes "no server-side key escrow, ever" a structural guarantee rather than a policy promise that could quietly erode later.

**Article(s) invoked:** Art. 7 (security must never reduce ownership), Art. 1 (ownership), Art. 9 (export/recoverability, bounded honestly rather than promised beyond what the design supports).

**Made by:** Chief Architect, resolving a Security Steward veto on `docs/capabilities/identity.charter.md` and `docs/capabilities/cryptography-and-keys.charter.md`.

### 2026-07-06 — Foundation contracts composition: opaque references, no live cycle

**Decision:** Identity, Permissions, and Audit / Explainability form a three-way contract reference (Identity → Audit, Audit → Identity; Audit → Permissions, Permissions → Audit; Permissions → Identity). This is resolved as follows: every cross-capability reference among the three (`identity_ref`, `subject`, `actor`) is an opaque contract-level identifier defined in `packages/contracts`, never a concrete struct owned by one capability crossing into another's package. Audit resolves actor identity and applies permission-gating lazily, at `Query`/`Explain` call time, rather than requiring all three services to be already-initialized to construct one another — so there is no live circular requirement at startup or at `Emit` time, only a contracts-level reference.

**Rationale:** Constitution Warden blocked the Identity, Permissions, and Audit charters because each charter correctly flagged the mutual-dependency risk but none resolved it — a flagged-but-unresolved cycle among three foundation capabilities is exactly the "assertion, not specifics" pattern the charter gate exists to catch. The existing mechanical Art. 10 check (`scripts/constitution/check-modularity.sh`) already anticipates cross-cutting substrates by exempting shared packages like `internal/audit` from the no-cross-import rule; combined with the Protobuf/Buf contracts decision above, opaque contract types plus lazy resolution is a standard, mechanically-checkable way to satisfy Article 10 without collapsing into a real circular package dependency.

**Article(s) invoked:** Art. 10 (modularity — capabilities depend only on published contracts, never each other's internals).

**Made by:** Chief Architect, resolving a Constitution Warden block on `docs/capabilities/identity.charter.md`, `docs/capabilities/permissions.charter.md`, and `docs/capabilities/audit-explainability.charter.md`.

### 2026-07-06 — Storage gains an explicit deletion primitive

**Decision:** Storage's interface adds `DeleteBlob(blob_ref)`: atomic, audited, permanent removal with no residual copy under the blob's storage policy. Where a backend can't guarantee true byte-level erasure, `DeleteBlob` must crypto-shred instead (destroy the blob's encryption key, making the remaining ciphertext permanently unrecoverable) — declared explicitly as an equivalent fulfillment of "deleted," not a silent gap. Storage's charter is also reworded so the plaintext boundary is unambiguous: Storage never observes plaintext at any point; encryption/decryption happens entirely within Cryptography & Keys.

**Rationale:** Security Steward vetoed the Storage charter because its original interface had no way to actually remove bytes — every version of every deleted File Object would otherwise either linger indefinitely (an undisclosed retention fact, contradicting Art. 15) or require some capability to bypass Storage's published contract to delete bytes directly (an Art. 10 violation). File Objects' `DeleteFileObject` guarantee ("no longer retrievable") was contingent on this gap being closed.

**Article(s) invoked:** Art. 15 (minimize hidden state), Art. 1 (ownership — deletion must be real), Art. 10 (modularity — no capability bypasses Storage's contract to delete bytes itself).

**Made by:** Chief Architect, resolving a Security Steward veto on `docs/capabilities/storage.charter.md`.

### 2026-07-16 — Cryptography & Keys algorithm/library choice: @noble/* + @scure/bip39, single audited CSPRNG entry point

**Decision:** Implementation in `apps/mobile/src/capabilities/crypto/` uses X25519 (Diffie-Hellman/ECDH) for all key-agreement and encryption primitives, XChaCha20-Poly1305 as the AEAD cipher, HKDF-SHA256 for key derivation, and BIP-39 (`@scure/bip39`) purely as an entropy<->mnemonic encoding for the recovery phrase — via the `@noble/curves`, `@noble/ciphers`, and `@noble/hashes` pure-TypeScript libraries (all v2.2.0), not `react-native-libsodium` or a custom native binding. Every call site that needs randomness goes through exactly one function, `random.ts`'s `randomBytes()`, which wraps `expo-crypto`'s `getRandomBytes` (native OS CSPRNG binding). No noble/scure API that has its own internal RNG (e.g. `@scure/bip39`'s `generateMnemonic()`, noble's `utils.randomPrivateKey()`) is used anywhere in this module — entropy is always generated by `randomBytes()` first and passed in explicitly (e.g. `entropyToMnemonic(randomBytes(32), wordlist)` instead of `generateMnemonic()`), so there is exactly one audited entropy source in the whole capability, satisfying the charter's "no custom entropy pooling" requirement structurally rather than by convention. `react-native-get-random-values` (a common noble-library companion polyfill) was evaluated and deliberately NOT added as a dependency, precisely because this design never lets any library reach for its own ambient `crypto.getRandomValues` — it would have been a real dependency with nothing in the code path actually calling it.

**Rationale:** `@noble/*` are pure-TypeScript, widely audited (noble-curves/noble-ciphers have had multiple third-party security audits), dependency-free, and work identically across iOS/Android/web/Jest without any native module compilation step — important for a capability with no server component, where "the client is the only implementation" means the crypto library itself carries the full trust burden. `react-native-libsodium` (a native binding) was considered and rejected for this first pass: it would require native module linking/config plugins before any code could even be tested, adds a native-build dependency to a repo that is currently pure-JS/TS scaffolding, and the pure-JS noble libraries are fast enough and audited enough that the native-binding performance argument doesn't outweigh the added build complexity here. X25519 (rather than P-256/NIST curves) and XChaCha20-Poly1305 (rather than AES-GCM) were chosen because they are the modern, constant-time-by-construction, misuse-resistant defaults used by Signal, age, and libsodium's own recommended API (`crypto_box`), and XChaCha20's 24-byte (vs. 12-byte GCM/ChaCha20) nonce removes any practical risk of nonce reuse from random generation — relevant since this module generates a fresh random nonce per encryption rather than maintaining a counter.

**Article(s) invoked:** Art. 7 (security must never reduce ownership — algorithm choice must not create a weaker-than-claimed guarantee), Art. 8 (privacy — CSPRNG sourced only from the OS, no custom entropy pooling, per charter §6 threat model).

**Made by:** Cryptography & Keys capability-engineer.

### 2026-07-16 — DeriveSharedSecret construction: symmetric-key ratchet + DH ratchet, X25519-based, session state kept out of the frozen contract's RPC surface

**Decision:** `DeriveSharedSecret` (in `apps/mobile/src/capabilities/crypto/index.ts`, backed by `ratchet.ts`) performs an X25519 ECDH between the caller's local private key and the given remote public key, derives a root key via HKDF-SHA256, and initializes a `RatchetState` (root key, a freshly generated local DH ratchet keypair, and an initial sending chain key) that is stored under the returned `shared_secret_handle` in the same opaque key registry used for private keys. Two internal, non-contract functions are also implemented and directly tested: `deriveNextMessageKey` (the symmetric/chain ratchet — each call derives a message key via HKDF and replaces the chain key with a new HKDF output, so the old chain key cannot be recomputed from the new state) and `ratchetAdvance` (the Diffie-Hellman ratchet — generates a brand-new local DH keypair and mixes a fresh ECDH output into the root key, so a new root key is unpredictable from the old one alone even to an attacker who fully compromised the old state). These two mechanisms together are what a real Double Ratchet combines to provide forward secrecy (chain ratchet) and post-compromise security (DH ratchet) per the charter §6 threat model. `ratchetEncrypt`/`ratchetDecrypt`-style per-message send/receive RPCs are deliberately NOT added to this capability's public surface, because the frozen `crypto.proto` contract only defines `DeriveSharedSecret` returning a handle — no message-level encrypt/decrypt-with-ratchet-state RPC exists in the frozen contract. Wiring per-message ratchet encryption into actual conversations is left as the entry point a future Messaging capability calls (`deriveNextMessageKey`/`ratchetAdvance` are exported from `ratchet.ts` for that purpose), not something this capability-engineer should add speculatively without a corresponding contract change.

**Rationale:** The charter explicitly leaves "double-ratchet or equivalent construction" as the capability engineer's implementation decision, gated only on the FS/PCS properties being real, not on matching Signal's exact wire protocol (X3DH's 3-DH handshake, prekey bundles, etc. — those require a prekey-publishing mechanism that doesn't exist yet since Identity's device-binding model is explicitly out of scope per the charter's §7 open questions). A single-DH handshake (rather than full X3DH) plus a genuine chain+DH ratchet afterward is the smallest construction that (a) is symmetric — both parties independently derive the identical initial root key from public keys they already have, requiring no additional out-of-band exchange the current contract doesn't support, and (b) still provides the two named security properties, tested directly in `__tests__/crypto.test.ts` ("forward secrecy" and "post-compromise security" test cases) rather than merely asserted. Building a full Signal-protocol-compatible X3DH implementation now, without a prekey-bundle contract to back it, would be over-building ahead of the interface that would actually need it — Messaging's eventual contract may shape the handshake differently once it exists.

**Article(s) invoked:** Art. 7 (security — FS/PCS are the concrete engineering guarantee behind "compromise doesn't reduce ownership retroactively or permanently"), Art. 10 (modularity — no RPC added beyond the frozen contract; extension point left for the capability that will actually consume it).

**Made by:** Cryptography & Keys capability-engineer.

### 2026-07-16 — Encrypt/Decrypt wire format: versioned multi-recipient sealed envelope (hybrid encryption)

**Decision:** `Encrypt`/`Decrypt` (in `envelope.ts`) implement a self-describing, versioned binary format: a single ephemeral X25519 keypair is generated per call to `Encrypt`; for each recipient public key, the ephemeral private key and that recipient's public key are combined via ECDH + HKDF into a per-recipient wrapping key, which encrypts a single random 32-byte content-encryption key (CEK) under XChaCha20-Poly1305; the CEK then encrypts the actual plaintext once, also under XChaCha20-Poly1305. Each per-recipient block is tagged with a truncated SHA-256 hash of the recipient's public key (not the public key itself) so `Decrypt` can find the block addressed to a given private-key handle without brute-forcing every entry or leaking which public keys were addressed to a passive ciphertext observer. The format has an explicit 1-byte version field so a future format change is detectable and rejected cleanly rather than silently misparsed.

**Rationale:** The frozen contract's `EncryptRequest` takes `repeated bytes recipient_public_keys`, i.e. multi-recipient is part of the interface, not an add-on — a naive design that just picks one recipient or duplicates the whole ciphertext per recipient would either violate the contract or waste bandwidth/storage linearly re-encrypting the same plaintext. The hybrid-encryption pattern (one CEK, wrapped per recipient) is the standard solution or this exact problem, used by age's and PGP's own multi-recipient modes for the same reason. Embedding a format version byte follows the same "documented, versioned format" discipline the charter requires of `ExportKeyMaterial`, applied here too since ciphertext produced by this module may need to remain decryptable by a later version of this same module.

**Article(s) invoked:** Art. 7 (security — recipient authentication is per-key, not an all-or-nothing shared secret), Art. 15 (minimize hidden state — the wire format is explicit and versioned rather than an undocumented internal detail).

**Made by:** Cryptography & Keys capability-engineer.

### 2026-07-16 — SecureLocalStore/Retrieve: OS keychain primary, in-memory-by-default software vault fallback, pluggable key-provider hook

**Decision:** `secureStore.ts` tries `expo-secure-store` (iOS Keychain / Android Keystore, checked live via `isAvailableAsync()` rather than assumed) as the primary backend for every `SecureLocalStore`/`SecureLocalRetrieve` call. When that backend genuinely isn't available (e.g. web, or an environment with no native module), it falls back to a "software vault": values are still always encrypted with XChaCha20-Poly1305 before being held in memory — plaintext is never written to disk on any path — but the vault's own symmetric key defaults to a random value that lives only in process memory (lost on restart) unless the app shell calls `setFallbackKeyProvider(...)` to supply a device-PIN/biometric-derived key instead. This provider hook is exported but intentionally left unwired to any real biometric API in this pass, since no UI/biometric-prompt flow exists yet in this scaffold-only mobile app.

**Rationale:** The charter's threat model asks for "a locally-derived encryption key (e.g. from a device PIN/biometric)" as the fallback, but no platform exposes raw PIN/biometric material to application code directly (biometric APIs return a yes/no authentication result, not key bytes) — any real implementation needs a platform-specific key-derivation strategy the app shell controls (e.g. gate a stored key behind `expo-local-authentication`, or a WebAuthn-backed key on web), which is a UI/platform-integration decision outside this capability's boundary, not a cryptographic one. Rather than fabricate a fake "PIN-derived" key that doesn't actually derive from a PIN (which would misrepresent the guarantee), the honest choice was: (1) never weaken the "no plaintext on disk" invariant — the vault always encrypts — and (2) make the weaker default explicit and inspectable (in-memory-only, data lost on restart) rather than silently persisting under a guessable or hardcoded key, with a clearly documented extension seam for the real per-platform key source to be wired in later without changing this module's public shape.

**Article(s) invoked:** Art. 7 (security must never reduce ownership — no silent weakening; the gap is documented, not hidden), Art. 15 (minimize hidden state — the fallback's reduced guarantee is stated in code comments and this entry, not left implicit).

**Made by:** Cryptography & Keys capability-engineer.

### 2026-07-16 — ExportKeyMaterial format: versioned JSON blob, recovery phrase deliberately excluded

**Decision:** `ExportKeyMaterial` (gated on `user_confirmation`) produces UTF-8 JSON, `format_version: "ascend-crypto-export-v1"`, containing every currently-registered private-key handle's purpose, base64 public key, and base64 private key, plus an export timestamp. The full JSON schema is documented directly in a comment block above `exportKeyMaterial` in `index.ts`. The recovery phrase itself is NOT included in the export blob — it was already shown once, in full, by the caller at `GenerateIdentityKeyMaterial` time, and this module never persists or re-derives it for re-display; the exported `identity`-purpose private key bytes are sufficient on their own to restore the identity keypair elsewhere, without needing the phrase a second time.

**Rationale:** Art. 9 requires export to guarantee the user is never locked out of their own cryptographic identity by the platform — a raw private-key export achieves that directly, and doing so in a self-describing, versioned JSON format (rather than an opaque proprietary binary blob) means the user (or a future competing implementation) can parse and use it without depending on this module's continued existence, which is the actual substance of "always able to leave" (Art. 1/9) applied to key material specifically. Excluding the recovery phrase from the export blob is a deliberate, documented boundary, not an oversight: re-surfacing the phrase on demand would mean this module retains it somewhere (in memory at minimum) beyond the single generation event, which the charter's §6 threat model explicitly forbids ("never persisted by the platform in any form, not even encrypted"); a private-key export is the constitutionally-required safety net, and it does not require reviving the phrase to provide it.

**Article(s) invoked:** Art. 9 (export always possible, in a documented format), Art. 1 (ownership — the user, not this module, is the durable source of truth for their key material), Art. 8 (privacy — recovery phrase never persisted in any form, including inside an export blob).

**Made by:** Cryptography & Keys capability-engineer.

### 2026-07-16 — Security Steward veto: DeriveSharedSecret's initial handshake lacks forward secrecy

**Decision:** Merge of the Cryptography & Keys implementation is blocked. `DeriveSharedSecret`'s initial root-key derivation (`index.ts`) uses a plain static-static X25519 ECDH between the caller's long-term private key and the remote long-term public key, with no ephemeral contribution mixed in before deriving `rootKey`/`sendingChainKey`. This means (a) every message encrypted under the chain before the first `ratchetAdvance()` call is retroactively decryptable by anyone who later obtains either party's long-term private key — the exact scenario charter §6 requires forward secrecy to prevent — and (b) because the derivation is fully deterministic, repeated `DeriveSharedSecret` calls between the same static keypair reproduce identical root/chain keys, a key-reuse hazard. Confirmed independently by Security Steward and an ephemeral crypto red-team specialist it spawned. A secondary, non-blocking finding: `audit.ts`'s `secure_local_store_write` event logs the raw `SecureLocalStoreRequest.key` string, which is safe today (console-log stub) but would leak potentially-identifying metadata if wired to a real Audit backend without first hashing the key.

**Rationale:** The chain-ratchet and DH-ratchet mechanisms implemented (`ratchet.ts`) are real and correctly tested for forward secrecy and post-compromise security *after* the initial root key exists — but the charter's forward-secrecy guarantee was implicitly assumed to hold from session start, and it doesn't: the seed itself is a deterministic function of static keys the engineer's own test suite feeds the identity private key handle into. This is a correctness gap in the specific construction chosen (single static-static DH, no ephemeral), not a flaw in the charter's requirement or the frozen contract — `DeriveSharedSecretResponse` returning only an opaque handle leaves room for an ephemeral public key to be carried alongside it without a contract change.

**Article(s) invoked:** Art. 7 (security must never reduce ownership — a forward-secrecy claim that doesn't hold from the first message is a claim the user can't actually rely on).

**Made by:** Security Steward, vetoing the Cryptography & Keys implementation at the merge gate. Required before re-review: mix a freshly-generated ephemeral contribution into the initial handshake (X3DH-style, no prekey bundle needed) plus a test proving long-term-key compromise does not expose pre-ratchet chain content; tighten `SecureLocalStoreRequest.key` handling in audit logging.

### 2026-07-16 — Test infrastructure: plain Jest + scoped Babel config + manual node_modules mocks, not jest-expo

**Decision:** `apps/mobile` gets a minimal `jest.config.js` (testEnvironment `node`, `babel-jest` transform, `transformIgnorePatterns` widened only for the `@noble`/`@scure` scopes since those ship ESM-only with no CommonJS build) and a `babel.config.js` that branches on `api.env("test")`: real Expo/Metro bundling uses `babel-preset-expo` as normal, but Jest runs under `@babel/preset-env` (explicit `modules: "commonjs"`) + `@babel/preset-typescript` instead. `expo-crypto` and `expo-secure-store` — both native-module bindings that throw or fail to parse when required outside a running Expo app — are given manual Jest mocks at `apps/mobile/__mocks__/expo-crypto.ts` and `apps/mobile/__mocks__/expo-secure-store.ts` (Jest auto-applies `__mocks__` files for node_modules packages without an explicit `jest.mock()` call per file). **Rationale:** `jest-expo` (the official Expo Jest preset) was evaluated and rejected for this module specifically: it pulls in a full React Native component-testing environment (NativeModules mocking, RN's own default mock set) that this capability doesn't need — none of this module's code renders a component or touches a React Native API directly, only `expo-crypto`/`expo-secure-store`, which still need hand-written mocks either way since Expo doesn't ship default Jest mocks for every module it publishes. A lighter, fully-understood Jest+Babel config keeps the test suite fast, keeps the exact transform behavior auditable (no inherited preset "magic"), and avoids importing test-environment complexity that belongs to whichever capability first needs to test actual RN components. The `jest-environment-node` pin is recorded here because it was a genuine, non-obvious blocker (silent Node module hoisting conflict, not a code bug) that a future engineer touching this test suite would otherwise waste time rediscovering.

**Article(s) invoked:** Art. 5 (explainability — this module's own test suite must be genuinely verifiable, not aspirational); no direct product-facing constitutional article, but recorded per the general "log every non-trivial choice" instruction since the dependency-resolution root-cause was non-obvious.

### 2026-07-16 — Fix: DeriveSharedSecret initial handshake forward secrecy (X3DH-style ephemeral contribution)

**Decision:** `initRatchetSession` (`ratchet.ts`) no longer takes a pre-computed shared secret. It now takes the local static private key and remote static public key directly and internally mixes two DH outputs into the root-key HKDF input: `staticStaticDh = X25519(localStaticPrivate, remoteStaticPublic)` (the original computation) and `ephemeralStaticDh = X25519(dhSelfPrivate, remoteStaticPublic)`, where `dhSelfPrivate` is a freshly generated, single-use X25519 private key created on every call. `rootKey = HKDF(staticStaticDh || ephemeralStaticDh)`. The freshly generated ephemeral keypair doubles as the session's initial DH-ratchet keypair (`dhSelfPrivate`/`dhSelfPublic`), so no new field was needed on `RatchetState` — `dhSelfPublic` was already the value later exposed for a future DH ratchet step, and is now also the value a future Messaging capability's key-exchange transport will need to deliver to the counterparty to complete the handshake. `index.ts`'s `deriveSharedSecret` was updated to call `initRatchetSession(entry.privateKey, request.remotePublicKey)` instead of pre-computing `x25519.getSharedSecret(...)` itself. Because two independent `DeriveSharedSecret` calls between the same static keypair now each generate their own fresh ephemeral key, they intentionally no longer produce matching root keys on their own (the previous test asserting Alice's and Bob's independently-derived root keys matched was removed — that property was exactly the key-reuse/no-forward-secrecy symptom being fixed, not a property worth preserving). Two new tests were added to `__tests__/crypto.test.ts`: "derives a fresh root key on every call, even for the exact same static keypair (no key-reuse hazard)" (two calls between the same static keypair produce different root/chain keys and different handles), and "forward secrecy at handshake time: compromising the long-term static private key does not let an attacker recompute the session's chain key derived before any ratchetAdvance() call" (recomputes the *old, vulnerable* static-static-only derivation directly using the real static private key and asserts it does NOT equal the live session's actual root/chain key). `ROOT_INFO`/`CHAIN_INFO` were exported from `ratchet.ts` so the test could perform that comparison without duplicating magic strings.

**Rationale:** Security Steward's veto (2026-07-16, "Security Steward veto: DeriveSharedSecret's initial handshake lacks forward secrecy") was correct: a static-static DH alone is fully determined by two long-term keys, so anyone who later obtains a party's long-term private key (and the counterparty's already-public key) can recompute every root/chain key ever derived from that pair — forward secrecy the charter requires from session start, not just after the first `ratchetAdvance()`. A full X3DH handshake (three DH computations against a signed prekey bundle) was considered and rejected for this pass, consistent with the original design rationale: no prekey-bundle publishing mechanism exists yet (Identity's device-binding model is out of scope per the charter's own §7 open questions), so a two-contribution mix (static-static + ephemeral-static) is the largest forward-secrecy improvement obtainable without inventing a prekey protocol ahead of the capability that would actually need to standardize it. This accepts that, for now, two independently-called `DeriveSharedSecret` invocations do not converge on a shared session by themselves — real convergence requires the ephemeral public key exchange a future Messaging capability's transport will perform, which was already the documented design intent before the fix (this fix does not change that scoping, only closes the concrete vulnerability inside it).

**Article(s) invoked:** Art. 7 (security must never reduce ownership — a forward-secrecy claim must hold from the first message, not just after the first ratchet step).

**Made by:** Cryptography & Keys capability-engineer, resolving the Security Steward veto above.

### 2026-07-16 — Grant-chain escalation rule: exact-action match, ranked scope, implicit first-grantor ownership

**Decision:** `service.go`'s `authorizeGrant` implements the charter §6 escalation rule as: (1) if the target resource (`resource_type` + `resource_id`) has no recorded owner yet, the grant is unconditionally allowed and the grantor becomes that resource's implicit owner (`Store.putGrant`'s owner-bootstrap logic) — this is the only unconditional case, and it only fires once per resource; (2) if the grantor **is** the resource's owner, the grant is always allowed, for any action/scope, on that resource; (3) otherwise, the grantor must currently hold an **active grant for the exact same `action`** on the exact same resource, with a scope that is equal-or-greater than the scope being granted, per a small explicit rank table in `scope.go` (`read` < `write` < `full` < `owner`; empty scope normalizes to `full`; any scope string outside that table is only ever "equal-or-greater" than itself, never comparable to the known tiers). Any other case is denied and both the denial and its reason (`insufficient_privilege`) are recorded in the audit event and the append-only history log. `RevokePermission` gets a parallel, separately-documented rule (`authorizeRevoke`): the resource owner may revoke any grant on their resource; the original grantor of a specific grant may revoke that same grant; and a subject may always revoke their own access (self-revocation only ever reduces standing access, so it cannot be an escalation vector).

**Rationale:** The charter's own §6 text names this as "the simplest correct rule" and specifies the ownership half almost verbatim ("the first grantor for a given resource is implicitly its owner"); the remaining design decision left to this capability-engineer was how to compare scopes and whether the action must match exactly. Requiring an *exact* action match (rather than, say, treating a "full" scope on action A as authority to grant action B) was chosen because the charter's threat model is specifically about a subject granting access they don't themselves hold — collapsing distinct actions into one comparable pool would let a `read`-only-havingsubject "launder" a scope comparison into an unrelated action, which is a strictly wider hole than the charter's example (re-sharing) describes. The rank table is intentionally small and explicit (not a general ordering function) so its behavior is auditable by reading four lines of code, consistent with Art. 12 ("power doesn't require complexity") applied to the capability's own implementation, not just its user-facing surface. Tested directly in `service_test.go`'s `TestGrantChainEscalationRejected` (a `read`-scoped grantor attempting to extend `write` scope is rejected; the same grantor re-sharing their own exact scope succeeds; a grantor attempting to grant a wholly different action they hold no grant for at all is also rejected).

**Article(s) invoked:** Art. 7 (security — least privilege; a grantor cannot manufacture authority they don't hold), Art. 5 (explainability — every denial records its reason in both the audit event and the history log, not just a bare boolean).

**Made by:** Permissions capability-engineer.

### 2026-07-16 — Sign RPC: Ed25519, purpose-namespaced key-type convention

**Decision:** Implemented `sign(privateKeyHandle, message) -> signature` in `apps/mobile/src/capabilities/crypto/index.ts`, backed by `@noble/curves/ed25519.js`'s `ed25519.sign`/`ed25519.getPublicKey` (already a transitive part of the `@noble/curves` dependency chosen for X25519 — no new dependency added). Since the frozen contract's `GenerateKeyPairRequest` has only a free-form `purpose: string` and no separate key-type field, key type is selected by a new, documented purpose-string convention (`apps/mobile/src/capabilities/crypto/keyPurpose.ts`): a purpose beginning with the `"sign:"` prefix produces and requires a signing-capable Ed25519 keypair; every other purpose (including the reserved `"identity"` purpose) remains DH-capable X25519, exactly as before this change. `generateKeyPair` now branches on this prefix to call `ed25519.getPublicKey` vs. `x25519.getPublicKey`. `sign()` looks up the handle, rejects (with an audited `sign_rejected` event) any handle whose registered purpose isn't `"sign:"`-prefixed, and otherwise returns a standard 64-byte Ed25519 signature via `ed25519.sign(message, privateKey)`. As a reciprocal guard, `decrypt()` and `deriveSharedSecret()` now reject any handle whose purpose IS `"sign:"`-prefixed, closing the same hazard from the other direction. `ExportKeyMaterial`'s documented format was updated to note that `publicKey`/`privateKey` are always 32 raw bytes but the curve depends on `purpose` per this same convention — a consumer of an export blob must branch on `purpose` exactly as this module does.

No `Verify` RPC was added, per the Chief Architect's decision above: verification needs only the already-public key and an unmodified standard algorithm, so it belongs wherever a signature needs checking (Identity, server-side), not round-tripped through this on-device-only module. The test suite proves the signature is standard, unmodified Ed25519 by verifying it with the raw `@noble/curves` `ed25519.verify` function directly in `__tests__/crypto.test.ts` ("Sign" describe block) — not via any helper this module provides, since none exists on this side. Additional tests confirm: a tampered message fails verification; a DH-capable (X25519) handle, including the identity key, is rejected by `sign()` rather than silently signed with; and, conversely, a signing-capable (Ed25519) handle is rejected by `decrypt()`/`deriveSharedSecret()`. One test independently re-derives both an Ed25519 and an X25519 public key from the *same* raw private-key bytes and confirms they differ — the concrete, executable proof of why signing-capable and DH-capable handles cannot be the same underlying key.

**Rationale:** Ed25519 was the natural choice given the existing `@noble/curves` dependency already bundles it alongside X25519 (same package, same audit history, zero new dependency surface) and it's the standard, widely-reviewed signature scheme for exactly this "device proves it holds a private key" use case (the same algorithm Signal, SSH, and most modern systems use for equivalent authentication proofs). The purpose-prefix convention (rather than, say, inferring key type from context or requiring callers to remember which purposes are which by tribal knowledge) makes the type distinction inspectable directly in code, in audit metadata (`keyType: "ed25519" | "x25519"` is now logged on every `GenerateKeyPair` call), and in the export blob's `purpose` field — consistent with Art. 15 (minimize hidden state): which curve a handle uses is never implicit. Adding reciprocal guards to `decrypt()`/`deriveSharedSecret()` (rejecting signing-purpose handles) was not explicitly requested but is the same hazard from the opposite direction, and costs two `if` checks to close now rather than leaving a latent asymmetry for whoever eventually calls those functions with a signing handle by mistake.

**Article(s) invoked:** Art. 7 (security — a device-authorization signature must be a real, correctly-scoped Ed25519 signature, not a key silently reused across two incompatible cryptographic purposes), Art. 10 (modularity — Identity depends on this published `Sign` RPC for the private-key half of `BindDevice`, not a reimplementation), Art. 15 (minimize hidden state — key type is explicit in purpose, audit metadata, and export format, never inferred).

**Made by:** Cryptography & Keys capability-engineer, implementing the Chief Architect's contract addition above.

### 2026-07-16 — Identity storage: in-memory `Store` interface, mirroring Permissions' pattern; no external UUID dependency

### 2026-07-16 — BindDevice signature verification: canonical domain-separated binding message, checked against root key or any bound device key

**Decision:** `sign.go` defines `buildDeviceBindingMessage(identityRef, devicePublicKey, deviceName) []byte`, a fixed, documented byte layout (`"ascend.identity.v1.BindDevice" || 0x00 || identityRef || 0x00 || base64(devicePublicKey) || 0x00 || deviceName`) that any `authorization_proof` must be a valid Ed25519 signature over. `authorizesBinding` (same file) accepts the proof if it verifies, via unmodified `crypto/ed25519.Verify`, against either the identity's on-file root `public_key` (the recovery-derived self-signed path) or any currently-bound device's `public_key` (the already-bound-device path) — with no further discretionary check on the recovery path, per charter §3/§7. The domain-separation prefix prevents a signature produced for this operation from being replayed as authorization for a different operation; NUL-byte field separators are safe because none of the three variable-length fields can contain a raw NUL in valid UTF-8/base64 input.

**Rationale:** `identity.proto`'s frozen `BindDeviceRequest` carries only opaque `authorization_proof` bytes — it does not itself define what byte sequence must be signed, so some concrete choice was required to make verification possible at all, and the frozen contract cannot be amended unilaterally to add a canonical-message field. A minimal, explicit, versionable construction (rather than, say, signing only the raw device public key) was chosen so the exact same proof cannot be replayed to bind the same device key to a different identity or under a different display name, closing an obvious downgrade path in the charter §6 "device spoofing" threat model. This construction is a real integration requirement for whichever client calls Cryptography & Keys' `Sign` RPC to produce `authorization_proof` (mobile) — it is not yet coordinated with that engineer directly (hub-and-spoke; this capability-engineer does not talk to other capability-engineers), so it is recorded here in full for the Chief Architect to relay.

**Article(s) invoked:** Art. 7 (security — device binding requires a genuine, non-replayable cryptographic proof, not a bare shared secret), Art. 10 (modularity — Identity depends only on Cryptography & Keys' published `Sign` contract for the private-key half; verification uses only the already-public key and an unmodified stdlib primitive, per the Chief Architect's 2026-07-16 "Crypto & Keys contract gains Sign" entry).

**Made by:** Identity capability-engineer.

### 2026-07-16 — Flagged for Chief Architect: possible curve-purpose mismatch between Identity's single `public_key` field and Cryptography & Keys' Sign purpose-convention

**Decision (none — this is a flag, not a resolution):** This capability's implementation treats every `public_key` field in `identity.proto` (the identity root key and every device key) as an Ed25519 signing-capable key, verified via `crypto/ed25519.Verify` (see the BindDevice signing-payload entry above) — this is internally self-consistent and fully tested with real Ed25519 keypairs. However, Cryptography & Keys' concurrently-logged `Sign` decision (2026-07-16, "Sign RPC: Ed25519, purpose-namespaced key-type convention," this file) establishes that its reserved `"identity"` purpose — the purpose `GenerateIdentityKeyMaterial` uses, and the natural candidate for what a real mobile client would pass as `CreateIdentityRequest.public_key` — produces a **DH-capable X25519 key, not an Ed25519 signing key**; only a separate `"sign:"`-prefixed purpose produces an Ed25519 keypair, and that engineer's own tests prove an X25519 and Ed25519 public key derived from the same private bytes differ (they are not interchangeable). If a real mobile client submits its `"identity"`-purpose X25519 public key as `CreateIdentityRequest.public_key` unchanged, `ed25519.Verify` against it will never succeed for a genuine recovery-derived self-signed assertion, because that on-file key was never an Ed25519 key to begin with — this would silently break the entire recovery path (charter §3/§7's "no discretionary authority to reject a validly-signed recovery assertion" is moot if no such assertion can ever verify).

This capability-engineer does not have the authority to resolve this unilaterally — it sits across two independently-evolving, already-frozen-or-decided surfaces (Identity's frozen `identity.proto`, and Crypto's own purpose-convention decision) and is exactly the kind of cross-capability integration question that must route back through the Chief Architect rather than being quietly special-cased by either engineer. Two resolutions seem plausible without a proto change: (a) the mobile client generates and submits a second, `"sign:"`-purpose Ed25519 keypair specifically as `CreateIdentityRequest.public_key`/each device's public key — i.e. Identity's `public_key` field is understood to mean "this identity/device's authorization key," decoupled from whatever key(s) a future Messaging/Encryption composition uses for confidentiality — or (b) the charter's Art. 8 manifest language ("the cryptographic material needed to bind devices and let others encrypt to this identity," implying one key serves both roles) needs an explicit amendment acknowledging that binding-authorization and encryption require two distinct keys under the chosen algorithm suite, with `identity.proto` documented accordingly. Not blocking this capability's own implementation or its test suite (which uses real, valid Ed25519 keypairs throughout and does not depend on Crypto's actual output), but blocking for real end-to-end mobile↔backend integration.

**Article(s) invoked:** Art. 10 (modularity — this capability depends only on published contracts and does not reach into or reinterpret another capability's internal purpose-convention unilaterally), Art. 7 (security — a recovery path that can never actually verify is a silent, disguised failure of the exact guarantee Art. 7 protects).

**Made by:** Identity capability-engineer, flagging for Chief Architect resolution.

### 2026-07-16 — Tamper-evidence mechanism: content-addressed SHA-256 hash chain, EventID is the hash

**Decision:** Every `AuditEvent`'s `EventID` is not a random UUID — it is the hex-encoded SHA-256 hash (`hash.go`'s `computeEventHash`) of a deterministic JSON encoding of the event's own fields (`actor`, `action`, `resource_type`, `resource_id`, `rule_reference`, `metadata`, `occurred_at_unix`) plus `PrevHash`, the `EventID` of the immediately-preceding event in global append order (empty string for the very first event ever emitted). Determinism across runs comes from `encoding/json`'s documented behavior of sorting `map[string]string` keys alphabetically when marshaling, so no hand-rolled canonicalization was needed. Because each event's identity is a function of its own content *and* the identity of the event before it, the events form a hash chain: `VerifyIntegrity` (`store.go`) walks a slice of events and, for each one, (a) recomputes its content hash and confirms it matches the stored `EventID`, and (b) confirms its `PrevHash` equals the previous event's `EventID`. Editing any field of any historical event, or removing/reordering an event, is detected by this walk — proven directly in `store_test.go`'s `TestVerifyIntegrity_DetectsTamperedField` (mutates a stored event's `Action` field post-hoc and confirms detection) and `TestVerifyIntegrity_DetectsBrokenLinkage` (removes a middle event and confirms the linkage break is detected).

**Rationale:** Charter §6 requires tamper-evidence "including by platform operators" — a mechanism that only prevents edits through this package's own API (e.g. simply omitting an `Update` method, as the `Store` interface also does) is necessary but not sufficient, because an operator with direct database access could still rewrite a row and no one would ever know. A hash chain makes such an edit *detectable* after the fact by anyone holding a copy of the trail (including the user themselves, via the export bundle — see the next entry), which is the concrete, checkable form of "not silently editable" the charter asks for. Content-addressing `EventID` itself (rather than a separate hash field alongside a random ID) was chosen over alternatives like a Merkle tree or per-batch signing: a Merkle tree would add complexity with no benefit for a single, strictly-ordered, single-writer-per-process event log (no need for parallel-branch proofs); a simple hash chain is the minimal mechanism that provides the required detection property and is easy for an external, non-Go reader of an exported bundle to independently re-verify (see `verification_note` in the export bundle, and the next entry).

**Article(s) invoked:** Art. 5 (explainability — a tampered trail is not really explainable; detectability is what makes the "why/when/by-what-rule" guarantee trustworthy rather than theater), Art. 1 (ownership — the user, not the platform, is the ultimate arbiter of whether their trail is intact, which requires them to be able to check it independently).

**Made by:** Audit / Explainability capability-engineer.

### 2026-07-16 — Explain template: synthesize only from the event's own fields, documented sentence shape

**Decision:** `Explain` (`explain.go`'s `renderExplanation`) builds a plain-language sentence entirely from `AuditEvent`'s own fields, using this shape: `"On <RFC3339 timestamp>, <actor> performed '<action>'[ on <resource_type> '<resource_id>'][, authorized by rule '<rule_reference>'].[ Additional context: <sorted metadata k=v pairs>.]"`. **Article(s) invoked:** Art. 5 (explainability — the literal purpose of this operation), Art. 15 (minimize hidden state — the template is documented in code and here, not an implicit convention).

### 2026-07-16 — Metadata over-collection guard: bounded size limits plus explicit purpose-only convention in DATA_MANIFEST.md

### 2026-07-16 — Found and fixed: literal marker text in prose comments crashes the shared mechanical checks; flagging a related crash in Permissions' code as out-of-scope

### 2026-07-16 — Fix: identity root key must be Ed25519 (signing-capable), not X25519

**Decision:** `generateIdentityKeyMaterial` and `restoreFromRecoveryPhrase` (`apps/mobile/src/capabilities/crypto/index.ts`) now derive the identity root public key via `ed25519.getPublicKey(privateKey)` instead of `x25519.getPublicKey(privateKey)`, and register the resulting handle under the reserved purpose `"sign:identity"` (a new `IDENTITY_KEY_PURPOSE` constant) instead of the bare `"identity"` string used previously. Under `keyPurpose.ts`'s existing `"sign:"`-prefix convention, this makes the identity key correctly signing-capable — `sign()` now accepts it, whereas before it always rejected it. `decrypt()`/`deriveSharedSecret()` now correctly reject the identity key (it's Ed25519, not X25519), which is the intended behavior: nothing in this module or its consumers calls those operations with the identity key specifically, only with separately-generated device/session keys from `GenerateKeyPair`. `mnemonic.ts` was updated to match: its doc comments and the `IDENTITY_HKDF_INFO` domain-separation string (`"ascend-crypto-v1:identity-x25519"` → `"ascend-crypto-v1:identity-ed25519"`) no longer claim a specific curve for the seed it derives — `deriveIdentityPrivateKeyFromPhrase` returns a curve-agnostic 32-byte seed; the caller (`index.ts`) decides which curve to apply it to. `ExportKeyMaterial`'s documented format and `keyPurpose.ts`'s convention comment were both corrected to state the identity key is `"sign:identity"`/Ed25519, not `"identity"`/X25519.

Test suite (`__tests__/crypto.test.ts`) updated to match: every test in the "Encrypt / Decrypt round trip" and "DeriveSharedSecret and ratchet forward secrecy / post-compromise security" describe blocks previously used `generateIdentityKeyMaterial()` results as stand-in DH-capable keys — that was always a test-fixture convenience, not a claim that identity keys are meant for encryption, but it happened to keep working only because the pre-fix bug made identity keys X25519. Both blocks now generate dedicated `generateKeyPair({ purpose: "device-session" })` keys instead, which is what those operations are actually meant to be called with. The "Sign" describe block's `"rejects a DH-capable (X25519) handle — including the identity key"` test had its identity-key assertion removed (that assertion encoded the bug, not a real invariant) and replaced with two new regression tests: one proving `sign()` now succeeds with a freshly generated identity key and the signature verifies via raw `@noble/curves` `ed25519.verify`, and a second proving the same for a `RestoreFromRecoveryPhrase`-restored identity — the exact recovery-path device-binding scenario Security Steward scrutinized hardest during chartering, because it is the only path that survives total device loss. Two new tests were also added confirming `decrypt()`/`deriveSharedSecret()` reject the identity key specifically (not just signing-purpose keys in general). `ExportKeyMaterial`'s two identity-related tests were updated to expect `purpose: "sign:identity"` and to re-derive the exported private key via `ed25519.getPublicKey` instead of `x25519.getPublicKey`.

**Rationale:** Identity's capability-engineer, implementing `BindDevice`, found that the recovery-path device-binding assertion — an already-bound device signing a binding request for a new device, using `Sign()` — could never actually be produced, because the identity key `GenerateIdentityKeyMaterial` returns was registered as a DH-capable (X25519) key, and `Sign()` (correctly, per its own contract) refuses any handle that isn't registered under a `"sign:"`-prefixed purpose. This was a real design defect shipped in the original `Sign` RPC implementation, not a caller error: the identity root key's actual job in this system — proving who a device/identity is, by signing device-binding assertions — is authentication, not confidentiality or key agreement, so it should have been Ed25519 from the moment `Sign` was added, before Identity ever tried to consume it. Coordinator confirmed the finding by reading the code directly (index.ts:67, :246, :162-168) before routing it back rather than accepting Identity's report at face value. This is treated with the same rigor as the ratchet forward-secrecy fix (2026-07-16, "DeriveSharedSecret initial handshake forward secrecy fix") because it has the identical shape: a security-relevant primitive that looked correct in isolation (Sign's own purpose-guard logic is right; GenerateIdentityKeyMaterial's derivation is right) but was wrong in composition, and wrong specifically on the one path — total-device-loss recovery — that exists precisely because every other safety net has already failed.

**Article(s) invoked:** Art. 7 (security must never reduce ownership — a recovery mechanism that cannot actually produce the proof it exists to produce is not a recovery mechanism, it's an unmet promise), Art. 10 (modularity — Identity's `BindDevice` depends on Crypto's `Sign` contract behaving as documented; the defect was in this capability's implementation of that contract, not in Identity's usage of it), Art. 5 (explainability — the regression tests make "identity key can sign, including after recovery" a directly verifiable fact, not an assumption).

**Made by:** Cryptography & Keys capability-engineer, resolving a defect found by the Identity capability-engineer and confirmed by the Chief Architect.

### 2026-07-16 — Fix: BindDevice replay — monotonic per-identity epoch bound into the signed message; `DATA_MANIFEST.md` gap closed

**Decision:** Resolving the Security Steward merge-gate veto (wave 2 entry above). `IdentityRecord` (`types.go`) gains a new persisted field, `Epoch int64`, starting at `0` at `CreateIdentity` and incremented by exactly 1 on every successful `BindDevice` and every successful `RevokeDevice` (`service.go`) — a strictly monotonic device-topology version counter, never decremented or reset. `buildDeviceBindingMessage` (`sign.go`) now takes a fourth argument, `epoch int64`, appended to the signed byte layout as a NUL-separated decimal string; `authorizesBinding` builds the verification message using `record.Epoch` as it stands *at verification time* — never a value the caller supplies — so a captured `authorization_proof` stops verifying the instant the identity's epoch advances for any reason, including a revoke. A monotonic counter was chosen over the veto's other named option (a hash of the current bound-device-ID set) after confirming the hash approach is insufficient for the exact required regression scenario: revoking device X returns the bound-device-ID set to bit-identical membership to what it was immediately before X was ever bound, so a hash-of-current-set check would let X's original proof verify again post-revoke — the epoch counter never revisits a prior value, so it does not have this gap. `export.go`'s `exportedIdentityRecord`/`ExportIdentityRecord` now include `epoch` in the export blob. `DATA_MANIFEST.md` gained two entries: `created_at_unix` (the Constitution Warden-identified gap — persisted and exported but previously undocumented) and `epoch` (documented as server-generated bookkeeping, not user-supplied data, consistent with the "every persisted/exported field is listed" discipline applied even to non-Art.-8 fields).

The required regression test, `TestBindDevice_RevokedDeviceOriginalProofReplayRejected` (`service_test.go`): binds device X at epoch 0, revokes X, replays the exact original, unmodified `authorization_proof` for X, and asserts `BindDevice` now returns `ErrInvalidSignature` and does not re-add the device — plus a same-test sanity check that a freshly-signed proof against the new current epoch (2, after one bind + one revoke) still succeeds, so the fix is proven not to be overbroad. All five pre-existing call sites that build a signing message for tests (`service_test.go` ×5, `http_test.go` ×1) were updated to pass `0` for epoch, since each corresponds to a fresh identity's first bind attempt.

Flagged, not resolved, in the same pass (documented in `sign.go`'s doc comment and not treated as blocking this fix): `identity.proto`'s response messages (`PublicIdentity`, `Device`, `ListDevicesResponse`) are frozen and expose no epoch field, so a caller cannot fetch "the current epoch" via any RPC before signing — the signer is expected to track it locally (0 at `CreateIdentity`, +1 per bind/revoke it itself observes). If a different device changed the topology in the interim, the signer's local epoch goes stale and its next `BindDevice` attempt correctly fails closed (`ErrInvalidSignature`) rather than silently succeeding on a wrong assumption — a fail-closed safety property, not a silent hole, but a real UX gap for genuine multi-device concurrent modification that a future contract revision (exposing epoch via `ResolveIdentity`/`ListDevices`) would need to close. This is a contract change outside this capability-engineer's authority to make unilaterally; routed to the Chief Architect.

**Verification:** `gofmt -l .` clean; `go build ./...` and `go vet ./...` clean for the whole `services/api` module; `go test ./...` passes for all three packages (`internal/audit`, `internal/identity` — including the new regression test — `internal/permissions`, the latter's own concurrent audit-error-handling fix landing independently and cleanly alongside this one). `bash scripts/constitution/run-all.sh` reports `OK` across all five mechanical checks repo-wide (Art. 2, 5, 8, 9, 10) — including `check-data-manifests.sh`, confirming the `DATA_MANIFEST.md` fix, and `check-audit-events.sh`/`check-export-paths.sh`, now clean thanks to the Chief Architect's shared-script hardening fix landed earlier in this same wave.

**Rationale:** Security Steward's finding was correct and, on the recovery path specifically, severe: the root identity key never rotates, so an unfixed leak of a root-signed binding proof would have been a *permanent* standing resurrection capability, not a time-bounded one. **Article(s) invoked:** Art. 7 (security must never reduce ownership — a revoke that can be silently undone by a replayed proof is a disguised loss of control, exactly what Art. 7 forbids), Art. 5 (explainability — the fix and its regression test make "a revoked device's old proof no longer works" a directly verifiable fact, not an assumption; the remaining discoverability gap is documented, not hidden), Art. 10 (modularity — fixed entirely within Identity's own internal convention, no `identity.proto` amendment).

### 2026-07-17 — Session / Request Authentication: token/nonce lifetimes, entropy sizes, and two-store design

**Decision:** `DefaultSessionLifetime = 30 minutes`, `DefaultChallengeNonceLifetime = 2 minutes` (service.go). `session_token` is 32 CSPRNG-sourced bytes, `challenge_nonce` is 24 CSPRNG-sourced bytes, both base64url-encoded via a single `crypto/rand.Read` entry point (token.go, mirroring identity/idgen.go's identical "one audited CSPRNG call site, panic if it fails" precedent). Storage is two separate in-memory, mutex-guarded maps (`nonceStore` keyed by nonce, `sessionStore` keyed by session_token — store.go), not one shared store: a consumed nonce is deleted outright rather than marked-and-kept (nothing to export, per DATA_MANIFEST.md's "not retained once consumed or expired"), while a session persists (active or expired) until explicitly revoked, so the two have different enough lifetimes/shapes that sharing one map/mutex would only couple two operations that don't need to serialize against each other.

**Rationale:** 30 minutes is short enough to genuinely bound a leaked token's blast radius (charter §6's core claim) while being long enough that automatic background renewal (fresh `GetSessionChallenge`+`IssueSession`, per charter §5/§6) doesn't need sub-minute-frequency re-signing traffic from a real client. 2 minutes for the nonce is generous slack for one real round trip (request challenge, sign, call IssueSession) while remaining "seconds/low minutes" per the charter's own data-manifest guidance. Both are within the charter's explicitly left-open range (§7: "minutes-to-low-hours, not days" for sessions; implementation-engineer discretion for the nonce) and are logged here as the concrete numeric answer, not left implicit.

**Article(s) invoked:** Art. 7 (security — short lifetime bounds leak exposure, a real not aspirational guarantee per charter §6), Art. 8 (privacy — nonce fields not retained past consumption/expiry), Art. 15 (minimize hidden state — the store-split rationale is stated here, not left implicit).

**Made by:** Session / Request Authentication capability-engineer.

### 2026-07-17 — Session / Request Authentication: nonce anti-replay via peek-then-atomic-consume, verified under concurrency

**Decision:** `IssueSession` (service.go) implements charter §3's five ordered steps exactly: (1) `nonceStore.peek` — a fast, non-mutating existence/expiry/binding check used only to fail fast before touching the DeviceResolver or verifying a signature; (2) `DeviceResolver.ResolveDevicePublicKey`; (3) `ed25519.Verify` against the canonical domain-separated message (sign.go, byte-for-byte the layout the frozen `sessionauth.proto` file header already specifies, NUL-separated fields matching `identity/sign.go`'s `buildDeviceBindingMessage` construction style); (4) `nonceStore.consumeIfValid` — a single mutex-guarded critical section that re-validates and deletes the nonce atomically, called only AFTER step 3 succeeds; (5) session creation. Because verification (step 3) is a pure function with no store-mutation side effect, two goroutines racing the identical captured `(nonce, proof)` pair can both pass steps 1-3, but only one can ever win the atomic step-4 consume — proven directly by `TestIssueSession_ReplayRejected_ConcurrentDuplicateRequestsOnlyOneWins` (25 goroutines firing the exact same request; asserts exactly 1 success), in addition to the simpler sequential-replay test.

**Rationale:** The charter's own language ("must happen atomically with, or immediately after, successful verification, such that a captured, already-used IssueSession request can never succeed twice, even under concurrent replay attempts") is a concurrency claim, not just a logical-ordering one — a sequential "call it twice" test cannot by itself distinguish a genuinely atomic consume from a check-then-act race that only manifests when two requests are in flight simultaneously, so a dedicated concurrent test was added rather than treating the sequential replay test as sufficient evidence of the atomicity property.

**Article(s) invoked:** Art. 7 (security — the anti-replay guarantee must hold under real concurrent adversarial conditions, not just in a single-threaded test), Art. 1 (ownership — the only path to a session is a fresh, unforgeable device signature).

**Made by:** Session / Request Authentication capability-engineer.

### 2026-07-17 — Session / Request Authentication: ValidateSession anomaly threshold, and hashing session_token before it ever reaches the audit trail

**Decision:** `anomaly.go`'s `failureTracker` emits the charter §4 "repeated ValidateSession failures" audit signal (`sessionauth.validate_session_anomaly`) after 5 failures for the same session_token within a 1-minute sliding window, resetting the window on trip so a sustained failure stream emits the signal once per window rather than on every subsequent failure. Every place a session_token might otherwise reach an audit call (the anomaly event's resource ID, `RevokeSession`'s and `RevokeAllSessions`' rejection-path events for an unknown/invalid caller token) uses `tokenFingerprint` (token.go — truncated SHA-256, hex-encoded) instead of the raw token, mirroring Cryptography & Keys' `auditFingerprint` precedent (2026-07-16, "Fix: hash SecureLocalStore key names before they reach audit metadata"). `TestValidateSession_RepeatedFailuresEmitAnomalyAuditEvent` asserts both the trip count and that the raw bad token never appears in the emitted event's resource ID.

**Rationale:** 5/minute is well above what ordinary clock skew or a slightly-stale cached token re-presented once or twice after `RevokeSession`/natural expiry would produce, while tight enough to catch a script probing a stolen or guessed token — charter §7 explicitly leaves the exact threshold to this capability engineer. Hashing the token before it reaches any audit call site is a structural requirement, not a style preference: `session_token` is explicitly documented in DATA_MANIFEST.md as a live bearer credential that must never appear verbatim outside the session store itself (the audit trail is not a secret store), so logging it raw in a "someone is trying stolen tokens" signal would be actively counterproductive — it would hand the very credential being investigated to anyone who can read the audit trail.

**Article(s) invoked:** Art. 5 (explainability — "has someone been trying to use a stolen/expired session as me" must be answerable without flooding the trail with routine-success noise), Art. 8 (privacy — a sensitive value is hashed before it reaches audit metadata, never logged verbatim).

### 2026-07-17 — Storage backend: local filesystem, two named policies, real physical delete

**Decision:** `services/api/internal/storage/backend.go` defines a `Backend` interface (`Store`/`Retrieve`/`Delete`/`SupportsPhysicalDelete`/`Location`) and one concrete implementation, `FilesystemBackend`, storing each blob as one file under a root directory (`DefaultDataDir`, computed relative to the package's own source location via `runtime.Caller`, not the process's working directory — so behavior is identical regardless of where the binary is launched from). `services/api/internal/storage/default.go`'s `NewFilesystemService` (the production-shaped constructor, not wired into `main.go` — see the standing rule below) registers **two** named policies, `local-default` and `local-secondary`, both backed by real `FilesystemBackend` instances rooted at different subdirectories of `.data/` (gitignored). `ListStoragePolicies` only ever advertises policies actually registered on a `Service` instance, each backed by a real, working `Backend` (enforced at `NewService` construction time, not left as a runtime possibility) — so it never advertises a location choice this instance cannot currently honor (charter §5/§6).

**Rationale:** No S3-compatible object store is deployed anywhere in this environment (per this capability's spawn brief), and a real local filesystem is the simplest backend that genuinely, physically supports true byte-level erasure — the "primary, preferred" `DeleteBlob` path the charter requires implementing for real, not simulated (`TestFilesystemBackend_StoreRetrieveDelete` asserts the file is gone from disk via `os.Stat`, not merely unreachable through this package's API). **Article(s) invoked:** Art. 1 (deletion must be real — physical delete implemented and tested against a real filesystem, not simulated), Art. 15 (no data in an unqueryable location — `Location()` and `GetStorageLocation` are backed by a real, inspectable path), Art. 10 (modularity — `Backend` is the swap seam for a future object-storage implementation).

**Made by:** Storage capability-engineer.

### 2026-07-17 — Storage wrapping-key construction: AES-256-GCM (stdlib), per-blob keys, never persisted or exported

**Decision:** `services/api/internal/storage/wrap.go` implements the outer, Storage-owned wrapping envelope (resolved design per the 2026-07-17 "Storage interface frozen; crypto-shred fallback resolved..." entry above) using Go's standard library `crypto/aes` + `crypto/cipher` (AES-256-GCM), not `golang.org/x/crypto/chacha20poly1305`. Every blob gets its own freshly generated 256-bit key from `crypto/rand` (`generateWrappingKey`) — never one shared, service-wide wrapping key. Keys are held only in `Store`'s `wrappingKeys` map (`store.go`), a structure deliberately separate from the exported/persisted `BlobRecord` type, and are zeroed (`zeroBytes`) before being dropped on destruction.

`TestDeleteBlob_CryptoShredPath` (`service_test.go`) proves the guarantee directly rather than asserting it: it captures the wrapping key via a test-only accessor and independently decrypts the raw sealed bytes sitting in the fake backend *before* deletion (proving the key/ciphertext relationship is real); calls `DeleteBlob` against a backend whose `SupportsPhysicalDelete()` is `false`; then asserts the key is genuinely absent from the store afterward, the sealed bytes are still physically present in that backend (this is the whole premise of needing the fallback), and that opening those still-present bytes with the correct key's own length but zeroed content fails. Getting this test to actually exercise the fallback required fixing `fakes_test.go`'s `fakeBackend.Delete`, which originally deleted its in-memory bytes unconditionally regardless of `SupportsPhysicalDelete` — a real bug in the test double (not the production code), since it made the crypto-shred branch's "bytes may still physically remain" premise untestable. **This is very likely the same failure the Session / Request Authentication capability-engineer observed and logged as a possible flake in its own 2026-07-17 "implementation complete" entry** (an `internal/storage` failure seen once on a full-suite run, not reproducing on a second run) — the timing lines up with this fix landing mid-session; recorded here to set the record straight: it was a real, since-fixed bug in this package's own test fake, not an intermittent flake, and not present in the merged result.

**Rationale:** Stdlib AES-GCM was chosen over `chacha20poly1305` (this capability's spawn brief explicitly allowed either) specifically to avoid adding `golang.org/x/crypto` as a new `go.mod` dependency for a purely backend-internal, non-end-to-end concern — `services/api`'s existing dependency set (`chi`, `grpc`, `protobuf`) has no crypto library dependency yet, and AES-GCM is sufficient for an operational, non-network-facing envelope (this key is never transmitted or exposed to a network peer, and each key seals exactly one blob, once, so XChaCha20's extended-nonce motivation — see Cryptography & Keys' 2026-07-16 rationale — does not apply here). Per-blob (rather than one global) keys were chosen so that destroying one blob's key never affects any other blob — a global key would mean the first crypto-shred delete on any blob under a non-physical-delete backend would either have to shred every other blob sharing that key too, or never actually be destroyed at all. Keeping keys in a map structurally separate from `BlobRecord` (rather than a struct field with a `json:"-"` tag) is defense in depth: a future change to `BlobRecord`'s export path cannot accidentally leak a wrapping key merely by forgetting a tag, because the key was never reachable from that type at all.

**Article(s) invoked:** Art. 7 (security must never reduce ownership — but this key is explicitly NOT end-to-end content encryption and must never be described to a user as a second layer of it; documented in `wrap.go`'s doc comment, `DATA_MANIFEST.md`, and here), Art. 15 (minimize hidden state — the wrapping key's existence, purpose, and non-end-to-end status are documented, not left implicit; the test-fake bug and its fix are also documented here rather than left as an unexplained coincidence with another capability's log entry), Art. 8 (privacy — the key itself is explicitly excluded from `DATA_MANIFEST.md`'s collected-fields list with a stated reason, not silently omitted).

**Made by:** Storage capability-engineer.

### 2026-07-17 — Storage: CheckPermission action-name convention, extended to MoveBlob/DeleteBlob beyond the charter's literal text

**Decision:** `RetrieveBlob`, `MoveBlob`, and `DeleteBlob` all call `PermissionChecker.CheckPermission(requesting_subject, action, "blob", blob_ref)` before taking effect, using `resourceType = "blob"` and one of three action constants (`types.go`): `ActionRetrieveBlob = "storage.retrieve_blob"`, `ActionMoveBlob = "storage.move_blob"`, `ActionDeleteBlob = "storage.delete_blob"`. This capability's spawn brief and the charter's own §3 text explicitly require the permission-check gate only for `RetrieveBlob` ("`RetrieveBlob` must call ... `CheckPermission` ... before returning data"); gating `MoveBlob`/`DeleteBlob` the same way goes beyond that literal text.

**Rationale:** Both `MoveBlobRequest` and `DeleteBlobRequest` carry a `requesting_subject` field in the frozen contract — the same field `RetrieveBlobRequest` carries specifically so it can be permission-checked — and both are irreversible or user-visible-consequential actions (an unauthorized `DeleteBlob` would let anyone who merely knows a `blob_ref` permanently destroy someone else's data; an unauthorized `MoveBlob` would let anyone silently relocate it). Leaving them ungated while gating only `RetrieveBlob` would be an internal inconsistency this capability-engineer judged indefensible under Art. 7 ("security must never reduce ownership") given the contract already carries the exact field needed to gate them the same way, at no cost to any legitimate caller and no change to the frozen wire contract (the gate is an internal authorization check, not a new RPC field). This is flagged explicitly, rather than silently done, because it is a deliberate reading of intent beyond the literal charter text — if the Chief Architect judges this incorrect (e.g. if some composition layer needs `MoveBlob`/`DeleteBlob` callable without a corresponding Permissions grant existing yet), it is a one-line reversion in `service.go`, not a contract change.

**Article(s) invoked:** Art. 7 (security must never reduce ownership), Art. 1 (ownership — only the owner, or someone the owner granted access to, may relocate or destroy their data), Art. 10 (the gate is enforced via the same injected `PermissionChecker` interface already used for `RetrieveBlob`, no new cross-capability dependency).

**Made by:** Storage capability-engineer. Flagged for Chief Architect awareness as a judgment call beyond the charter's literal text, not a contract change.

### 2026-07-17 — Storage: StoreBlob rolls back on audit-emit failure, diverging from the Permissions/Identity precedent

**Decision:** `StoreBlob` (`service.go`) is the one mutation in this capability that does NOT follow Permissions'/Identity's established "audit emit failed after a mutation already landed → return an error, but leave the mutation committed" pattern (see e.g. `internal/permissions/service.go`'s `GrantPermission`/`RevokePermission`, and this log's wave-2 entries). Instead, if the audit emit fails after `StoreBlob` has already written the sealed bytes to a `Backend` and recorded a `BlobRecord`, it deletes the backend write and the metadata record (and destroys the just-generated wrapping key) before returning the error — a true rollback, not merely a loud failure. `MoveBlob` and `DeleteBlob` both keep the original precedent (mutation stands, error surfaces loudly) — this divergence is specific to `StoreBlob`.

**Rationale:** `StoreBlobResponse.blob_ref` is the ONLY handle its owner will ever receive to a newly stored blob — there is no `List`/`Query` RPC in this contract that could later recover an orphaned `blob_ref` the caller never got. If the audit emit fails and the write is left committed anyway (matching the Permissions/Identity precedent), the result is a blob that genuinely, permanently exists, consumes storage, and is attributed to a real owner, but that owner has no way to ever learn its `blob_ref`, retrieve it, move it, or delete it — a strictly worse Art. 15 hidden-state hazard than the cases the existing precedent tolerates (a denied/failed Permissions grant, for instance, has no such "only ever reachable via this one response" property; the caller already knows what they attempted and can retry). `MoveBlob`/`DeleteBlob` don't have this problem — their blob remains reachable via the same, already-known `blob_ref` regardless of whether the audit emit for that specific call succeeded — so they correctly keep the original, less destructive precedent.

**Article(s) invoked:** Art. 15 (minimize hidden state — an unreachable, un-audited blob would be exactly the kind of hidden state this article forbids), Art. 5 (explainability — every important action, including a rolled-back one, must be discoverable; the rollback itself is not separately audited because the mutation it undoes was never durably observable to begin with), Art. 1 (ownership — a blob the owner can never reach is not really theirs in any usable sense).

**Made by:** Storage capability-engineer.

### 2026-07-17 — File Objects: pre-freeze interface amendment closes a missing content-retrieval path

### 2026-07-17 — File Objects re-gate: Experience Guardian and Security Steward pass; Constitution Warden finds a real end-to-end composition gap

**Decision:** Experience Guardian initially blocked (§5 didn't commit to a zero-config default for the new read path, and left the `GetFileHistory`/`ListVersions` composition question unstated — the same shape of gap Session/Auth's charter was blocked for), then passed after §5 was amended to commit to default-to-current-version-on-open and one merged history/version timeline with no separate Versions screen. Security Steward passed the amended charter outright on its first re-gate pass, independently confirming (against the real Storage/Permissions implementations, not the charter's prose) that the `GetFileContent` per-version bypass is closed, `ExportFile` genuinely avoids Storage's tracked ungated-bulk-export gap, `SetFilePermissions`' delegation can't become a privilege-escalation side channel, and `DeleteFileObject`'s content-unreachability guarantee holds independent of permission-record state.

**Constitution Warden blocked with a real, load-bearing finding, found by reading the actual code rather than the charter's claims:** `GetFileContent`/`ExportFile` delegate to Storage's `RetrieveBlob`, which performs its **own independent** `CheckPermission` against resource type `"blob"` (`services/api/internal/storage/types.go`, `resourceTypeBlob`/`ActionRetrieveBlob = "storage.retrieve_blob"`) — a separate Permissions resource namespace from anything File Objects checks. Traced end to end: nothing in either capability's contract ever establishes a `"blob"`-level Permissions record (`Storage.StoreBlob` never calls `DefinePolicy` or `GrantPermission` for `"blob"`), so as originally specified, Storage's own check would fail closed on every `RetrieveBlob` call regardless of what File Objects' own permission decision was — the entire read path this amendment exists to add could not have worked. Two bad fixes were explicitly ruled out: an undocumented, engineer-invented blob-grant-bootstrapping scheme (Art. 10 — the charter must own cross-capability composition, not leave it to be discovered mid-implementation), and passing a synthetic/service subject to Storage instead of the true caller (the confused-deputy pattern Permissions' own charter §6 forbids). Also found: the Art. 2 mechanical check (`check-file-objects.sh`) requires a field-name substring match for "History" on any `// ascend:file-object`-marked struct, but the charter's described data model (history lives in Audit) would plausibly fail that check as written; the self-emit-on-denial audit obligation was inconsistently scoped to only `GetFileContent` when its own reasoning applies equally to `ListVersions`/`GetFileMetadata`; and `ExportFile`'s multi-version content bundling wasn't explicitly held to the same per-version gating discipline `GetFileContent` was.

**Resolved:** §3/§4/§6 amended with a full design — File Objects owns exactly one primary Permissions resource, `"file_object"`, with exactly two defined actions (`fileobjects.read`, `fileobjects.write`), and transparently mirrors matching `"blob"`-level grants underneath at `CreateFileObject` (bootstrap), `CreateVersion` (propagate existing grants to new versions), and `SetFilePermissions` (mirror every grant/revoke onto every existing version's blob). This is bookkeeping via Permissions' own `GrantPermission`/`RevokePermission` calls, not a second access-control decision — Storage's own blob-level check remains real defense-in-depth, never disabled or routed around, and the confused-deputy risk is avoided because File Objects always passes the true `requesting_subject` through to Storage, never a synthetic identity. The Art. 2 struct requirement and the audit-scoping/`ExportFile`-per-version gaps are also closed in the same pass (§4, §6). Sent back to Constitution Warden for re-review of this design specifically.

**Rationale:** This is the deepest architectural finding of the whole Phase 1 build so far — not a missing field or an unaudited call, but two already-`stable`, already-guardian-approved capabilities (File Objects' design, Storage's frozen contract) that individually make sense but don't compose without an explicit bridging design. Worth recording as a general lesson alongside the Crypto/Identity/Storage findings: composing two capabilities that each independently gate access on their own resource type is not free — the composing capability must own keeping both resource namespaces in sync, and that ownership must be stated in the charter, not discovered by an implementing engineer.

**Article(s) invoked:** Art. 10 (modularity — the composition boundary between File Objects and Storage's independent permission checks now has an explicit, charter-owned design), Art. 7 (no confused-deputy shortcut was taken to make the read path "just work"), Art. 1 (a revoke must actually revoke access at every layer that could otherwise still grant it), Art. 2 (the mechanical-check fix).

**Made by:** Chief Architect, resolving Constitution Warden's blocking finding.

### 2026-07-17 — File Objects re-gate, round 2: policy-registration gap traced to a pre-existing defect in Storage; ownership-bootstrap hazard closed

**Decision:** Constitution Warden's second pass on the dual-layer permission design confirmed points 2-4 (Art. 2, Art. 5, `ExportFile` gating) as genuinely resolved, but found the design still didn't clear its own first gate: `Permissions.CheckPermission` fails closed on `!hasPolicy(resource_type)` *before* the owner/grant check the design spent its effort establishing — and nothing anywhere calls `Permissions.DefinePolicy` for `"file_object"` or `"blob"` in real service wiring (confirmed by a full-tree grep; only Permissions' own unit tests call it). Tracing this further: **this is a pre-existing, latent defect in Storage's own already-`stable` implementation**, not something File Objects introduced — `Storage.RetrieveBlob`/`MoveBlob`/`DeleteBlob` all call `CheckPermission` against `"blob"`, but Storage's own `NewFilesystemService` never registers that resource type's policy, so against a real (non-fake) Permissions instance, every call would fail closed, including for the blob's own owner. Invisible until now because nothing has been wired to a real Permissions instance and every capability's own tests use fakes. Separately, Constitution Warden found a genuine ownership-bootstrap hazard in the mirroring design itself: `CreateVersion`'s grant-mirroring loop, if it used an unspecified/naive grantor identity, could let a non-owner collaborator (holding only `fileobjects.write`) become a *new* blob's permanent, unrevocable Permissions-owner via `bootstrap_owner` semantics (Permissions' `Store` has no owner-transfer mechanism) — a real Art. 1/7 ownership-integrity violation.

**Resolved:** §6 point 0 (new) states each capability registers its own resource type's default policy at its own construction — File Objects registers `"file_object"`, and Storage (separately, tracked as task "Fix Storage: register 'blob' Permissions policy at construction") registers `"blob"`; File Objects' merge gate is stated to depend on the Storage fix landing first, and File Objects must not work around the gap by registering `"blob"` on Storage's behalf (that would be the exact Art. 10 encroachment the finding warned against). §6 point 3 now requires `CreateVersion`'s mirroring loop to grant the file object's actual owner first, deterministically, on every new blob, before mirroring any other subject's grant — closing the bootstrap-ownership hazard. §6 point 4 now requires `SetFilePermissions`' revoke-mirroring loop to fail loudly, not report success, on partial failure. The Storage fix itself is dispatched to a capability-engineer in parallel (this is additive, non-breaking — one `DefinePolicy` call in Storage's constructor plus a test proving it — not a design change to Storage's existing guarantees, so a fast Security Steward confirmation rather than a full re-gate is appropriate once it lands).

**Rationale:** Worth stating plainly: this second finding is the same *class* of lesson as the first (a real gap only surfaces when you trace actual code, not charter prose), but one level deeper — it wasn't caught at Storage's own merge gate because nothing at that point needed the full chain (real Permissions instance, real policy registration, real grant bootstrap) to actually work end-to-end. File Objects is the first capability whose correctness depends on that full chain, which is exactly why chartering it surfaced a defect two capabilities upstream. This is a strong argument for the standing practice (already followed) of re-verifying composition end-to-end at each new capability's charter gate, not just trusting that already-`stable` capabilities compose correctly by virtue of each having individually passed its own gate.

**Article(s) invoked:** Art. 10 (each capability owns registering its own resource type's default policy — a clean, generalizable boundary rule, not just a one-off fix), Art. 1/Art. 7 (the ownership-bootstrap hazard directly threatened the "owner" concept's integrity), Art. 5 (this entire chain of findings is recorded here specifically so a future capability hitting the same composition pattern doesn't have to rediscover it).

**Made by:** Chief Architect, resolving Constitution Warden's second-round blocking finding; Storage fix dispatched to a capability-engineer in parallel.

### 2026-07-17 — Storage: register 'blob' Permissions policy at construction (closing a real fail-closed gap)

**Rationale:** `Permissions.CheckPermission` (`services/api/internal/permissions/service.go`) fails closed on `!hasPolicy(resource_type)` *before* its owner/grant lookup runs. `RetrieveBlob`/`MoveBlob`/`DeleteBlob` all call `CheckPermission` against `resourceType = "blob"`, but nothing in this package (or anywhere in `services/api`'s real service wiring — confirmed by a full-tree grep) ever called `Permissions.DefinePolicy("blob", ...)`. **Article(s) invoked:** Art. 10 (modularity — the fix is a same-capability construction-time call through this package's own DI interface, no new cross-capability import; the test-approach correction is itself an Art. 10 mechanical-check finding), Art. 7 (security must never reduce ownership — this fix is what makes a blob's own owner actually able to reach their own data against a real Permissions instance, closing an unintended total-denial defect), Art. 1 (ownership — ownership is meaningless if the owner is unconditionally denied), Art. 5 (the registration failure path fails loudly, as a construction-time error, rather than silently).

### 2026-07-17 — File Objects: version storage strategy is full copy per version, not delta

**Decision:** Every `CreateVersion` call stores the caller's full, complete content as a brand-new, independent Storage blob (`Service.CreateVersion` → `s.storage.StoreBlob`) — never a delta/diff against a prior version. Charter §7 required this decision to explicitly confirm two properties hold under whichever strategy was chosen: (1) **per-version `CheckPermission` gating is unaffected** — true by construction here, since every version is an independently-addressed, independently blob-level-permission-gated Storage object with no reconstruction step at read time (`GetFileContent`/`ExportFile` call `Storage.RetrieveBlob` once per version, gated exactly like any other blob); (2) **no intermediate delta blob is independently reachable or can be orphaned outside `DeleteFileObject`'s atomic teardown** — trivially true because no intermediate/delta blob exists at all under this strategy; every blob a version's `VersionRecord.BlobRef` points at is a complete, independently retrievable artifact, and `DeleteFileObject`'s teardown loop (`store.go`'s `listVersions` + `storage.DeleteBlob` per version) covers every blob this capability ever created, with nothing else to account for.

**Rationale:** Delta/diff storage would have required either (a) a reconstruction step at `GetFileContent`/`ExportFile` time that walks a chain of prior versions' blobs before returning content — directly complicating the "per-version `CheckPermission` gating is unaffected" property the charter demands be confirmed, since a chain reconstruction would need read access to every ancestor blob, not just the requested version's — or (b) a separate, File-Objects-owned diff/patch storage mechanism entirely outside Storage's own blob abstraction, which charter §4 Art. 10 forbids ("File Objects composes Storage... through their published contracts only; it adds no independent storage... logic of its own"). Full-copy-per-version avoids both problems by construction and keeps every version exactly as independently governable (and independently deletable) as `CreateFileObject`'s own version 1 already was under charter §6's design — no special-cased reconstruction path for GetFileContent to get wrong, and no delta blob that could ever end up orphaned by a partial `DeleteFileObject` failure (there are none to orphan). The storage-efficiency cost of full copies is a legitimate, revisitable future optimization, but not one this implementation wave needed to take on to satisfy the charter.

**Article(s) invoked:** Art. 10 (modularity — no independent storage mechanism invented), Art. 15 (minimize hidden state — no delta blob exists to become orphaned/hidden), Art. 9 (export — `ExportFile` can retrieve every version's complete content directly, with no reconstruction step that could silently fail or omit an ancestor).

**Made by:** File Objects capability-engineer.

### 2026-07-17 — File Objects: grant-cleanup-on-delete revokes both resource namespaces, best-effort

**Decision:** `DeleteFileObject` (`service.go`) does revoke every active grant it can enumerate on both resource namespaces this capability owns: every active grant on `("file_object", file_object_id)` (via `ListGrantsForResource` + `RevokePermission`, grantor always the file's owner) and every active grant on every version's `("blob", blob_ref)`. This cleanup step is **best-effort, not fail-loud** — unlike the content-deletion loop immediately above it (which DOES block marking the file object deleted if any version's `Storage.DeleteBlob` call fails), a failed `RevokePermission` call during grant cleanup is silently ignored (`_ = s.perms.RevokePermission(...)`) and does not prevent `DeleteFileObject` from completing and reporting success.

**Rationale:** Charter §7 explicitly named this as a required, not-charter-blocking decision, and explicitly named the justifying example this implementation adopts: **content deletion already makes any lingering grant record moot**, because by the time grant cleanup runs, every version's blob has already been irreversibly destroyed (physical delete or crypto-shred, Storage's own charter-committed guarantee) — a stale grant record pointing at a `blob_ref` whose content no longer exists poses no residual content-access risk, only a harmless bookkeeping inconsistency in Permissions' own store. Making grant cleanup fail-loud (blocking the delete from completing) would create a strictly worse outcome than skipping it: a caller could correctly destroy all content, yet have `DeleteFileObject` report failure and leave the record un-tombstoned, purely because an unrelated Permissions bookkeeping call failed — exactly backwards from what "the file is genuinely gone" should mean to a user. Attempting the cleanup at all (rather than skipping it entirely) still matters for Permissions' own store hygiene and to prevent `ListGrantsForResource` on a deleted file object from returning stale-looking "active" grants indefinitely — it is done, just not treated as blocking. The content-deletion loop that precedes it remains fail-loud and names the specific failed version(s) in its returned error, per charter §3's "no longer retrievable is a real guarantee" — only the grant-cleanup step is best-effort.

**Article(s) invoked:** Art. 1 (ownership — content-unreachability is the guarantee that actually matters to the user, and it must not be gate-kept by an unrelated bookkeeping failure), Art. 15 (minimize hidden state — cleanup is still attempted, not silently skipped, even though it isn't blocking), Art. 7 (security must never reduce ownership — a fail-loud cleanup step here would make deletion *less* reliable, which would itself reduce the user's ownership over "is my data actually gone"), Art. 5 (the content-deletion failure path is fail-loud and names the affected versions explicitly).

**Made by:** File Objects capability-engineer.

### 2026-07-17 — File Objects: DeleteFileObject gated by fileobjects.write; no third action invented

**Article(s) invoked:** Art. 10 (the frozen contract's own action vocabulary is not expanded unilaterally), Art. 7 (no ad hoc, Permissions-bypassing local authorization check).

### 2026-07-17 — File Objects: FileObjectRecord and VersionRecord carry separate Art. 2 / Art. 9 markers

**Decision:** `FileObjectRecord` (`types.go`) is marked `// ascend:file-object` only; `VersionRecord` is marked `// ascend:persisted` only and ships its own `ExportVersionRecord` function plus `version_record_export_test.go`. The two markers are never stacked on the same struct declaration.

**Article(s) invoked:** Art. 2 (files first-class — verified mechanically effective, not just present), Art. 9 (exportability — VersionRecord gets a real, CI-checked export path; FileObjectRecord's is the charter-specified `ExportFile` RPC itself).

### 2026-07-17 — Storage: concurrency-harden DeleteBlob/MoveBlob (per-blob_ref operation lock)

**Decision:** `Store` (`store.go`) gains `opLocks sync.Map` (keyed by `blob_ref`, values `*sync.Mutex`) and a `lockBlob(blobRef string) func()` method (`sync.Map.LoadOrStore` to get-or-create the mutex, `Lock()`, returns `Unlock`). `DeleteBlob` and `MoveBlob` (`service.go`) each acquire this lock — `unlock := s.store.lockBlob(req.BlobRef); defer unlock()` — immediately after the permission check and before the first `s.store.get(req.BlobRef)` call, holding it across the entire remaining check-then-act sequence (read record, decide, mutate backend(s)/wrapping key, write record, emit audit). This closes the gap Security Steward flagged at Storage's original merge gate: the existing `Store.mu sync.RWMutex` only ever made each individual map read/write atomic in isolation, not the multi-step sequence built from several such calls — two concurrent `DeleteBlob` calls for the same `blob_ref` could previously both observe `Deleted == false` before either wrote the tombstone back, and both would then run the deletion mechanism and report success. Different `blob_ref`s never block each other (the lock is per-key, not a single service-wide mutex), so this does not become a whole-service bottleneck as blob count grows. `RetrieveBlob`, `StoreBlob`, and `GetStorageLocation` were deliberately left unchanged — none of them has a check-then-act sequence whose interleaving could produce an inconsistent result (`RetrieveBlob`/`GetStorageLocation` are pure reads after their gate; `StoreBlob` only ever creates a brand-new, unique `blob_ref`, so no other call can race it for the same key).

**Behavior chosen for concurrent duplicate MoveBlob requests:** "both calls safely serialize and both report success" (not "one succeeds, one fails"). Whichever call acquires the lock first performs the real relocation; the second, once unblocked, re-reads the now-updated record and — via `MoveBlob`'s pre-existing "already at this policy" no-op branch (unrelated to this fix, already in the merged code) — reports success with a real, audited no-op rather than an error. This was chosen because a caller that legitimately retried an ambiguous prior request (the realistic source of "concurrent duplicate requests" in production — e.g. a network timeout followed by a client-side retry) should not need to distinguish "my call performed the move" from "an identical concurrent call already did" to know its data safely ended up at the requested policy; failing the second call would incorrectly signal that the retry itself failed, when the caller's actual goal (the blob is now at `new_policy_id`) was met. `DeleteBlob`, by contrast, correctly returns `ErrBlobAlreadyDeleted` (not success) for the losing call — this is intentional and pre-existing (not changed by this fix): a delete's very premise is "this had not already happened," so unlike a move's idempotent target-state check, a second delete attempt reporting success would misrepresent that the caller's own call was what removed the data.

**Testing (no `-race` available — `gcc` re-confirmed absent in this environment):** `service_concurrency_test.go`, following Security Steward's own precedent for Session/Request Authentication's nonce-consumption proof (mutation-testing a deliberately broken variant in an isolated copy, since `-race` cannot run here), adds two tests, each running `concurrencyTestIterations = 200` independent trials with `raceGOMAXPROCS` forcing `GOMAXPROCS >= 4`:
- `TestDeleteBlob_ConcurrentDuplicateRequests_ExactlyOneSucceeds`: 16 concurrent goroutines call `DeleteBlob` for the same freshly-stored `blob_ref`, released via a closed channel to maximize simultaneous start. Asserts, every iteration: exactly 1 `nil` result and exactly 15 `ErrBlobAlreadyDeleted` results (never more than one success); the fake backend's `Delete` was invoked exactly once (a new `deleteCalls`/`storeCalls` counter pair was added to `fakeBackend`, `fakes_test.go`, specifically so a double-invocation is provable rather than inferred from final map state, which for an idempotent in-memory fake would stay correct even under a real double-call race a production backend might not tolerate); exactly one `storage.delete_blob` audit event and exactly 15 `storage.delete_blob_failed`/`already_deleted` events; and the final `BlobRecord` is a single consistent physical-delete tombstone.
- `TestMoveBlob_ConcurrentDuplicateRequests_SafelySerialized`: 16 concurrent goroutines all call `MoveBlob` for the same `blob_ref` targeting the same `new_policy_id`. Asserts, every iteration: all 16 calls return `nil` (per the "safely serialized, both/all succeed" behavior above); no dual copy and no lost copy across the two backends; the new backend's `Store` and the old backend's `Delete` were each invoked exactly once (proving only one call took the real-move branch, the rest genuinely took the no-op branch rather than each performing — and each being counted for — its own relocation); content is unchanged and still retrievable; and exactly 1 real-move audit event plus exactly 15 no-op audit events.

Both tests pass 100% across 10 repeated full runs against the real, fixed code (2,000 trials each, `count=10`). Both worker counts (starting from 2, raised through 8, settled on 16) and the run-count-10 sweep were chosen empirically, documented in the tests' own doc comments: at 2 concurrent callers, the unguarded `DeleteBlob` check-then-act window (a few in-memory map operations, no I/O) was found to be narrow enough that a deliberately-broken (lock-removed) variant sometimes did NOT exhibit the race within 200 iterations, which would have made the test an unreliable bug-catcher; at 8 workers the broken variant's catch rate was still only about 9 of 10 full 200-iteration runs; at 16 workers (120 pairwise races per iteration instead of 1) the broken variant failed in 9-10 of 10 full runs for `DeleteBlob` and 10 of 10 for `MoveBlob`, while the fixed code passed all 2,000 trials at the same worker count in every run — this is the evidence basis for keeping 16 workers as the committed value, not an arbitrary round number.

**Mutation-testing procedure (matching Security Steward's own precedent exactly, performed manually, not committed to the repo):** the entire `internal/storage` package (all `.go` files, including the exact final test files above) was copied into an isolated scratchpad directory (`<scratchpad>/storage_mutation/services/api/`, alongside a copy of `go.mod`/`go.sum` so the same cached module dependencies resolve) — never the real repository files. In that isolated copy only, the two `unlock := s.store.lockBlob(req.BlobRef); defer unlock()` lines in `DeleteBlob`/`MoveBlob` were deleted (replaced with a comment noting the deliberate removal), reproducing the exact pre-fix code shape. `go test ./internal/storage/... -run 'Concurrent' -count=10` against that broken copy failed reliably (9-10 of 10 runs per test, as above); the identical command against the real, unmodified repository passed 10 of 10 runs (2,000/2,000 trials) for both tests. The scratchpad copy was never used to run `go build`/`go test` against the real module, and no scratchpad file was ever copied back into the repository except the already-finalized `service_concurrency_test.go`/`fakes_test.go`, which were written directly in the real repo first and only mirrored into the scratchpad copy for the mutation-test comparison.

**Rationale:** This closes the concurrency-hardening item Security Steward flagged as required "before this capability is wired to any real network path" (charter §6) — required for that future wiring step, addressed now per the Chief Architect's dispatch alongside the two gating fixes above, since all three touch the same package. The per-`blob_ref` (rather than whole-service) lock granularity was chosen specifically so this fix does not trade a correctness bug for a scalability regression: a single service-wide mutex would have been simpler to reason about but would serialize `DeleteBlob`/`MoveBlob` calls for entirely unrelated blobs, which the charter's threat model does not require and which would become a real bottleneck as this capability's blob count grows past a first implementation wave. `RetrieveBlob`/`StoreBlob`/`GetStorageLocation` were left unlocked after explicit analysis (not merely because the task didn't name them) — extending the lock to operations with no check-then-act race would be unnecessary serialization with no correctness benefit, which this capability-engineer judged out of scope for a fix whose brief was specifically `DeleteBlob`/`MoveBlob`.

**Article(s) invoked:** Art. 7 (security must never reduce ownership — a concurrency bug that could double-delete, double-audit, or corrupt a blob's deletion state would itself be a real Art. 1/15 hazard, not just a code-quality issue), Art. 1 (deletion must mean exactly what it claims — never fewer, never more, than one real deletion per genuine delete), Art. 5 (the concurrent-duplicate-request behavior for both `DeleteBlob` and `MoveBlob`, including which one reports success versus failure for the losing call, is documented here and in code comments, not left as an accidental emergent property), Art. 15 (the lock's existence, scope, and granularity are documented in `store.go`/`service.go`, not a hidden implementation detail).

**Made by:** Storage capability-engineer.
