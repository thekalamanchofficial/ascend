# Capability Registry

The single source of truth for Ascend's capabilities. A **capability** is a durable, reusable primitive (Identity, File Objects, Permissions, ...). A **feature** is a transient, named composition of one or more capabilities and does not get its own row here — see `docs/DECISION_LOG.md` and individual feature entry points for those.

Never plan work directly against a feature. Decompose first — see `CLAUDE.md` §Workflow.

## Format

Each capability gets one row here and one charter at `docs/capabilities/<capability-name>.charter.md` (copy `_TEMPLATE.charter.md` to start one).

| Capability | Status | Owner (subagent) | Charter | Depends on | Consumed by |
|---|---|---|---|---|---|
| Cryptography & Keys | `stable` | capability-engineer | [charter](capabilities/cryptography-and-keys.charter.md) | Audit / Explainability | Identity, Permissions, Storage, File Objects |
| Identity | `stable` | capability-engineer | [charter](capabilities/identity.charter.md) | Cryptography & Keys, Audit / Explainability | Permissions, File Objects |
| Permissions | `stable` | capability-engineer | [charter](capabilities/permissions.charter.md) | Identity, Audit / Explainability | Storage, File Objects |
| Audit / Explainability | `stable` | capability-engineer | [charter](capabilities/audit-explainability.charter.md) | Identity, Permissions | Identity, Cryptography & Keys, Permissions, Storage, File Objects |
| Storage | `stable` | capability-engineer | [charter](capabilities/storage.charter.md) | Cryptography & Keys, Permissions, Audit / Explainability | File Objects |
| File Objects | `stable` | capability-engineer | [charter](capabilities/file-objects.charter.md) | Storage, Permissions, Identity, Cryptography & Keys, Audit / Explainability | (features, once chartered) |
| Session / Request Authentication | `stable` | capability-engineer | [charter](capabilities/session-authentication.charter.md) | Cryptography & Keys, Identity, Audit / Explainability | Identity, Permissions, Audit / Explainability (as the caller-identity verification layer in front of each) |

**Status values:** `proposed` → `chartering` → `gated` (passed guardian review) → `frozen` (interface contracts locked) → `building` → `stable` → `deprecated`.

## Notes

- A capability moves to `frozen` only after all applicable guardian gates (Constitution Warden always; Experience Guardian and/or Security Steward if their surface is touched) sign off on the charter — see the gate results recorded in each charter file and cross-referenced in `docs/DECISION_LOG.md`.
- "Depends on" must reference only other capabilities' published contracts in `packages/contracts`, never internal implementation details (Article 10).
- When a capability is deprecated, its replacement and migration/export path must be recorded before removal (Article 9).
- **Network exposure status (docs/DECISION_LOG.md, 2026-08-16, "Identity network wiring", "Permissions and Audit network wiring", and "Storage and File Objects network wiring"):** `services/api/main.go` now actually runs an HTTP server. **Every backend capability chartered so far — Identity, Session / Request Authentication, Permissions, Audit / Explainability, Storage, and File Objects — is live and reachable.** `/v1/identity/*` and `/v1/sessionauth/*` were wired first; `/v1/audit/*` (all 4 routes) and `/v1/permissions/*` (5 of 7 routes) followed, resolving the real Audit↔Permissions circular-construction dependency via a late-bound pointer adapter (`services/api/wiring.go`'s `lateBoundPermissionChecker`) — the first live exercise of the charter-time "opaque reference, lazy resolution" design (2026-07-06). `/storage/*` (all 7 routes) and `/file-objects/*` (all 10 routes) were wired last, closing out the registry. `RevokeDevice`/`ListDevices`/`ExportIdentity` are gated by a session-matches-identity middleware; Audit's, Permissions', Storage's, and File Objects' gated routes are gated by a session-verifies-then-overwrites-caller-header middleware (`requireVerifiedCaller`), with each handler additionally requiring the request's own actor/grantor/subject/owner field to match the verified caller. `CreateIdentity`/`BindDevice`/`ResolveIdentity` remain intentionally open. **`DefinePolicy` (`/policies`) and `ListGrantsForResource` (`/grants/resource`) are deliberately excluded from `permissions.Mount` entirely** — `DefinePolicy` stays an in-process-only bootstrapping call, and `ListGrantsForResourceRequest`'s frozen contract has no caller-identity field to check at all (tracked as a future wire-contract amendment). Every wiring pass so far has been verified the same way: real `httptest`-driven integration tests against the real composition root (`services/api/main_test.go`) plus a live manual walkthrough against the actual `go run .` binary — not code review alone. Any future capability wired onto the network follows the same standing rule: a fresh Security Steward gate on that specific act, using this verification standard as the template, not a lighter one.
- **Resolved, 2026-08-16 (was: "Known gap, surfaced 2026-08-16"):** `Permissions.CheckPermission`'s fail-closed-for-unregistered-`resource_type` behavior (charter §6) is now moot for `"blob"` and `"file_object"` — both `storage.NewService` and `fileobjects.NewService` register their own resource type's default policy at construction, and both constructors are now actually reached from the real composition root (`services/api/main.go`'s `newRouter()`), which is what had been missing. Confirmed live: a blob's/file object's true owner can genuinely store then retrieve their own data end to end through the real Permissions instance (`main_test.go`'s `TestStorageRoutes_GatedAndReachable`/`TestFileObjectsRoutes_GatedAndReachable`). The underlying mechanism (fail-closed for any *other*, still-unregistered `resource_type`) remains exactly as designed — this was never a bug in `CheckPermission` itself, only a reachability gap in who called `DefinePolicy`, now closed for the two resource types any wired capability actually uses.
- **Gap found and closed during this pass, 2026-08-16 ("Storage: StoreBlob establishes Permissions ownership via GrantPermission"):** a second, separate, more severe gap was found while writing the live wiring tests above — `Storage.StoreBlob` never called `Permissions.GrantPermission` for a newly-stored blob, so even with `"blob"`'s policy registered, a blob's own creator could never retrieve/move/delete it afterward (Permissions' `ownerOf` requires an actual prior grant, not just a registered policy). Fixed by having `StoreBlob` bootstrap the owner's grant itself, mirroring File Objects' own pre-existing pattern exactly, with rollback on failure. Independently verified by both guardians at this pass's merge gate, including live adversarial probing, not just the automated test suite.
- **Merge gates:** "Permissions and Audit network wiring" (docs/DECISION_LOG.md, 2026-08-16) — both Constitution Warden and Security Steward independently PASSed via real rebuild/test/live-probing. Two non-blocking follow-ups tracked from that gate: Audit's export defaults to self when `identity_ref` is omitted, Permissions' export doesn't (Art. 16 inconsistency); Audit's actor-mismatch error message is worded for cross-subject `Query` denial, not `Emit` forgery (cosmetic). "Storage and File Objects network wiring" (docs/DECISION_LOG.md, 2026-08-16) — both guardians independently PASSed this pass too, via the same standard (own throwaway adversarial clients against the live binary, not reused test code). One non-blocking follow-up from that gate: File Objects' `Mount` doc comment claiming it was still unwired has been corrected (`internal/fileobjects/http.go`).
- **Tracked, not yet done, before broader network exposure:** rate limiting on `CreateIdentity`/`GetSessionChallenge`, and a documented TLS-termination/CORS stance (currently plaintext `ListenAndServe`, safe only under an assumed reverse proxy that isn't written down anywhere yet).
