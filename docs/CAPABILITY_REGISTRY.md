# Capability Registry

The single source of truth for Ascend's capabilities. A **capability** is a durable, reusable primitive (Identity, File Objects, Permissions, ...). A **feature** is a transient, named composition of one or more capabilities and does not get its own row here — see `docs/DECISION_LOG.md` and individual feature entry points for those.

Never plan work directly against a feature. Decompose first — see `CLAUDE.md` §Workflow.

## Format

Each capability gets one row here and one charter at `docs/capabilities/<capability-name>.charter.md` (copy `_TEMPLATE.charter.md` to start one).

| Capability | Status | Owner (subagent) | Charter | Depends on | Consumed by |
|---|---|---|---|---|---|
| Cryptography & Keys | `stable` | capability-engineer | [charter](capabilities/cryptography-and-keys.charter.md) | Audit / Explainability | Identity, Permissions, Storage, File Objects |
| Identity | `stable` | capability-engineer | [charter](capabilities/identity.charter.md) | Cryptography & Keys, Audit / Explainability | Permissions, File Objects |
| Permissions | `stable` | capability-engineer | [charter](capabilities/permissions.charter.md) | Identity, Audit / Explainability | Storage, File Objects |
| Audit / Explainability | `stable` | capability-engineer | [charter](capabilities/audit-explainability.charter.md) | Identity, Permissions | Identity, Cryptography & Keys, Permissions, Storage, File Objects |
| Storage | `stable` | capability-engineer | [charter](capabilities/storage.charter.md) | Cryptography & Keys, Permissions, Audit / Explainability | File Objects |
| File Objects | `stable` | capability-engineer | [charter](capabilities/file-objects.charter.md) | Storage, Permissions, Identity, Cryptography & Keys, Audit / Explainability | (features, once chartered) |
| Session / Request Authentication | `stable` | capability-engineer | [charter](capabilities/session-authentication.charter.md) | Cryptography & Keys, Identity, Audit / Explainability | Identity, Permissions, Audit / Explainability (as the caller-identity verification layer in front of each) |

**Status values:** `proposed` → `chartering` → `gated` (passed guardian review) → `frozen` (interface contracts locked) → `building` → `stable` → `deprecated`.

## Notes

- A capability moves to `frozen` only after all applicable guardian gates (Constitution Warden always; Experience Guardian and/or Security Steward if their surface is touched) sign off on the charter — see the gate results recorded in each charter file and cross-referenced in `docs/DECISION_LOG.md`.
- "Depends on" must reference only other capabilities' published contracts in `packages/contracts`, never internal implementation details (Article 10).
- When a capability is deprecated, its replacement and migration/export path must be recorded before removal (Article 9).
- **Network exposure status (docs/DECISION_LOG.md, 2026-08-16, "Identity network wiring", "Permissions and Audit network wiring", and "Storage and File Objects network wiring"):** `services/api/main.go` now actually runs an HTTP server. **Every backend capability chartered so far — Identity, Session / Request Authentication, Permissions, Audit / Explainability, Storage, and File Objects — is live and reachable.** `/v1/identity/*` and `/v1/sessionauth/*` were wired first; `/v1/audit/*` (all 4 routes) and `/v1/permissions/*` (5 of 7 routes) followed, resolving the real Audit↔Permissions circular-construction dependency via a late-bound pointer adapter (`services/api/wiring.go`'s `lateBoundPermissionChecker`) — the first live exercise of the charter-time "opaque reference, lazy resolution" design (2026-07-06). `/storage/*` (all 7 routes) and `/file-objects/*` (all 10 routes) were wired last, closing out the registry. `RevokeDevice`/`ListDevices`/`ExportIdentity` are gated by a session-matches-identity middleware; Audit's, Permissions', Storage's, and File Objects' gated routes are gated by a session-verifies-then-overwrites-caller-header middleware (`requireVerifiedCaller`), with each handler additionally requiring the request's own actor/grantor/subject/owner field to match the verified caller. `CreateIdentity`/`BindDevice`/`ResolveIdentity` remain intentionally open. **`DefinePolicy` (`/policies`) and `ListGrantsForResource` (`/grants/resource`) are deliberately excluded from `permissions.Mount` entirely** — `DefinePolicy` stays an in-process-only bootstrapping call, and `ListGrantsForResourceRequest`'s frozen contract has no caller-identity field to check at all (tracked as a future wire-contract amendment). Every wiring pass so far has been verified the same way: real `httptest`-driven integration tests against the real composition root (`services/api/main_test.go`) plus a live manual walkthrough against the actual `go run .` binary — not code review alone. Any future capability wired onto the network follows the same standing rule: a fresh Security Steward gate on that specific act, using this verification standard as the template, not a lighter one.
- **Resolved, 2026-08-16 (was: "Known gap, surfaced 2026-08-16"):** `Permissions.CheckPermission`'s fail-closed-for-unregistered-`resource_type` behavior (charter §6) is now moot for `"blob"` and `"file_object"` — both `storage.NewService` and `fileobjects.NewService` register their own resource type's default policy at construction, and both constructors are now actually reached from the real composition root (`services/api/main.go`'s `newRouter()`), which is what had been missing. Confirmed live: a blob's/file object's true owner can genuinely store then retrieve their own data end to end through the real Permissions instance (`main_test.go`'s `TestStorageRoutes_GatedAndReachable`/`TestFileObjectsRoutes_GatedAndReachable`). The underlying mechanism (fail-closed for any *other*, still-unregistered `resource_type`) remains exactly as designed — this was never a bug in `CheckPermission` itself, only a reachability gap in who called `DefinePolicy`, now closed for the two resource types any wired capability actually uses.
- **Gap found and closed during this pass, 2026-08-16 ("Storage: StoreBlob establishes Permissions ownership via GrantPermission"):** a second, separate, more severe gap was found while writing the live wiring tests above — `Storage.StoreBlob` never called `Permissions.GrantPermission` for a newly-stored blob, so even with `"blob"`'s policy registered, a blob's own creator could never retrieve/move/delete it afterward (Permissions' `ownerOf` requires an actual prior grant, not just a registered policy). Fixed by having `StoreBlob` bootstrap the owner's grant itself, mirroring File Objects' own pre-existing pattern exactly, with rollback on failure. Independently verified by both guardians at this pass's merge gate, including live adversarial probing, not just the automated test suite.
- **Merge gates:** "Permissions and Audit network wiring" (docs/DECISION_LOG.md, 2026-08-16) — both Constitution Warden and Security Steward independently PASSed via real rebuild/test/live-probing. Two non-blocking follow-ups tracked from that gate: Audit's export defaults to self when `identity_ref` is omitted, Permissions' export doesn't (Art. 16 inconsistency); Audit's actor-mismatch error message is worded for cross-subject `Query` denial, not `Emit` forgery (cosmetic). "Storage and File Objects network wiring" (docs/DECISION_LOG.md, 2026-08-16) — both guardians independently PASSed this pass too, via the same standard (own throwaway adversarial clients against the live binary, not reused test code). One non-blocking follow-up from that gate: File Objects' `Mount` doc comment claiming it was still unwired has been corrected (`internal/fileobjects/http.go`).
- **Tracked, not yet done, before broader network exposure:** rate limiting on `CreateIdentity`/`GetSessionChallenge`, and a documented TLS-termination/CORS stance (currently plaintext `ListenAndServe`, safe only under an assumed reverse proxy that isn't written down anywhere yet).
- **Database infrastructure (docs/DECISION_LOG.md, 2026-08-17, "Database setup: shared platform foundation + Audit on real Postgres"; extended same date across three batches, "Migrating remaining capabilities onto Postgres: batch plan"):** `services/api/internal/platform` (Postgres pool, Redis client, S3-compatible client, migration runner) plus a local Docker Compose stack (Postgres, Redis, MinIO) now exist. **Every backend capability — Audit, Identity, Permissions, Storage (metadata), File Objects, and Session/Request Authentication — is now backed by real, durable storage**, the composition root requiring each with no in-memory fallback. Session/Request Authentication (Batch C) is the only capability split across two backends: challenge nonces on Redis (leaning on Redis's own native per-key TTL, no expiry logic reimplemented in Go — `internal/sessionauth/redis_nonce_store.go`), sessions on Postgres (`internal/sessionauth/postgres_session_store.go` — `ExportSessions` must show expired-but-not-yet-revoked sessions, which a Redis TTL would evict and lose). Storage's blob *bytes* still live on the local filesystem (unchanged `Backend`/`FilesystemBackend`) — only metadata (owner, policy_id, location, tombstone fields) and outer wrapping keys moved to Postgres. Permissions', Storage's, File Objects', and Session/Request Authentication's `Store`(s) all became real interfaces in this series (previously concrete structs built internally, no DI seam). The S3-compatible client is still constructed and health-checked at startup but consumed by nothing yet, reserved for a future pass wiring Storage's blob bytes onto it. **The database-migration series is complete** — every backend capability's durable data now survives a restart.
- **Resolved, 2026-08-17 (Security Steward Batch B merge-gate finding, fixed and independently re-verified same day — was: "Known gap... fix in progress"):** `Storage.Service`'s `lockBlob` (serializing `MoveBlob`/`DeleteBlob`'s check-then-act sequence per `blob_ref` via a Postgres session-level advisory lock held on a dedicated checked-out pool connection) originally had no timeout anywhere (`context.Background()` throughout), and Security Steward live-proved this was a **total, indefinite, whole-server denial of service**, not a mere "stall": ~10-20 concurrent duplicate requests against ONE blob a single ordinary authenticated user already owns could exhaust `internal/platform`'s entire shared connection pool (`maxPoolConns = 10`) in a genuine circular deadlock, taking down every Postgres-backed capability (not just Storage) with no self-recovery. **Fixed:** both the connection-acquire and advisory-lock steps now run under a 5-second bounded timeout (`context.WithTimeout`), converting the deadlock into a bounded, self-recovering failure (a clean `500`, not a hang). **Independently re-verified live by Security Steward** (not just the fixing engineer's own report): 3×20-request floods plus a 4-round sustained-attack test, 0 hangs across 60+ flood requests and 987+ concurrent unrelated-capability (`Identity`) probes fired *during* the contention windows — 100% success throughout, not merely recovery afterward; post-flood recovery confirmed in 12-25ms every time, connection pool returning to a clean idle baseline with no manual intervention. The 5s bound itself was independently judged reasonable (~50-400x normal-case critical-section latency, zero false-positive timeouts observed under legitimate contention in either engineer's or guardian's testing). **What remains honestly disclosed, not closed:** the fix bounds and self-resolves contention, it does not eliminate shared-pool contention itself — a hot-`blob_ref` burst can still transiently elevate (never hang) latency for other capabilities during the contention window, since every other capability's own `PostgresStore` still calls `pool.Acquire` under unbounded `context.Background()`. A fully separate connection pool for lock-holders (closing this residual cross-capability latency coupling entirely) remains a scoped, not-yet-built follow-up. See `docs/DECISION_LOG.md`, "Batch B merge gate: Constitution Warden PASS, Security Steward BLOCKED (lockBlob deadlock)" and "Storage: lockBlob bounded-timeout fix (Security Steward block)".
- **Known gap, surfaced 2026-08-17 (Security Steward merge-gate finding, "Database setup" pass), not yet resolved:** Audit's charter §6 promises tamper-evidence "including by platform operators." The real implementation enforces this against the running application's own runtime credential (`ascend_app`, `REVOKE UPDATE, DELETE`, live-verified) and against every network caller (no `Update`/`Delete` RPC exists on this capability's contract at all) — but **not** against `ascend_admin`, the migration-time role that owns the `audit_events` table. Postgres table ownership cannot be restricted via `GRANT`/`REVOKE` — an owning role always retains the implicit right to `DELETE`/`ALTER`/`DROP`/re-grant itself any privilege. A credential with that specific role can silently delete or alter rows today, with no error and no chain-repair — live-demonstrated during the merge gate (a genuine, non-adversarial test-cleanup `DELETE`, not a contrived attack). The charter (§6) has been amended to disclose this precisely rather than overclaim; this bullet is the tracking record. **Real fix, scoped but not built:** decouple the schema-owning role from the migration-runner role (so no login-capable credential owns the table), and/or periodically anchor the hash-chain tip to storage the DB admin doesn't control, so tampering by any DB-level actor becomes detectable even where it can't be prevented.
- **Merge gate (docs/DECISION_LOG.md, 2026-08-17, "Database setup: composition, live verification" and "Database setup: Security Steward block and fix"):** Constitution Warden independently PASSed (own throwaway adversarial client, live restart-survival and `REVOKE`-enforcement proof). Security Steward initially **blocked** — not on the Postgres/platform implementation itself (every `ascend_app`-level control, parameterization, secret handling, and transient-admin-connection discipline verified sound via direct live attack, including a real adversarial-payload test of `ProvisionAppRolePassword`'s literal-escaping) but specifically on the charter overclaiming the "platform operators" guarantee documented above — unblocked after the charter amendment and this tracking entry landed. Two non-blocking follow-ups: Constitution Warden's own review of registry staleness (this entry) and a recommended convention for serializing concurrent local verification runs against the one shared `docker compose` stack (multiple guardians'/engineers' `go run .`/test runs interleaving on `:8080` or the audit table bit this pass at least three times, documented in the decision log as a testing-environment caveat, not a product defect).
- **Mobile client integration, Identity + Session/Request Authentication (docs/DECISION_LOG.md, 2026-08-17, "Identity + Session/Request Authentication mobile client integration"):** `apps/mobile/src/capabilities/identity/` and `apps/mobile/src/capabilities/sessionauth/` are the first mobile client wrappers built against a network-wired backend capability (previously only Cryptography & Keys had client code, and it has no network component at all). Both capabilities' status stays `stable` — this added a consumer, it did not change either capability. An onboarding composition layer (`apps/mobile/src/features/onboarding/`) ties them together with Cryptography & Keys for the two real identity-lifecycle journeys. **Unresolved, routed to Chief Architect:** the device-removal session-cascade gap — the current RPC surface cannot support "removing a device also revokes that device's active sessions" (no `session_token` in `ListActiveSessions`, `RevokeAllSessions` is identity-scoped not device-scoped); implemented this pass as device-binding-revocation only, with the gap documented at the call site and in the decision log rather than papered over. Also surfaced: Cryptography & Keys' frozen contract has no seam to reload a device's raw private key bytes into a signable handle after a process restart, bounding automatic session renewal to the lifetime of one app process.
