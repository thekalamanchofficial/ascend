# Capability Charter: Session / Request Authentication

## 1. Name and one-line purpose

**Session / Request Authentication** — proves which bound device of which identity is making a given request, so every other capability can trust the `actor`/`subject`/`grantor`/`identity_ref` fields it's handed instead of accepting them at face value.

## 2. Article 17 answer (asked first)

Yes, and it is a precondition for several already-shipped capabilities' guarantees to mean anything outside a developer's own machine. Identity's `RevokeDevice`, Permissions' `GrantPermission`/`CheckPermission`, and Audit's `Emit`/`Query` all take the acting identity as a request field today, verified by nothing — any ownership or access-control claim those capabilities make is unenforceable the moment they're reachable over a real network, because "the user" in every one of those calls is currently just whatever string the caller decided to send. This capability is what makes "the user owns this action" a checked fact rather than an assertion.

## 3. Interface

**Exposes:**
- `GetSessionChallenge(identity_ref, device_id) -> challenge_nonce, challenge_expires_at` — issues a random, single-use, short-lived nonce. Exists specifically so `IssueSession`'s signature has a freshness input to sign over — see §6; a capability-engineer-invented freshness scheme is exactly the gap that produced the Identity `BindDevice` replay veto, so this RPC is specified here, not left implicit.
- `IssueSession(identity_ref, device_id, challenge_nonce, proof) -> session_token, expires_at` — a bound device proves possession of its own device private key by signing over a **canonical, domain-separated message**: `"ascend.session.v1.IssueSession" || 0x00 || identity_ref || 0x00 || device_id || 0x00 || challenge_nonce` (via Cryptography & Keys' `Sign`, the same primitive Identity's `BindDevice` already uses — no new crypto invented here; the distinct domain-separation string, distinct from `BindDevice`'s, is what guarantees a proof for one operation can never be replayed as the other, mirroring `sign.go`'s existing pattern in Identity). The server verifies `challenge_nonce` was genuinely issued by `GetSessionChallenge`, is unexpired, and has not already been consumed — then consumes it, one-time-use, same discipline as Identity's epoch counter but shaped as a nonce because sessions are issued repeatedly rather than representing a topology change. On success, a new session record is created server-side and an opaque, random `session_token` is returned. There is no username/password path and no server-side ability to mint a session without a fresh device signature.
- `ValidateSession(session_token) -> identity_ref, device_id, valid` — the call every other capability's request-handling middleware uses to resolve who is actually making a request. Looks up the session **server-side** (not a self-contained/stateless token whose validity can't be revoked) — see §6 for why this is a deliberate, not incidental, design choice.
- `RevokeSession(session_token)` — sign out one session (e.g. "log out this device"). The token itself is the bearer credential authorizing this call — presenting it to end it is a reasonable, sufficient authorization on its own.
- `RevokeAllSessions(caller_session_token) -> sessions_revoked` — sign out everywhere, a first-class user action, not a support request (Art. 9's "no lock-in" cousin: the user can always cut off access, not just always leave). **Takes the caller's own currently-valid session token, resolved via `ValidateSession`, never a bare `identity_ref`** — `identity_ref` is a public, discoverable value (Identity's own `ResolveIdentity` is an unauthenticated public lookup), so accepting it directly here would let any caller sign an arbitrary user out of every device — an anonymous account-lockout primitive, not a user-owned action. A caller can only ever revoke-all for the identity their own presented token already resolves to.
- `RevokeSessionsForDevice(caller_session_token, device_id) -> sessions_revoked` — **added 2026-08-17**, closing a real gap found integrating the mobile client: §5's "remove this device" commitment (revoke the Identity binding *and* every active session for that device, as one action) was not achievable with the RPCs above — `ListActiveSessions`' `session_summary` deliberately carries no `session_token` (same rationale as `ExportSessions` excluding it — a live transparency view must not itself become a way to harvest usable bearer credentials for other devices, including your own), so a caller can never learn the token needed to drive per-session `RevokeSession` calls for a device it isn't currently using, and `RevokeAllSessions` is scoped to every device at once, not one. Same authorization shape as `RevokeAllSessions`/`ListActiveSessions` and for the identical reason: takes `caller_session_token`, resolves the acting identity from it, and revokes only sessions matching both that identity and the given `device_id` — never a bare `identity_ref`. Returns the count revoked (mirroring `RevokeAllSessions`' `sessions_revoked` shape) so the caller can confirm zero vs. several were live, without ever seeing the tokens themselves. **Atomicity requirement (Security Steward gate, 2026-08-17):** `RevokeSessionsForDevice` must guarantee no session for `device_id` can remain live after the call returns success — including one from a concurrently in-flight `IssueSession` for that same device. `sessions_revoked` is a completion guarantee, not a point-in-time snapshot count: the implementer must close the race via a per-`device_id` serialization point (e.g. a transactional lock held across both the revoke query and any concurrent `IssueSession`'s session-insert for that device, or a revoked-at watermark for the device that `IssueSession` checks as part of its own commit) — mirroring the same rigor already required of `IssueSession`'s nonce-consumption atomicity (§6), and verified the same way at the implementation merge gate (mutation-testing the serialization logic, not just a happy-path regression test).
- `ListActiveSessions(caller_session_token) -> [session_summary]` — device_id, issued_at, expires_at, last_used_at, for the same "Devices screen"-style transparency Identity already provides for bindings (Art. 5, Art. 12). Same authorization shape as `RevokeAllSessions` and for the same reason: a bare `identity_ref` parameter would let any caller read another user's device count and activity timestamps, a real fingerprinting/targeting signal, not just a theoretical one.
- `ExportSessions(caller_session_token) -> export_blob, format_version` — Art. 9's export half, named explicitly (not left implicit in `ListActiveSessions`, which is a live transparency view, not a durable export artifact). Exports every persisted session-record field for the caller's own identity — `identity_ref`, `device_id`, `issued_at`, `expires_at`, `last_used_at` per §4's data manifest — in the same versioned, self-describing, independently-usable format every other capability's export has met (the Cryptography & Keys bar). **`session_token` itself is deliberately excluded** from the export, the same way Cryptography & Keys' `ExportKeyMaterial` deliberately excludes the recovery phrase: a live bearer credential is not archival user data, and including active tokens in an export would hand out valid, unrevoked sessions to whoever holds the export file — a live authentication capability re-exposing active credentials to a file a user might store less carefully than the platform does would itself violate Art. 7, not fulfill Art. 9. The `func Export<TypeName>`/`*_export_test.go` mechanical check convention (`scripts/constitution/check-export-paths.sh`) applies to whatever struct backs the persisted session record, marked `// ascend:persisted`, at implementation time.

**Consumes:**
- **Cryptography & Keys** — `Sign`/device key material stays entirely client-side; this capability never sees a private key, only a signature and the already-public device key it verifies against (verification is server-side, direct `crypto/ed25519.Verify`, same already-decided pattern as Identity's `BindDevice` — see `docs/DECISION_LOG.md`, 2026-07-16, "signature verification is not 'own crypto'").
- **Identity** — to resolve which device keys are currently valid for a given `identity_ref` (a revoked device's key must not be able to issue a new session, even with a perfectly valid signature over fresh data).
- **Audit / Explainability** — every issuance, validation failure (not routine success — see §4), and revocation is audited.

## 4. Constitutional obligations

- **Art. 1 (ownership):** the only way to obtain a session is proving possession of a private key the user's own device generated and holds — there is no password, no email-reset link, no support-mediated override, mirroring Identity's own recovery-path commitment (no disguised server authority).
- **Art. 5 (explainability):** `IssueSession`, `RevokeSession`, `RevokeAllSessions`, and `RevokeSessionsForDevice` all emit audit events. Repeated `ValidateSession` failures for the same `session_token` or `identity_ref` within a short window also emit an event (distinct from normal traffic) — a user should be able to answer "has someone been trying to use a stolen/expired session as me?" Routine successful validations are **not** individually audited (charter judgment, not an oversight): every other capability already validates a session on effectively every request, and logging each one would flood the audit trail with noise that drowns out the events a user actually cares about, violating Art. 8's "minimum data necessary" in spirit even though technically about actions not data fields.
- **Art. 7 (security never reduces ownership):** sessions are server-side records, not self-contained tokens — this is a direct, deliberate response to the Identity `BindDevice` replay finding (see §6). A revoked session must be **actually** unusable the instant it's revoked, not merely inconvenient to use, and not valid-until-natural-expiry.
- **Art. 8 (privacy) — data manifest:**
  - `session_token` — purpose: the opaque bearer credential itself; random, unguessable, carries no embedded identity data (unlike a JWT, deliberately — see §6).
  - `identity_ref`/`device_id` — purpose: the minimum needed to answer "who and which device is this."
  - `issued_at`/`expires_at`/`last_used_at` — purpose: powers expiry enforcement and the Art. 5 "has this been misused" answer; `last_used_at` lets a user spot a session they don't recognize being actively used, the session-level analog of Identity's `device.last_seen`.
  - `challenge_nonce`/`challenge_expires_at` — purpose: the freshness input `IssueSession` signs over (§3, §6), closing the replay class of bug found in Identity's `BindDevice`. Short-lived (expires in seconds/low minutes, exact value an implementation decision) and consumed on first successful use; not retained once consumed or expired.
  No other fields. No IP address, user agent, or device fingerprinting beyond what Identity's `Device` record already captures — that would be new, undocumented collection this capability has no charter basis to introduce.
- **Art. 9 (export, and no lock-in — both halves):** `ExportSessions` is the export mechanism — every persisted session-record field the user's own identity owns is retrievable in a durable, self-describing format, with `session_token` deliberately excluded as a live credential rather than archival data (see §3). `RevokeAllSessions` is the no-lock-in mechanism — a user is never dependent on this platform's goodwill to cut off access to their own identity. The two are complementary, not substitutes for each other.
- **Art. 10 (modularity):** depends only on Cryptography & Keys' and Identity's published contracts for the signature/device-validity half, and Audit's for the explainability half — never their internals.

## 5. Experience budget

Invisible by default, concretely: session issuance is triggered automatically by the client immediately following a successful `BindDevice`, and again automatically in the background well before `expires_at` (via fresh re-issuance — see §6), with no user-visible step distinguishable from binding and no login form or password anywhere in this capability. A device that's already bound simply works, continuously, with no session-expiry interruption a user ever has to react to in normal use.

**Devices/Sessions composition — committed here, not deferred:** there is no separate top-level "Sessions" screen. The existing Identity Devices screen stays the one place a user looks, and its rows stay device-level, using Identity's own terminology — "session" is not a concept a user needs to learn to operate it. A device's row shows freshness via the existing `device.last_seen` (or its data superseded by the more precise `last_used_at` this capability tracks, an implementation choice, not a second competing timestamp shown to the user). The default action from that screen — "remove this device" — is a single action that, under the hood, both revokes the device's Identity binding and calls `RevokeSessionsForDevice` for that `device_id` (added 2026-08-17 — see §3; before that, this composition was a stated commitment the RPC surface could not yet fulfill); a user is never shown a device removal and a session sign-out as two separate steps or two separate lists. **Composition ordering requirement (Security Steward gate, 2026-08-17):** Identity's `RevokeDevice` is called first, so any new `IssueSession` attempt for that device is blocked (via Identity's `DeviceResolver` check, §3) before `RevokeSessionsForDevice`'s revoke query runs; the composed "remove this device" action is not considered complete until *both* calls succeed. A session that was issued in the network round-trip between the two calls must still be caught — this is exactly what `RevokeSessionsForDevice`'s own atomicity requirement (§3) exists to guarantee, not a second, separate gap to close; the two requirements together mean no session for a removed device can survive the composed action, regardless of which of the two narrow windows (mid-`RevokeDevice`, or the gap between the two calls) it was issued in. If a device can in practice hold more than one concurrent session (e.g. renewal overlap during a token refresh, or multiple app instances under one `device_id`), that per-session detail lives behind an optional expand on that device's row, never as a parallel top-level list — "sign out everywhere" (`RevokeAllSessions`) is the one exception: a single, clearly-labeled, identity-level action, not a per-device one, and stays on the same screen.

## 6. Threat model

In scope — this capability exists specifically to close a security gap, so it gets full rigor, same standing as Cryptography & Keys.

- **The exact lesson from Identity's `BindDevice` replay finding (docs/DECISION_LOG.md, 2026-07-16) applies here by construction, not by reminder:** a signed proof with no freshness check is a standing resurrection risk. `IssueSession` now requires a `challenge_nonce` obtained from `GetSessionChallenge` — genuinely random, single-use (consumed on successful verification, rejected if reused), short-lived — signed as part of a canonical, domain-separated message distinct from `BindDevice`'s own domain string (see §3). A captured `IssueSession` request cannot be replayed: the nonce it embeds is already consumed, so re-submitting the identical request fails.
- **Self-contained tokens (e.g. JWT) were considered and rejected for the primary design**, specifically because a self-contained token's validity can't be revoked without either a blocklist (which is just a server-side session store by another name, so there's no complexity saved) or accepting that revocation only takes effect at natural expiry (unacceptable — "sign out this device" must be immediate and real, mirroring the Art. 7 obligation above). `ValidateSession` is therefore a real lookup against server state, every time.
- **Session token theft, and the renewal mechanism resolved:** the token is a high-value bearer credential once issued. This charter commits to **fresh-signature re-issuance, not bearer-token-only renewal**: extending a session past `expires_at` always means calling `GetSessionChallenge` + `IssueSession` again, with a new device signature — the client does this automatically, in the background, before expiry, so the user never sees an interruption (§5), but a stolen `session_token` alone, without the device's private key, cannot extend its own life past the original `expires_at`. This is what makes "short default lifetime bounds the blast radius of a leaked token" an actual guarantee rather than an aspiration: the worst case for a leaked token is bounded by `expires_at` at the moment of leak, full stop, not by however long an attacker keeps re-presenting it.
- **Server compromise scenario:** a compromised server can see active session records (identity_ref/device_id/timestamps) but — because sessions are only ever issued in response to a real, fresh device signature it cannot forge and cannot replay (challenge nonces are single-use) — it cannot mint a valid new session for a user, nor extend an existing one, without that user's device signing again. It can revoke or read metadata about existing sessions, not fabricate or prolong trust.

## 7. Open questions / risks

- Exact session-token and challenge-nonce generation (CSPRNG-sourced opaque random strings, length/encoding) and storage backend (mirrors Audit's own "in-memory first pass, interface-isolated for a durable backend later" precedent, or may share infrastructure with Audit's eventual real datastore) are implementation decisions for the capability engineer once frozen.
- **This capability is the prerequisite for lifting the standing gate recorded in `docs/CAPABILITY_REGISTRY.md`** ("Identity, Permissions, and Audit / Explainability... not wired into `services/api/main.go`... until a chartered, gated Session/Request Authentication capability exists"). Wiring any of those three (or this one) into `main.go` remains a separate, later act requiring its own fresh Security Steward gate per that entry — chartering and even implementing this capability does not, by itself, lift that gate.
- Exact numeric value of `expires_at`'s lifetime (charter states "short," an implementation decision within that constraint) and of `challenge_nonce`'s own, necessarily much shorter, expiry are left to the capability engineer.
