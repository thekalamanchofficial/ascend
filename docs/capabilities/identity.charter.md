# Capability Charter: Identity

## 1. Name and one-line purpose

**Identity** — user-owned identity and device/key binding, with no silent server-side identity authority.

## 2. Article 17 answer (asked first)

Yes. Identity is the root of ownership: if the platform (not the user) is the ultimate authority over "who a user is," every other ownership claim in the Constitution is hollow. This capability exists specifically to make identity something the user creates and controls, not something the server assigns and can unilaterally reissue.

## 3. Interface

**Exposes:**
- `CreateIdentity()` — generates a new user identity locally, backed by a key pair from **Cryptography & Keys**. The server never generates a user's root identity key.
- `BindDevice(identity, device_public_key)` — links a new device to an existing identity, requiring proof of possession from an already-bound device, **or**, in the all-devices-lost path, a binding assertion self-signed by key material derived from the recovery phrase (see Cryptography & Keys' `RestoreFromRecoveryPhrase`). The server only relays and audit-logs this assertion — it never authenticates, approves, or overrides a binding itself, and has no discretionary or support-mediated path to bind a device.
- `RevokeDevice(identity, device_id)` — removes a device's binding.
- `ResolveIdentity(identity_ref) -> public_identity` — read-only lookup of the public-facing identity record (display name, public key, device count) for use by other capabilities (e.g. Permissions' subject resolution).
- `ListDevices(identity)` — enumerates bound devices with metadata (added date, last-seen, name). **Amended 2026-08-19:** each device also carries `unconsumed_one_time_prekey_count` — see §6's "Prekey exhaustion as an abuse vector" bullet for why (a minimal, self-only passive detectability signal, added at this amendment's own gate finding, not part of the original freeze).
- `ExportIdentity(identity)` — produces a complete, user-readable export of the identity record and device list (Art. 9).
- `PublishPrekeyBundle(identity, device_id, identity_dh_public_key, identity_dh_public_key_signature, signed_prekey, one_time_prekeys[]) -> {published_count}` — **added 2026-08-19, the Cryptography & Keys amendment's own named follow-up (`cryptography-and-keys.charter.md` §3/§7 item 1) — closing the "who stores/serves prekey bundles" gap that amendment deliberately left to Identity.** `identity`/`device_id` must equal the verified caller's own identity/device (HTTP-level binding, mirroring the caller-identity-binding discipline now established codebase-wide — see §6). Replaces the device's current signed prekey (rotation) and **additively** appends `one_time_prekeys` to that device's available pool — never removes or replaces an existing unconsumed one-time prekey. Every value here is already-public, already-signed bytes Cryptography & Keys' `GeneratePrekeyBundle` produced; this capability never generates, signs, or touches private key material — pure storage/relay for public prekey material, the same role it already plays for `device_public_key`. **`identity_dh_public_key` — added 2026-08-21 (Cryptography & Keys' companion key-separation fix, `cryptography-and-keys.charter.md` §3, Security Steward implementation-merge-gate finding):** the identity's X25519 DH-capable public key, deterministically derived from the same recovery-phrase seed as the Ed25519 signing key but via a domain-separated KDF — **a genuinely different value from `identity`'s own Ed25519 `public_key`** (`ResolveIdentity`/`CreateIdentity`), never interchangeable with it at the wire level. Identity has no way to independently derive this value (it requires the private seed), so it must be republished here, alongside the signed prekey, rather than sourced from the identity record Identity already holds. **`identity_dh_public_key_signature` — added 2026-08-21, round 2 (Security Steward finding: an unsigned `identity_dh_public_key` is a substitution surface a compromised publish/fetch path could exploit — see `cryptography-and-keys.charter.md` §6's bounded-impact analysis):** signed with the identity's Ed25519 key at `GeneratePrekeyBundle` time, republished here verbatim — Identity stores and relays it, never generates or verifies it itself.
- `FetchPrekeyBundle(identity_ref, device_id?) -> {identity_dh_public_key, identity_dh_public_key_signature, identity_signing_public_key, device_id, signed_prekey: {prekey_id, public_key, signature, created_at}, one_time_prekey: {prekey_id, public_key}?}` — **added 2026-08-19, same amendment. Response field renamed `identity_public_key` → `identity_dh_public_key` and its semantics corrected 2026-08-21 (same key-separation fix): this field returns the target device's most-recently-published `identity_dh_public_key` (above) — the X25519 DH-capable key, not the Ed25519 signing key `ResolveIdentity` returns.** The rename is deliberate, not cosmetic — an ambiguously-named `identity_public_key` field is exactly what let the original key-reuse design go unnoticed at the design gate; naming it explicitly forecloses that confusion for any future reader of this contract. A device that has published a `signed_prekey` but (from a pre-fix client) never an `identity_dh_public_key` must be treated identically to "no bundle published" (`PrekeyBundleStatus.NOT_PUBLISHED`, §3's existing indistinguishability requirement) — fail closed on missing DH key material, never silently fall back to returning the wrong (Ed25519 signing) key in its place. **`identity_signing_public_key` — added 2026-08-21, round 2:** the identity's Ed25519 signing key, sourced from the identity record already established at `CreateIdentity` (the same value `ResolveIdentity` returns, unchanged by this fix) — included here so a caller can verify `signed_prekey.signature`/`identity_dh_public_key_signature` without a second round trip through `ResolveIdentity`. **The one deliberately open, non-self-scoped read this capability exposes** (mirroring `ResolveIdentity`'s existing openness, not a new pattern — see §6 for why this doesn't reopen any enumeration concern): any authenticated caller may fetch any identity's bundle, because that's the entire point — an initiator who has never talked to someone before must be able to reach their public key material to start a session at all. `device_id` optional; if omitted, resolves to the identity's most-recently-active bound device (by `last_seen`, per `ListDevices`) — a reasonable default for this freeze, not a solved multi-device answer (§7). **Atomically claims and permanently removes one available one-time prekey from the pool on every successful fetch (§6)** — required, not optional: this is what durably guarantees the single-issuance property Cryptography & Keys' own charter depends on. If none remain, `one_time_prekey` is simply absent from the response (the caller's `CompleteSharedSecret`/`DeriveSharedSecret` then correctly falls into that charter's already-specified, already-disclosed exhaustion-fallback path). **If the target device has never published a signed prekey at all** (§7's inherited brand-new-identity edge case, resolved here as this amendment's own responsibility) — distinct from "signed prekey present but one-time prekeys exhausted" — this RPC returns a distinguishable "no bundle published" result, never silently reusing the exhaustion-fallback shape for a genuinely different state. **A caller-supplied `device_id` that is not actually bound to `identity_ref` at all must return this identical "no bundle published" result — required, not left unspecified (Security Steward gate finding, round 1: a real, new enumeration oracle, not covered by §6's existing openness argument).** `ResolveIdentity` never exposes individual `device_id` values, only a device count — a `FetchPrekeyBundle` response that distinguished "real device, no bundle yet" from "device_id doesn't exist for this identity" would let a caller enumerate a target's actual bound device IDs, a capability this platform deliberately doesn't expose anywhere else. Both cases must be byte-for-byte identical responses.

**Consumes:**
- **Cryptography & Keys** — for key pair generation, device key binding proofs, and local secure storage of the identity's private material. Identity never implements its own crypto.
- **Audit / Explainability** — every bind/revoke/export emits an audit event.

## 4. Constitutional obligations

- **Art. 1 (ownership):** the identity's private key is generated and held client-side via Cryptography & Keys. The server stores only the public identity record. There is no server-side "reset identity" path that does not go through a user-controlled recovery mechanism.
- **Art. 5 (explainability):** `BindDevice`, `RevokeDevice`, and any change to the public identity record emit audit events — a user can always answer "when was this device added, and by which already-bound device." **Amended 2026-08-19:** `PublishPrekeyBundle` and every `FetchPrekeyBundle` call that consumes a one-time prekey also emit audit events (actor, action, target `identity_ref`/`device_id`, never any key bytes — public or otherwise, matching Cryptography & Keys' own "never the key material itself" discipline even though these particular keys are public). `FetchPrekeyBundle`'s actor is the *fetcher*, not the target device's owner — per Audit's own established actor-scoped, self-only-by-default `Query` visibility (`audit-explainability.charter.md` §3 — citation corrected 2026-08-19, Constitution Warden gate finding, round 1: was miscited as §6/§7), the target identity does not automatically see "someone fetched my bundle" unless a future capability explicitly surfaces it; this is a deliberate, minimal choice (avoiding a passive "who's been looking at me" surveillance signal with no clear purpose yet), not an oversight. **This choice is revisited, not reversed, by §6's new compounding-risk finding below** — a low-resolution, count-only passive signal is added there, which does not conflict with keeping per-fetch/per-fetcher visibility off.
- **Art. 7 (security never reduces ownership):** device recovery (lost-all-devices case) must not become a disguised server-side override. See Open Questions. **Amended 2026-08-19:** `PublishPrekeyBundle` must be caller-bound (`identity`/`device_id` == verified caller's own) — without this, anyone could publish a bogus prekey bundle for someone else's device, corrupting the cryptographic trust root for every future session with that device until detected. This is a more severe failure mode than a typical caller-mismatch bug elsewhere in this codebase, not an equivalent-severity instance of the same pattern.
- **Art. 8 (privacy) — data manifest:**
  - `display_name` — purpose: shown to other users so they know who they're communicating with; user-editable, not derived from any other source.
  - `public_key(s)` — purpose: the Ed25519 signing key used to bind devices and verify signed assertions (device-binding proofs, and — as of the key-separation fix, 2026-08-21 — `signed_prekey`/`identity_dh_public_key`'s own signatures); no corresponding private material ever leaves the device. **Corrected 2026-08-21 (Security Steward gate finding on the key-separation fix: this line still claimed "let others encrypt to this identity," which is no longer accurate now that encryption/X3DH runs through the separately-manifested `device.identity_dh_public_key` field below, not this one — the exact ambiguity this whole fix exists to eliminate, now closed here too).**
  - `device.name` — purpose: lets the user tell devices apart in the Devices screen; user-editable.
  - `device.added_at_unix` — purpose: powers the Art. 5 "when was this device added" answer. (Cosmetic naming sync, 2026-08-19, Experience Guardian gate finding on `conversations.charter.md`: this prose previously said `device.added_at`, pre-dating the `_unix` suffix convention already applied to the real proto/Go field; corrected so this charter's prose matches the code Conversations' own charter now depends on.)
  - `device.last_seen` — purpose: lets the user spot a device they no longer recognize or use, as a security signal; **amended 2026-08-19: also now the basis for `FetchPrekeyBundle`'s default device-selection rule when `device_id` is omitted (§3), a second use of an already-collected field, not a new one.**
  - **Added 2026-08-19:** `device.signed_prekey.public_key`/`.signature`/`.created_at`/`.prekey_id` — purpose: identical category and purpose to Cryptography & Keys' own manifest entry for the same material (`cryptography-and-keys.charter.md` §4) — lets another identity's device asynchronously establish an E2E session with this device. **`device.identity_dh_public_key` — added 2026-08-21 (key-separation fix, same purpose category): the identity's X25519 DH-capable public key, genuinely distinct from `identity.public_key` (the Ed25519 signing key) — see §3's `PublishPrekeyBundle`/`FetchPrekeyBundle` correction. Purpose: the DH-capable half of the X3DH construction; without this being genuinely separate from the signing key, the identity's signing scalar would be exposed to attacker-influenced DH input on every session establishment (the exact defect this fix closes).** **`device.identity_dh_public_key_signature` — added 2026-08-21, round 2 — purpose: proves `identity_dh_public_key` genuinely came from this identity's own signing key, not a value a compromised publish/fetch path substituted (§6's substitution-threat bullet, mirrored from `cryptography-and-keys.charter.md` §6).** `device.one_time_prekeys[].public_key`/`.prekey_id` — same purpose, plural (a consumable pool rather than a single value). **Consumed one-time prekeys are deleted from this device's pool on fetch, not retained with a "consumed" marker** — once used, the public key serves no further purpose (its corresponding private key is independently, atomically deleted client-side per Cryptography & Keys' own amendment), and retaining it would be data collection with no documented purpose, the exact thing this bullet exists to prevent. **`device.unconsumed_one_time_prekey_count` (Security Steward gate finding, round 1, added to §3's `ListDevices` bullet) — purpose: a self-only, count-only passive signal letting a device's owner notice abnormal prekey depletion (the exhaustion-abuse-vector mitigation, §6), the same "security signal" purpose already established for `device.last_seen` above. This is a derived count, not a new category of collected material — it's computed from the same pool already covered by the entry above, never a per-fetch or per-fetcher log.**
  No other fields are collected at this layer. No collection of unrelated profile data at this layer; that belongs to a future profile-composition feature, not this capability.
- **Art. 9 (export):** `ExportIdentity` is a first-class, always-available operation, not a support-ticket process. **Prekey state is deliberately excluded from `ExportIdentity`'s output, stated explicitly rather than left as a silent gap (2026-08-19):** unconsumed one-time-prekey counts and the current signed prekey are ephemeral, automatically-regenerating routing infrastructure, not data whose loss would harm a leaving user — a device that rejoins or a fresh device that binds simply regenerates and republishes on next launch (Cryptography & Keys §5's own "invisible background maintenance" commitment). `ExportIdentity`'s actual purpose — a user is never locked out of their own cryptographic identity — is unaffected by this exclusion.
- **Art. 10 (modularity):** depends only on Cryptography & Keys' and Audit's published contracts; does not reach into their internals. **Reaffirmed 2026-08-19:** this capability still "never implements its own crypto" (opening sentence of this bullet) — prekey publish/fetch is pure storage/relay for public material Cryptography & Keys already generated and signed, the same role this capability already plays for `device_public_key`; no new capability dependency is introduced. **Named as a bounded exception, not silently smuggled past this bullet's "pure storage/relay" claim (Constitution Warden gate finding, round 1: the original text was silent on this):** `FetchPrekeyBundle`'s default-device-selection rule when `device_id` is omitted (§3, most-recently-active by `last_seen`) is a real routing decision this capability makes unilaterally — it is not storage/relay of already-signed bytes, it is Identity choosing *which* device's bytes to relay. This is a deliberate, narrow exception to this bullet's general claim, held to the same explicit-justification standard as `FetchPrekeyBundle`'s openness exception immediately above: it's acceptable because the decision is reversible, non-cryptographic (it doesn't affect the security of the resulting session, only which device receives it), and disclosed as a placeholder pending real multi-device support (§7) — not because it's somehow not a decision.

## 5. Experience budget

Zero-config path: identity and a first device key are generated automatically on first launch — no signup form beyond a display name. "Transparent when curious": a Devices screen lists every bound device, when it was added, and by whom (which device authorized it) — discoverable, not front-and-center. Adding a second device is a deliberate, visible pairing flow (e.g. scan/confirm), never silent. `ExportIdentity` lives alongside the Devices screen as an explicit action, not hidden in a settings submenu.

The recovery flow (identity creation) is a single, guided screen shown once: it generates the recovery phrase, states plainly in one sentence that losing it together with all devices means permanent, unrecoverable loss of identity, and requires the user to actively confirm they've saved it before proceeding — mirroring the seriousness of the moment without turning it into a multi-step wizard.

**Amended 2026-08-19:** `PublishPrekeyBundle`/`FetchPrekeyBundle` must be fully invisible, automatic machinery — no user action, no user awareness required. Publishing happens as a byproduct of Cryptography & Keys' own already-specified invisible background maintenance (`GeneratePrekeyBundle`, that charter's §5); fetching happens transparently the moment a user sends their first message to someone, as part of Conversations' own already-specified lazy `CreateConversation` flow (`conversations.charter.md` §5). Neither introduces a new user-facing surface.

## 6. Threat model

In scope because device binding is a security-sensitive boundary, though the deep cryptographic mechanics are owned by **Cryptography & Keys**.

- **Device spoofing:** binding a new device must require cryptographic proof from an existing device (or the recovery mechanism), not just knowledge of a shared secret transmitted over a channel the server could observe.
- **Server-as-identity-authority risk:** the server must not be able to unilaterally bind a device to a user's identity or reissue an identity without a user-controlled action being provable after the fact (feeds the Art. 5 audit trail).
- **Lost-all-devices recovery:** the hardest open question — see below. Any recovery path is in Security Steward's remit to approve before this charter can freeze.
- **Server-side atomic single-issuance — the core new requirement of this amendment, added 2026-08-19, and the direct server-side mirror of Cryptography & Keys' own client-side mutex requirement (`cryptography-and-keys.charter.md` §6):** `FetchPrekeyBundle`'s one-time-prekey claim must be a single atomic database operation — claim-and-**delete** within one transaction/statement (**corrected 2026-08-19, Constitution Warden gate finding, round 1: the original sketch here, `UPDATE ... SET consumed = true ... RETURNING`, directly contradicted §4's own Art. 8 commitment that consumed one-time prekeys are deleted, not retained with a marker — a real self-contradiction, not just imprecise wording** — e.g. `DELETE FROM one_time_prekeys WHERE prekey_id = (SELECT prekey_id FROM one_time_prekeys WHERE device_id = ? FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING *`, or an equivalent construction that never leaves a "consumed" row behind) — never a separate read-then-delete. Two concurrent fetches for the same device must never both receive the same `prekey_id`. **The actual failure mode if this is violated, corrected 2026-08-19 (Security Steward gate finding, round 1 — the original text overstated this as a forward-secrecy break, which it is not):** Cryptography & Keys' already-frozen `CompleteSharedSecret` independently guarantees that only the *first* caller to reference a given `prekey_id` succeeds — its own atomic delete-plus-distinguishable-error (that charter's §6) means a second, double-issued caller cleanly fails rather than completing a session, so **forward secrecy itself is not actually at risk from double-issuance at this layer; the crypto-layer guarantee already fully absorbs it.** The real, still-serious consequence is different: because the prekey-bundle design lets an initiator send real ciphertext in their very first message (the whole reason this construction was chosen over a round-trip handshake), the *losing* initiator's real first message — sent believing the handshake would succeed — is silently and permanently undecryptable, with no ack/nack path back to them specified anywhere in this charter or Conversations'/Cryptography & Keys' own. That is an Art. 1 (data loss) and Art. 5 (no explainable failure) problem, not a security compromise — but it is the actual reason this requirement matters, and whoever eventually designs message-delivery failure handling in Conversations inherits this as a named, not-yet-solved gap (§7), not something this charter resolves.
- **Bounded-timeout locking, required — this codebase has already suffered the alternative once:** whatever row-level or advisory lock the atomic claim above uses must be bounded by a timeout, never held indefinitely. `docs/CAPABILITY_REGISTRY.md`'s own record of Storage's `lockBlob` incident (an unbounded lock genuinely exhausted the shared connection pool and took down every Postgres-backed capability, not just Storage, until fixed) is the concrete precedent this bullet exists to prevent from recurring on a second table. This is a required design constraint on the implementation, not an optional hardening pass.
- **Impersonation via `PublishPrekeyBundle`:** see Art. 7 above — caller-binding closes this; stated here too since it's a threat-model item, not only a constitutional one. **Required, stated explicitly and independently confirmed by both guardians against the real code, not assumed: caller-binding here means both `identity` AND `device_id` must be checked against the verified session, not identity alone — and nothing wired today does this.** `sessionauth.Session`/`ValidateSessionResponse` genuinely carries a cryptographically-verified `DeviceID` (proof-of-possession checked at `IssueSession` time, per `services/api/internal/sessionauth/service.go`) — the underlying guarantee this needs already exists. But **the actual currently-wired middleware, `requireCallerMatchesIdentity` (`services/api/internal/identity/http.go` — corrected 2026-08-19, Security Steward gate finding, round 1: an earlier draft of this bullet named the wrong middleware, `requireVerifiedCaller`), checks `identity_ref` only; no capability's gating pattern in this codebase does device-level binding today.** A capability engineer who reuses `requireCallerMatchesIdentity` unmodified for `PublishPrekeyBundle` would correctly bind `identity` but leave `device_id` completely unchecked — meaning any of a multi-device identity's own already-bound devices could publish a bogus bundle *for a different device of the same identity*, corrupting that other device's trust root for every future session — a real, narrower but still genuine instance of the impersonation risk this bullet exists to close. **Required, not merely flagged for the merge gate: this RPC needs a *new*, explicit `device_id`-binding check sourced from `ValidateSession`'s verified `device_id`, which does not yet exist anywhere in this codebase and must not be assumed to fall out of reusing existing middleware.** The capability engineer must add it, and the merge gate must verify it was added, not merely that `requireCallerMatchesIdentity` was applied.
- **Prekey exhaustion as an abuse vector, corrected 2026-08-19 (Security Steward gate finding, round 1: the original text mischaracterized this as already tracked in `docs/CAPABILITY_REGISTRY.md`, which it wasn't — checked directly, that entry names only `CreateIdentity`/`GetSessionChallenge`; fixed by amending the registry to add this RPC explicitly, see `docs/DECISION_LOG.md`) and named as its own compounding-risk bullet, not folded into a generic "rate limiting later" note:** an attacker could repeatedly call `FetchPrekeyBundle` against a victim's device to drain their one-time-prekey pool, forcing every subsequent real session into Cryptography & Keys' already-disclosed, already-secure-but-weaker exhaustion-fallback guarantee. This is **not a new catastrophic failure on its own** — the fallback already exists, is disclosed, and remains secure against anything except a future compromise scoped to the current signed-prekey rotation window — **but three individually reasonable design choices compound into something worse than that framing alone suggests: (1) `FetchPrekeyBundle`'s deliberate openness (any caller, any target), (2) a "read" with a real resource-depleting write side effect, and (3) §4's deliberate choice not to surface per-fetch visibility to the target.** Together, a sustained, targeted drain of one victim's pool is invisible to that victim by explicit design, with no passive signal on the responder side analogous to the exhaustion-fallback badge that already exists on the *initiator* side. **Minimal mitigation, added here rather than left unaddressed:** `ListDevices` (§3 of this charter, pre-existing) gains a new self-only field per device, `unconsumed_one_time_prekey_count` — a low-resolution, count-only passive signal (never per-fetcher, never per-fetch-event) that lets the device's own owner notice abnormal depletion, consistent with `device.last_seen`'s own established "security signal" purpose (§4) and without reopening the deliberate choice to keep per-fetch visibility off.
- **Signature integrity in storage:** Identity stores the signed prekey's signature byte-for-byte as published and returns it unmodified on fetch — it has no signing key and must never regenerate, re-sign, or reformat it. Stated explicitly to close off any temptation to "helpfully" transform it in transit.
- **`FetchPrekeyBundle`'s openness — a deliberate, bounded exception to this capability's otherwise self-scoped read patterns, argued rather than silently mirrored from `ResolveIdentity`, and corrected 2026-08-19 (Constitution Warden gate finding, round 1: the original argument conflated confidentiality with full behavioral equivalence to `ResolveIdentity`) to name both axes separately, not just one:**
  - **Confidentiality axis — genuinely parallel to `ResolveIdentity`:** its response shape contains *only* material that is already, unconditionally public by Cryptography & Keys' own design (`identity_dh_public_key` — corrected 2026-08-21, Constitution Warden gate finding: this line still named the pre-key-separation-fix field, `identity_public_key`, as if current — a signed prekey's public parts, one one-time prekey's public part) — nothing in the response has a private or self-only counterpart that could leak. This part of the analogy holds by construction.
  - **Behavioral axis — genuinely *not* parallel, stated plainly rather than left implicit:** unlike `ResolveIdentity` (a pure, idempotent, non-mutating read), `FetchPrekeyBundle` atomically consumes and permanently deletes a scarce, finite resource belonging to the target identity on every successful call — an open-to-any-caller "read" with a real, resource-depleting write side effect. This is a materially different behavioral class, and it is precisely what makes prekey exhaustion (this section's own dedicated bullet, above) a real threat-model concern in a way `ResolveIdentity` never had to consider. The openness decision is still correct — an initiator genuinely cannot start a session without this call being reachable — but its safety rests on *both* axes being separately true, not on the confidentiality axis alone standing in for the whole picture.

## 7. Open questions / risks

- **Recovery when all devices are lost — resolved.** Per Cryptography & Keys' committed design (see `docs/DECISION_LOG.md`, 2026-07-06, "Recovery mechanism: deterministic key derivation, no server escrow"), the recovery phrase deterministically derives the identity's key material, and a new device binds itself by self-signed proof from that derivation — the server never verifies or approves it, only relays and audit-logs it (see §3, §6). If the recovery phrase is lost in addition to every bound device, **identity recovery is permanently and intentionally impossible** — there is no support-mediated fallback, by design, because any such fallback would itself be the disguised server override Art. 7 forbids. This tradeoff must be stated plainly to the user at identity creation, not hidden in fine print.
- **Mutual dependency shape with Audit and Permissions — resolved.** Identity, Audit, and Permissions form a three-way contract reference (see each charter's Interface). Per `docs/DECISION_LOG.md`, 2026-07-06 ("Foundation contracts composition: opaque references, no live cycle"), every cross-capability reference among these three (`identity_ref`, `subject`, `actor`) is an opaque contract-level identifier, never a concrete struct owned by one capability crossing into another's package. Audit resolves actor identity and applies permission-gating lazily, at `Query`/`Explain` call time, not as a live dependency required at `Emit` time — so no capability requires the other two to be already-initialized to construct itself. This satisfies Art. 10: the dependency exists only at the published-contract level, never as a circular Go package import.
- **Resolved 2026-08-19 — the brand-new-identity edge case Cryptography & Keys' amendment named and deliberately left to this one (`cryptography-and-keys.charter.md` §7 item 1):** a device with no published bundle at all must never be silently treated as "exhausted one-time-prekeys but has a signed prekey" — `FetchPrekeyBundle` returns a distinguishable "no bundle published" result for this case (§3). The recommended client-side mitigation (mobile onboarding should call `GeneratePrekeyBundle`/`PublishPrekeyBundle` immediately after `BindDevice` succeeds, before treating onboarding as complete) is a client-orchestration responsibility, not a new requirement on `BindDevice`'s own contract — this charter does not couple the two RPCs at the interface level, only recommends the ordering at the feature-composition layer.
- **Which device `FetchPrekeyBundle` targets when `device_id` is omitted (§3, §6) is a reasonable default (most-recently-active), not a solved multi-device answer** — inherits, rather than newly introduces, the multi-device-routing gap already disclosed in Cryptography & Keys' charter §6/§7 and Conversations' charter §5/§7. Revisit when real multi-device support is chartered.
- **No ack/nack path for a first message that fails to establish a session, named as a real gap rather than solved here (Security Steward gate finding, round 1, arising from correcting §6's atomicity rationale):** if `FetchPrekeyBundle`'s single-issuance guarantee is ever violated (implementation bug, not a designed behavior), the losing initiator's real first message is silently and permanently undecryptable, with no error surfaced anywhere in this charter, Cryptography & Keys', or Conversations' own. This is inherited by whoever eventually designs message-delivery failure handling in Conversations — flagged here so it isn't lost, not resolved by this amendment.
- **One-time prekeys carry no per-key signature (unlike the signed prekey), non-blocking but named rather than silently absent (Security Steward gate finding, round 1):** a compromised/malicious server could substitute a bogus one-time prekey's public key in a fetched bundle. This cannot yield plaintext or break confidentiality — the algebra simply produces a non-matching secret, a clean decrypt failure at the crypto layer, not a leak — but it is an unaddressed integrity/availability vector (a silently corrupted specific handshake) not currently named in either this charter or Cryptography & Keys'. Not blocking this amendment; a candidate for a future hardening pass if it's ever worth the added complexity of per-one-time-prekey signing.
- **New capability-engineer implementation note, corrected 2026-08-19 (Security Steward gate finding, round 1: the original version of this note pointed at the wrong precedent and, taken literally, would have reopened the exact "separate read-then-delete" pattern §6 forbids).** The atomic-claim SQL sketch in §6 is illustrative in its exact syntax, not in its shape — but the *shape* is prescriptive: **a single atomic statement (or a genuinely transaction-scoped equivalent with no extra network round-trip), never a multi-statement check-then-act sequence.** Storage's `lockBlob` (`services/api/internal/storage/postgres_store.go`) is **not** an acceptable model to follow here, and must not be cited as one: it holds a session-level advisory lock across a *multi-statement, non-transactional* sequence (`MoveBlob`/`DeleteBlob` span several separate `Store` calls) — a different mechanism solving a different problem. An engineer who copies that pattern (acquire a lock → `SELECT` an available prekey → `DELETE`/`UPDATE` it → release) would be implementing exactly the "separate read-then-delete" this bullet forbids, just with a lock wrapped around it, and would reintroduce the dedicated-connection/bounded-timeout complexity that caused the whole-server DoS `lockBlob` itself required a fix for. **`lockBlob` is cited in this charter for one lesson only — bounded timeouts on any lock this implementation does use — never as a mechanism template.** Required regardless of exact SQL chosen: single-statement atomicity, plus a concurrency test proving two simultaneous fetches for the same device's last remaining one-time prekey never both succeed.
