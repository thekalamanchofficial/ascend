# Capability Charter: File Objects

## 1. Name and one-line purpose

**File Objects** — files as first-class citizens: every file carries identity, ownership, versions, metadata, history, and lifecycle, never a disposable attachment (Art. 2).

## 2. Article 17 answer (asked first)

Yes, directly — this capability exists because Article 2 names files as first-class citizens explicitly. Treating a file as a durable object with its own identity and history (rather than a blob bolted onto a message) is what lets a user actually own their files: know their provenance, control their permissions independent of where they were shared, and see their full history.

## 3. Interface

**Exposes:**
- `ListFileObjects(owner, requesting_subject) -> [file_object]` — **added 2026-08-18**, closing a real gap found integrating the mobile client: no RPC anywhere in this charter ever let a caller discover *which* `file_object_id`s exist for them at all — every other operation requires already knowing one. A "my files" screen was structurally impossible to build without this. **Deliberately self-only, not `CheckPermission`-gated**, mirroring Storage's own `ExportAllBlobs` precedent (§3 of that charter) exactly: listing everything an owner has is a right-to-see-your-own-stuff operation, not a shareable read, so this is never routed through Permissions.

  **Authorization — two independent checks required, not one (Security Steward gate finding, 2026-08-18):** an initial version of this bullet specified only that `requesting_subject == owner` as a service-level self-consistency check between the two request fields — that alone is a real authorization bypass: nothing stopped a caller from sending `owner=requesting_subject=<victim>` and receiving the victim's entire file inventory, since neither field was ever bound to who was actually, verifiably making the request. Fixed to require the identical two-layer discipline `ExportAllBlobs` and every other File Objects RPC already carry (§3's closing paragraph, corrected below): (1) service-level, `requesting_subject == owner`; (2) HTTP-level, `requesting_subject == caller` — the verified, server-overwritten identity resolved from the bearer session token, never a client-supplied value — checked before either handler logic or the service-level check runs. Both must hold or the call is rejected; there is no path where `owner`/`requesting_subject` are trusted as self-asserted request fields.

  **Denial auditing — required on every rejection, of either check above (broadened from the original Constitution Warden fix per Security Steward's same-day finding):** `ExportAllBlobs` emits `storage.export_all_blobs_denied` on its own self-only rejection — a precedent this bullet's first draft claimed to mirror "exactly" while specifying the opposite (no audit at all), which did not survive either guardian's review. `ListFileObjects` must call `audit.Emit` on every rejection — whether from the service-level owner/requesting_subject mismatch or the HTTP-level caller mismatch — naming the attempted target `owner` (e.g. action `file.list_denied`, actor the verified caller, resource `("identity", owner)`), never any individual file's `file_object_id`. Required and test-backed at implementation, same standard as this charter's other audit obligations (§4). This is a real, non-theoretical control: without it, an enumeration attempt sweeping many `owner` values leaves no trace at all.

  Returns the existing `file_object` shape (§3's `CreateFileObject` return type) unchanged — `file_object_id`, `owner`, `current_version_ref`, `name`, `mime_type`, `tags`, `size` — which was already confirmed leak-free of `blob_ref` by §6 point 8; this amendment introduces no new field and therefore reopens none of that point's three closed leak paths (independently re-confirmed by Security Steward: no `Storage.RetrieveBlob` path, no new Permissions/Storage calls at all, and bulk `current_version_ref` exposure to a file's own owner grants no capability beyond what looping `ListVersions` per file already allows the same owner).

  **Unbounded result set, named explicitly rather than silently inherited (Security Steward finding):** this returns every file object an owner has ever created, with no pagination — consistent with, and no worse than, `ListDevices`/`ListActiveSessions`/`ListVersions`'s existing precedent elsewhere in this codebase, which share the same unbounded shape. Accepted as a standing, consistent platform pattern for this pass, not a novel risk this RPC introduces alone; a future pass introducing pagination across all of these RPCs together, if ever needed at scale, is tracked as a platform-wide concern, not specific to this one.

  **What this deliberately does not solve, tracked in §7 — corrected 2026-08-18 (Security Steward found the original §7 text factually wrong, not merely conservatively scoped):** discovering files *shared to you by someone else* (as opposed to files you own). The primitive this would need — **`Permissions.ListGrants(subject)` (that charter's §3) already exists, is implemented, and is network-mounted and self-scoped** (`GET /v1/permissions/grants/subject`) — the original text here incorrectly claimed no such reverse index existed at all. It is not used by this amendment because each returned `Grant` carries only `resource_type`/`resource_id`/`action` (`("file_object", file_object_id, "fileobjects.read")` for a relevant one), not the `file_object`'s own name/metadata a "shared with me" list needs to be usable — composing it into a real list view means filtering `ListGrants`' output client-side or server-side and then hydrating each match via `GetFileMetadata`, which is a deliberate scope exclusion of *this* amendment (a second, small composition to build, not a missing primitive to charter), not a blocked-on-Permissions gap. Until that composition is built, a recipient learns a shared file's `file_object_id` out-of-band from the sharer and opens it directly via the already-functional, already-gated `GetFileContent`/`GetFileMetadata`.
- `CreateFileObject(owner, requesting_subject, initial_content) -> file_object` — allocates identity, records owner, creates version 1. Per §6, also establishes the resource `("file_object", file_object_id)` in Permissions (owner's first grant on it makes them its implicit owner, per Permissions' own bootstrap rule) and the matching `("blob", blob_ref)` grant for the newly stored blob — both are bookkeeping this call performs, not new access-control logic.
- `CreateVersion(file_object_id, requesting_subject, content) -> version_ref` — every edit is a new version, never an overwrite. Per §6, also mirrors every currently-active `fileobjects.read` grant on the file object onto the new version's blob, so a subject already shared on the file keeps read access to future versions without a fresh `SetFilePermissions` call.
- `GetFileContent(file_object_id, requesting_subject, version_ref?) -> content` — **added at charter-freeze review, 2026-07-17: the original charter text had no RPC that ever returns a file's actual bytes back to a caller** — `CreateFileObject`/`CreateVersion` write content, `GetFileMetadata`/`GetFileHistory` read metadata/events, but nothing read content back. A file object no capability can ever read is not a usable primitive; this closes that gap. Omitting `version_ref` returns the current (latest) version. Delegates to Storage's `RetrieveBlob` for the underlying bytes, and **must** call `CheckPermission` first (see §6) — File Objects never returns content Permissions would deny.
- `ListVersions(file_object_id, requesting_subject) -> [version_summary]` — added alongside `GetFileContent` for the same reason: `GetFileContent`'s optional `version_ref` is meaningless if there's no way to discover what versions exist. Returns `version_ref`, `created_at`, `created_by`, `size` per version — the version-level analog of `GetFileMetadata`, feeding both the "transparent when curious" version-history UI (§5) and `GetFileContent`'s parameter.
- `GetFileHistory(file_object_id, requesting_subject) -> [events]` — full lifecycle history (created, versioned, shared, permission-changed, deleted).
- `SetFilePermissions(file_object_id, requesting_subject, grant_or_revoke, subject, action, scope)` — grants or revokes `subject`'s access to the file object. `action` is one of exactly two values defined by this charter (§6): `fileobjects.read` or `fileobjects.write` — not an open-ended string, so File Objects' own resource stays bounded the same way its metadata schema does (§3). Calls **Permissions**' own `GrantPermission`/`RevokePermission` against resource `("file_object", file_object_id)`; File Objects does not reimplement access control, and `requesting_subject` itself must already hold grant/revoke authority on this resource per Permissions' own escalation rule, not a separate check File Objects invents. Per §6, a `fileobjects.read` grant/revoke also mirrors onto every existing version's underlying blob — that mirroring is bookkeeping to keep Storage's own independent permission check satisfied, not a second access-control decision; the allow/deny logic itself is made exactly once, by Permissions, at the `file_object` level. A `fileobjects.write` grant/revoke needs no blob-level mirror — writing creates a new blob under the file's existing owner-established storage credentials (§6), it doesn't read an existing one.
- `GetFileMetadata(file_object_id, requesting_subject)` / `SetFileMetadata(file_object_id, requesting_subject, name?, mime_type?, tags?)` — a fixed field set (`name`, `mime_type`, `tags`, `size`), independent of any one conversation or context the file appears in. `size` is derived (from the current version's stored blob), never caller-settable via `SetFileMetadata`. Any future field beyond this fixed set requires a charter amendment through this capability's data manifest (§4), not an open-ended schema — this closes off the "other descriptive metadata" bucket that would otherwise let arbitrary fields accrete without Art. 8 review.
- `ExportFile(file_object_id, requesting_subject) -> portable_bundle` — file content (all versions, not just current — an export that silently dropped history would violate Art. 9's "complete artifact" promise below) plus its full metadata/history, in a documented portable format (Art. 9).
- `DeleteFileObject(file_object_id, requesting_subject)` — lifecycle termination: calls Storage's `DeleteBlob` (or its crypto-shred fallback) on every version's underlying blob, so "no longer retrievable" is a real guarantee, not just an API-level flag. The file object's identity and history entries remain resolvable in the audit trail per Art. 5, but never the content.

Every operation above now explicitly names `requesting_subject` (added at the same 2026-07-17 review, for the same reason Storage's contract already carries it on every content-touching RPC). **Two independent mechanisms enforce this is never a self-asserted field, corrected 2026-08-18 (Security Steward gate finding on `ListFileObjects`, below — this sentence previously implied `CheckPermission` was the sole mechanism, which is only true for the nine RPCs that call it):** for the nine RPCs whose access-control decision is delegated to Permissions, `CheckPermission` is what gates a mismatched `requesting_subject`; independently, and applying to **all ten** RPCs including the self-only `ListFileObjects`, the network HTTP layer itself checks `requesting_subject == caller` (the verified, server-overwritten identity from the bearer session token — never a client-supplied header) before any handler logic runs, exactly the discipline `docs/DECISION_LOG.md`'s 2026-08-16 File Objects network-wiring entry already committed to for the original ten. File Objects has no operation that trusts an implicit or ambient caller identity at either layer.

**Consumes:**
- **Storage** — file content (and each version) is stored as one or more blobs. **Storage's own `RetrieveBlob` performs its own independent `CheckPermission` against resource type `"blob"` (`services/api/internal/storage/types.go`, `resourceTypeBlob`/`ActionRetrieveBlob = "storage.retrieve_blob"`) — this is not bypassable and File Objects must never route around it with a synthetic/service subject (that would be the confused-deputy pattern Permissions' own charter §6 forbids). See §6 for how File Objects keeps this check satisfiable.**
- **Permissions** — every access-control *decision* delegates here; File Objects holds no parallel ACL and makes no allow/deny judgment of its own. File Objects does, however, own keeping two of Permissions' own resource namespaces in sync (`"file_object"`, its primary user-facing resource, and `"blob"`, Storage's) — see §6. This is bookkeeping performed via Permissions' own `GrantPermission`/`RevokePermission` calls, not a second ACL.
- **Identity** — owner and history actor references.
- **Cryptography & Keys** — indirectly, via Storage's encryption boundary.
- **Audit / Explainability** — every mutating operation emits an event, which is also how `GetFileHistory` is largely populated.

## 4. Constitutional obligations

- **Art. 2 (files first-class):** every file object schema must carry identity, owner, and history fields — this is mechanically enforced by `scripts/constitution/check-file-objects.sh` once the Go types exist (mark persisted file-object structs with `// ascend:file-object`), which requires a case-insensitive field-name substring match for `ID`, `Owner`, **and `History`** (verified directly against the script, 2026-07-17 re-gate). Detailed history lives in Audit, not duplicated on the struct — but the persisted, `ascend:file-object`-marked struct itself must still carry a field whose name contains "History" (e.g. `HistoryRef` or `LastHistoryEventID`, cross-referencing Audit rather than storing events inline) so the mechanical check passes by construction, not by accident of naming.
- **Art. 5 (explainability):** every mutation (`CreateFileObject`, `CreateVersion`, `SetFilePermissions`, `SetFileMetadata`, `DeleteFileObject`) emits an audit event; `GetFileHistory` is the user-facing surface for "why does this file look like this / who touched it." Read operations (`GetFileContent`, `ListVersions`, `GetFileMetadata`, `GetFileHistory`) route through the single `fileobjects.read` `CheckPermission` decision (§6) but are otherwise not individually audited on success, matching the precedent Session / Request Authentication set for `ValidateSession` (2026-07-17) — logging every successful read would flood the trail with noise, not add explainability. **Verified against the real implementation, not assumed:** `Permissions.CheckPermission` (`services/api/internal/permissions/service.go`) is a pure decision function with no audit side effect of its own — a denied read is *not* automatically audited by Permissions. Because all four read RPCs share one `CheckPermission` call site (§6), File Objects satisfies this with **one** shared denial-audit code path, not four separate ones: any denial there emits a single audit event (`file.access_denied` or equivalent) naming which RPC was attempted, so "someone tried to read a file they don't have access to" remains discoverable regardless of which read operation triggered it. **This obligation is merge-gate/test-verified, not CI-mechanically-enforced** — `check-audit-events.sh` only scans functions marked `// ascend:mutates` for `audit.Emit(`, and a conditional, denial-only audit call on an otherwise-unmarked read function is invisible to that check (confirmed precedent already exists unmarked in the codebase: `sessionauth.Service.ValidateSession`'s anomaly-audit call). The capability engineer must write a dedicated test proving a denied read actually emits this event — CI passing is not evidence this obligation was met. **`ListFileObjects` (added 2026-08-18) is a second, separate case, not covered by the shared `fileobjects.read` denial path above**, since it bypasses `CheckPermission` entirely by design (§3) — every rejection (service-level `requesting_subject != owner` mismatch, or HTTP-level caller mismatch — both required per §3's authorization discipline) must emit its own dedicated audit event (§3's `ListFileObjects` bullet has the exact requirement), independently test-verified the same way.
- **Art. 8 (privacy) — data manifest:** `name` — purpose: user-facing identification; `mime_type` — purpose: correct rendering/handling; `tags` — purpose: user-driven organization (Art. 11); `size` — purpose: display and storage-policy decisions. No other fields; see §3 on closing off open-ended metadata.
- **Art. 9 (export):** `ExportFile` bundles content, metadata, and history — a user leaving the platform gets a complete, self-contained artifact, not just raw bytes stripped of provenance.
- **Art. 10 (modularity):** File Objects composes Storage + Permissions + Identity + Audit through their published contracts only; it adds no independent storage or access-control logic of its own.
- **Art. 16 (consistency):** the same file-object model applies everywhere a file appears (a message attachment, a shared note, etc.) — no per-context reimplementation.

## 5. Experience budget

Zero-config default: attaching a file "just works" and automatically gets identity/history/permissions with no extra steps from the user. **Opening/viewing a file resolves silently to the current version — no version-selection step is ever required in the default path.** `GetFileContent`'s optional `version_ref` (§3) exists solely for the "transparent when curious" affordance below, never for primary retrieval; a capability engineer must not read its existence as license to put a version picker in front of the common "open this file" flow.

"Transparent when curious": `GetFileHistory` and `ListVersions` compose into **one surface, not two the user has to learn are different** — a single history/timeline view, one tap away from anywhere the file is referenced, with version-creation events shown inline among the other lifecycle events (shared, permission-changed, etc.), and each version-creation entry links directly to that version's content via `GetFileContent(version_ref=...)`. There is no separate "Versions" tab or screen a user navigates to independently of the history they already reach.

"Powerful when needed": permission and metadata editing available but not surfaced unless requested.

## 6. Threat model

Largely delegated — File Objects' own logic is not security-sensitive in isolation (it composes chartered primitives), but Security Steward should confirm no bypass:

- File Objects must not cache or duplicate content outside what Storage returns (no shadow plaintext copies for "performance").
- `SetFilePermissions` must not offer a path that skips Permissions' `CheckPermission`/grant model.

**The dual-layer permission problem, found and resolved at charter-freeze re-gate (2026-07-17, Constitution Warden):** `GetFileContent`/`ExportFile` delegate to Storage's `RetrieveBlob`, which performs its **own independent** `CheckPermission` against resource type `"blob"` (`services/api/internal/storage/types.go`) — a separate resource namespace from anything File Objects checks on its own. As originally specified, nothing ever established a `"blob"`-level Permissions record, so Storage's own check would fail closed on every call regardless of File Objects' own decision — the read path could not have worked end-to-end. Two bad fixes were explicitly ruled out: inventing an undocumented blob-grant-bootstrapping scheme (an Art. 10 violation — the charter must own this, not leave an engineer to discover it), and passing a synthetic/service subject to Storage instead of the true caller (the exact confused-deputy pattern Permissions' charter §6 forbids: "a capability that calls `CheckPermission` on behalf of a user must pass the true acting subject, never a capability's own service identity, or checks become meaningless").

**Resolved design — File Objects owns exactly one primary Permissions resource, `"file_object"`, and mirrors matching `"blob"`-level grants underneath, transparently:**

0. **Policy registration — traced and confirmed necessary, not assumed (second re-gate finding, Constitution Warden, 2026-07-17):** `Permissions.CheckPermission` fails closed on `!hasPolicy(resource_type)` *before* it ever reaches the owner/grant check — a resource type with no prior `DefinePolicy` call denies every subject, including the true owner, regardless of any grant established below. **Every capability that calls `CheckPermission` against its own resource type must register that type's default policy at its own construction/wiring time** — this is precisely what Permissions' own charter §3 describes `DefinePolicy` for ("lets a capability register its default policy shape when it comes online"), and `setPolicy` (`services/api/internal/permissions/store.go`) is a plain, idempotent, unauthenticated map write, safe to call once at startup. Concretely: **File Objects registers `"file_object"`'s own default policy (deny-by-default, owner-and-explicit-grant-only) at its own construction — this is File Objects' own resource type, no boundary question.** `"blob"` is Storage's resource type, not File Objects' — **Storage must register `"blob"`'s own default policy at its own construction**, the same pattern. Tracing the current codebase found this registration is missing from Storage's already-`stable` implementation (confirmed by a full-tree grep: `DefinePolicy` is called only from Permissions' own unit tests, nowhere in real service wiring) — this is a **pre-existing, latent gap in Storage, not introduced by this charter**, invisible until now only because nothing has been wired to a real (non-fake) Permissions instance. Tracked as a required fix to Storage (see `docs/DECISION_LOG.md`), and **File Objects' implementation may not merge until that fix has landed** — File Objects must not work around the gap by registering `"blob"`'s policy on Storage's behalf, which would be exactly the Art. 10 boundary-encroachment Constitution Warden's finding warned against. **The Storage fix's acceptance criterion, stated explicitly (third re-gate finding, Constitution Warden, 2026-07-17):** Storage's existing local `PermissionChecker` interface (`services/api/internal/storage/types.go`) currently exposes only `CheckPermission` — it must gain a `DefinePolicy`-shaped method and Storage's constructor must call it through that same local, capability-owned interface, exactly the DI pattern Storage's own merge gate praised for declining Audit's direct-import exemption (`docs/DECISION_LOG.md`, 2026-07-17, "Session / Request Authentication passes merge gate"). A fix that imports `internal/permissions` directly to call `DefinePolicy` satisfies this point's letter but regresses that discipline and does not satisfy this charter's dependency.
1. **`"file_object"` is the single, authoritative, user-facing permission surface.** Exactly two actions are defined on it: `fileobjects.read` (gates `GetFileContent`, `ListVersions`, `GetFileMetadata`, `GetFileHistory`, `ExportFile` — one action, one `CheckPermission` call site, deliberately not four+ granular read actions, so the Art. 5 denial-audit obligation above has exactly one place to live) and `fileobjects.write` (gates `CreateVersion`, `SetFileMetadata`). `SetFilePermissions` grants/revokes are themselves gated by Permissions' own escalation rule on this resource — `requesting_subject` must already hold grant authority, not a rule File Objects invents.
2. **`CreateFileObject`** establishes both records: the owner's first grant on `("file_object", file_object_id)` (bootstrapping ownership per Permissions' own first-grantor rule) and a matching grant of `"storage.retrieve_blob"` on `("blob", blob_ref)` for the version-1 blob — this is what makes Storage's own `RetrieveBlob` check succeed for the owner, **given point 0's registration is in place.**
3. **`CreateVersion`'s mirroring must use the file object's actual owner as `grantor`, with the owner's own grant established first, deterministically, before any mirrored grant (third re-gate finding, Constitution Warden, 2026-07-17):** Permissions' `Store` sets a resource's owner permanently and implicitly from whichever `GrantPermission` call happens to run *first* on it (`bootstrap_owner`, no privilege check — this is the same mechanism that correctly bootstraps `CreateFileObject`'s owner grant in point 2, applied here to a *new* blob resource that starts with no owner at all). A `CreateVersion` call may legitimately be made by a non-owner subject who holds only `fileobjects.write` — if the mirroring loop's grantor identity were left unspecified (e.g. naively using `requesting_subject`), that non-owner's mirrored grant could become the *first* `GrantPermission` call on the new blob, making them its **permanent, unrevocable** Permissions-owner instead of the file's real owner (Permissions' `Store` has no owner-transfer mechanism). To prevent this: `CreateVersion` must call `GrantPermission` for the file object's owner (as `grantor`, on the new blob, `"storage.retrieve_blob"`, full scope) **first**, unconditionally, before mirroring any other subject's grant onto that same blob — regardless of who called `CreateVersion`. Only after the owner's grant is the resource's first-ever grant does the mirroring loop proceed to other currently-active `fileobjects.read` subjects, mirroring `"storage.retrieve_blob"` for each (same subject, same scope) — so a subject already shared on the file keeps read access to future versions automatically, with no window where their access silently lags the file object's own.
4. **`SetFilePermissions`** grants/revokes on `("file_object", file_object_id)` are mirrored onto **every existing version's blob** at the same time (loop over `ListVersions` internally), using the file object's owner as `grantor` for every mirrored call (same discipline as point 3 — the owner already holds the first-mover grant on every existing blob from creation time, so this loop never risks a bootstrap-ownership hazard the way point 3's *new*-blob case does, but the grantor identity must still be stated explicitly, not left implicit). **This loop must fail loudly, not report success, on partial failure** (fourth re-gate finding, Constitution Warden, 2026-07-17): if a mirror-revoke fails partway through (call N of M errors), the file-object-level and blob-level state would otherwise silently drift — some already-revoked-at-the-file-object-level subject would remain able to read specific old versions directly via `Storage.RetrieveBlob`. `SetFilePermissions` must surface this as an error naming which versions' mirroring failed, matching Permissions' own established "mutation landed, completion failed → fail loudly" pattern (e.g. `GrantPermission`'s own audit-failure handling).
5. **This mirroring is bookkeeping, not a second access-control decision** — File Objects never decides allow/deny itself; it only keeps Permissions' own two resource namespaces in sync via Permissions' own `GrantPermission`/`RevokePermission` calls, so Art. 10's "File Objects... adds no independent... access-control logic of its own" still holds. The `"blob"`-level check remains genuine defense-in-depth (Storage's own charter-committed gate, never disabled or routed around), not redundant theater.
6. **This resolves the original per-version gating concern without needing per-version Permissions records:** because `fileobjects.read` is checked unconditionally on every `GetFileContent`/`ExportFile` call regardless of `version_ref`, and blob-level mirroring keeps every version's Storage-level grant in lockstep with the file-object-level grant, there is no path where an old, since-revoked version stays readable — a revoke removes both the file-object-level grant `GetFileContent` checks and the blob-level grants `RetrieveBlob` independently checks, for every version, in the same `SetFilePermissions` call (given point 4's fail-loudly requirement — a *reported-successful* revoke is a *complete* revoke, or the caller knows it wasn't).
7. **`ExportFile`** checks `fileobjects.read` once (same as `GetFileContent`), then loops `Storage.RetrieveBlob` per version — each call's independent Storage-level check is real defense-in-depth given the mirroring above, not an unchecked loop.
8. **`blob_ref` must never be returned through any File Objects RPC response, and — tightened after Security Steward's follow-up, 2026-07-17 — three specific leak paths this same charter's other commitments could otherwise open must be explicitly closed, not just the interface's own return values:**
   - `ListVersions` returns `version_ref` (§3), never `blob_ref`; `GetFileContent` returns raw content, never a ref. This is necessary but was **not sufficient as originally stated** — Security Steward traced two concrete paths already present in this charter's own other commitments that could leak `blob_ref` regardless: (a) Permissions' own audit events for the blob-level mirror calls (points 2-4) legitimately record `resource=blob_ref` verbatim, per Permissions' own charter Art. 8 data manifest; (b) an unhandled `Storage.RetrieveBlob` error propagated verbatim could embed `blob_ref` in its message.
   - **Closing (a): `GetFileHistory` and `ExportFile`'s "full lifecycle history" means File Objects' own emitted audit events only — `CreateFileObject`, `CreateVersion`, `SetFilePermissions`, `SetFileMetadata`, `DeleteFileObject`'s own `audit.Emit` calls — never a raw aggregation of the underlying Permissions/Storage calls File Objects happens to make internally (the blob-level mirror `GrantPermission`/`RevokePermission` calls, or Storage's own `StoreBlob`/`RetrieveBlob` events).** File Objects' own `SetFilePermissions` audit event records `subject`/`action`/`scope` — the user-facing grant, never Storage's internal `blob_ref`, which has no place in File Objects' own audit vocabulary. This was always the intended meaning of "history" in this charter but was not previously stated precisely enough to preclude the broader reading Security Steward correctly flagged as risky; it is now a bounded definition, not an open aggregation. **Required, test-backed at implementation, same as (b) and (c) below:** a test proving `GetFileHistory`/`ExportFile` never return an event whose `resource` field is a `blob_ref` — e.g. asserting the returned event set is exactly File Objects' own five mutation events and nothing pulled from Permissions' or Storage's own audit trails.
   - **Closing (b): `GetFileContent`/`ExportFile` must catch and re-wrap any error from `Storage.RetrieveBlob` into a File-Objects-level error (e.g. "content unavailable") — never pass Storage's error through verbatim.** Required, test-backed at implementation (same "merge-gate/test-verified" standard as the Art. 5 denial-audit obligation in §4).
   - **The third path — Audit's own `Query`/`Explain` surface, a separate capability File Objects doesn't control — reasoned through, not silently deferred:** Audit's own charter commits to a fail-closed cross-subject default (a subject's `Query` surfaces only events where they are the `actor`; visibility into another subject's trail requires an explicit permission grant that doesn't exist by default). The mirrored `GrantPermission`/`RevokePermission` calls' `actor` is the file object's owner (per point 3/4's grantor discipline), not the granted/revoked subject — so a subject who was granted, then revoked, access would not see that event via their own `Query` by default, only the owner would (as the actor of their own actions). This reasoning is stated here, not left implicit, but it is **not a substitute for verification**: the capability engineer must write a test proving a revoked subject cannot discover a `blob_ref` via Audit's `Query`/`Explain` surface for a version they've lost access to, before this obligation is considered met — matching how point 0's Storage `DefinePolicy` gap is a named, required-before-merge item rather than an assumption.
   - **The original race** (a `CreateVersion` grant-mirror snapshot interleaving with a concurrent `SetFilePermissions` revoke, leaving one version's blob-level grant stale) remains real and is contained by the combination of all of the above — `blob_ref` genuinely has no path back to a caller once (a), (b), and the Audit surface are closed the way this point now requires. Any future amendment exposing `blob_ref` through any File Objects RPC, audit event, error message, or Audit-surface query must first close the underlying race properly (e.g. `CreateVersion`'s grant-mirror snapshot taken inside the same lock/transaction as the grant state it copies) or accept the exposure as a new, explicitly-reviewed risk — not silently inherit this point's accepted-limitation status.

- `DeleteFileObject`'s guarantee is only as strong as Storage's `DeleteBlob` — since Storage's charter now commits to atomic deletion or crypto-shred fallback (see Storage charter §3, §6), this guarantee is real rather than aspirational. **Note the two tracked, not-yet-fixed gaps in Storage's own frozen contract** (`docs/DECISION_LOG.md`, 2026-07-17, "Storage passes merge gate"): `ExportAllBlobsRequest`/`GetStorageLocationRequest` carry no caller-identity field. File Objects' `ExportFile` must not call Storage's `ExportAllBlobs` in a way that would inherit that gap — it retrieves each version's content via the already-gated, per-blob `RetrieveBlob` instead, per point 7 above.

N/A beyond the above — no independent cryptographic or storage-boundary design in this charter.

## 7. Open questions / risks

- Version storage strategy (full copy per version vs. delta) is an implementation decision for the capability engineer, constrained by Storage's blob-level contract, not a charter-level decision. **Whichever strategy is chosen, its decision-log entry must explicitly confirm two properties hold under it** (Security Steward, 2026-07-17 re-gate): per-version `CheckPermission` gating is unaffected by delta reconstruction, and no intermediate delta blob is independently reachable or can be orphaned outside `DeleteFileObject`'s atomic teardown of every version.
- **Grant-cleanup-on-delete is not specified by this charter, and now spans two resource namespaces, not one** (Security Steward, 2026-07-17 re-gate; sharpened after §6's dual-layer design was added): Permissions' own Art. 8 promise is that grant records are "deleted when the resource is deleted," but `DeleteFileObject`'s steps (§3) don't state whether it triggers that cleanup for either the `("file_object", file_object_id)` resource or the `("blob", blob_ref)` resource of every version — and per §6's design, a lingering blob-level grant is the more concrete risk, since it's what `Storage.RetrieveBlob` itself checks. Flagged as a required decision-log entry at implementation time, not a charter-blocking gap: the capability engineer must state, and test, whether `DeleteFileObject` calls `RevokePermission` for every active grant on both the file-object resource and every version's blob resource, or documents why it deliberately doesn't (e.g. because Storage's own `DeleteBlob`/crypto-shred already makes the blob-level grant moot — the content is gone regardless of who still holds a stale grant to request it).
- How file objects interact with a future Search capability (indexing metadata without leaking encrypted content) is out of scope for this charter and flagged for when Search is chartered.
- **Added 2026-08-18, alongside `ListFileObjects`; corrected same day (Security Steward gate finding — the original text below was factually wrong, not merely conservatively scoped):** a "shared with me" file list is not built by this amendment, but **not because the needed reverse-index primitive is missing** — `Permissions.ListGrants(subject)` (`permissions.charter.md` §3) already exists, is implemented, and is network-mounted and self-scoped (`GET /v1/permissions/grants/subject`; confirmed against the real `service.go`/`http.go`, not assumed). Each returned `Grant` carries only `resource_type`/`resource_id`/`action`, not a `file_object`'s name/metadata — composing a usable "shared with me" screen means filtering `ListGrants`' output for `("file_object", *, "fileobjects.read")` and hydrating each match via `GetFileMetadata`, a small, deliberate scope exclusion of *this* amendment (a second composition to build later, entirely within File Objects' own client-facing surface), not a capability blocked on a future Permissions charter amendment. Until that composition is built, a shared file is discovered out-of-band (the sharer tells the recipient its `file_object_id`) and opened directly via `GetFileContent`/`GetFileMetadata`, both already correctly gated for a non-owner grantee.
