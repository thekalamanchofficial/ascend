# Capability Charter: Conversations

## 1. Name and one-line purpose

**Conversations** — the durable, participant-scoped message-relay and history primitive for direct communication between two identities. The platform's first actual *messaging* surface — everything chartered before this (Identity, Cryptography & Keys, Permissions, Audit, Storage, File Objects) is the trust/ownership substrate messaging is built on top of, not messaging itself.

## 2. Article 17 answer (asked first)

Yes, directly and overdue. CLAUDE.md's own framing states "communication is not messaging... messaging is only the first manifestation" — but until this charter, messaging did not exist at all: seven capabilities deep, a user can own their identity, keys, files, permissions, and audit trail, but cannot send another person a message. This capability is what turns "the most capable communication platform" from an aspiration into something a user can actually do. It increases ownership concretely: message content is end-to-end encrypted such that the platform is *structurally* incapable of reading it (see §6), not merely policy-forbidden from doing so — the strongest form Art. 1/7 can take.

## 3. Interface

**Scope of this first freeze, stated up front:** direct (exactly two-participant) conversations only. Group conversations are a real, anticipated future extension (§7) requiring a different cryptographic scheme (sender-keys, layered on top of what this charter establishes) and Permissions integration for membership changes — deliberately not attempted here, the same way File Objects' first freeze deliberately excluded "shared with me" rather than build it half-right.

**Caller-identity binding — stated once here, applying to every RPC below (added 2026-08-19, Constitution Warden gate finding, first draft: this was entirely unstated):** every RPC below requires HTTP-level binding of its identity-bearing field(s) (`creator`, `sender`, `requesting_subject`) to the network-verified caller identity — resolved via Session/Request Authentication's session validation, the same `requireVerifiedCaller`-shaped middleware every gated route in this codebase already uses — checked **before** any handler logic runs, exactly the two-layer discipline (HTTP-level caller match + service-level decision) File Objects' charter was required to state explicitly across two separate gate rounds (`ListFileObjects`, `ListFileAccess`). Rejection on mismatch is a 403, and (per Art. 5, below) audited. This is not optional per-RPC framing — it is a blanket requirement on this capability's entire surface, stated once so no individual RPC bullet below needs to repeat it, mirroring how File Objects' §3 closing paragraph states it once for all ten of that capability's RPCs rather than per-bullet.

**Exposes:**
- `CreateConversation(creator, participant) -> conversation_id, created_at` — establishes a direct conversation between exactly two identity_refs. `creator` must equal the verified caller (binding above) — this is what closes the specific enumeration risk Constitution Warden traced: without it, an unrelated caller could probe arbitrary `(creator, participant)` pairs to learn whether two strangers already have a conversation, given the idempotent-by-pair behavior below; with it, a caller can only ever create or probe for a conversation they themselves are a party to, which reveals nothing about anyone else's relationships. Idempotent by pair: calling this again for a pair that already has a conversation returns the existing `conversation_id` rather than creating a duplicate — a real UX quality bar (Art. 12), not just a technicality, since silently duplicating conversations would be confusing and would fragment message history across two threads. Bootstraps Permissions access for both participants (see Consumes, below) — mirroring `CreateFileObject`'s own bootstrap-grant pattern.
- `SendMessage(conversation_id, sender, ciphertext, session_establishment_payload?) -> message_id, sent_at` — `ciphertext` is opaque bytes, already encrypted client-side by Cryptography & Keys before this call is ever made; this capability's backend never decrypts, never attempts to, and structurally cannot (see §6). `session_establishment_payload` is optional opaque bytes carrying the sender's ephemeral public key contribution for the X3DH-style handshake (Cryptography & Keys charter §3), present only on a session-establishing or session-re-establishing message; Conversations relays it byte-for-byte without ever interpreting it, the same opacity discipline File Objects already applies to `blob_ref`. **Authorization, stated explicitly (Constitution Warden gate finding, first draft: this was entirely unstated) — two checks, neither optional:** (1) HTTP-level, `sender == caller` (the blanket binding above); (2) `sender` must hold the conversation's Permissions grant (delegated to `Permissions.CheckPermission`, see Consumes) — a caller who is authenticated but not a participant of `conversation_id` is rejected, audited, and told nothing distinguishing "you're not a participant" from "this conversation doesn't exist" (same discipline as the read RPCs below).
- `ListMessages(conversation_id, requesting_subject, before_message_id?, limit) -> [message], has_more` — ascending chronological order, cursor-paginated from day one (**deliberately not following the "unbounded, accepted for now" precedent** `ListFileObjects`/`ListDevices`/`ListActiveSessions`/`ListVersions` share — a long-running conversation can genuinely reach message volumes those RPCs' resource counts never will; this is a difference in kind, not a stricter opinion about the same risk, and should not be read as second-guessing those prior acceptances). Each `message`: `message_id`, `sender`, `ciphertext`, `session_establishment_payload` (if present), `sent_at`. **Gated to conversation participants only, via `Permissions.CheckPermission`, with the identical enumeration-oracle-safe indistinguishability requirement `GetConversation` carries below — stated explicitly here too (Constitution Warden gate finding, first draft: this charter stated the requirement for `GetConversation` but not `ListMessages`, despite grouping both under one denial-audit obligation in §4) — required and test-backed at implementation: a nonexistent `conversation_id` and an existing-but-not-a-participant `conversation_id` must produce byte-for-byte identical response status/body and identical audit event shape, the same standard `ListFileAccess` was held to.**
- `ListConversations(requesting_subject) -> [conversation_summary]` — self-only, mirroring `ListFileObjects`/`ListGrantsForSubject`'s established self-scoped-inventory pattern. Each summary: `conversation_id`, `other_participant`, `created_at`, `last_message_at` (for inbox ordering — **derived at query time as `MAX(sent_at)` over the conversation's stored messages, never a separately persisted/denormalized field**, per Art. 8 below). **Deliberately no message preview/snippet field** — the server never has plaintext to preview; an inbox preview is necessarily a client-side concern (the mobile app decrypts the last message it already has locally and caches its own preview), not something this contract can offer. **A `conversation_summary` with `created_at` set but no messages yet (a `CreateConversation`-succeeded/`SendMessage`-failed partial-failure gap, not a normal state — Experience Guardian gate finding, round 2) must be omitted from this RPC's results entirely, indistinguishable from never having called `CreateConversation` at all** — since `CreateConversation` is idempotent by pair (above), a client recovering from a crash between the two calls simply retries `SendMessage` against the same, already-existing `conversation_id`; the row becomes normally visible the moment a message actually lands, and never needs its own "empty conversation" UI state.
- `GetConversation(conversation_id, requesting_subject) -> {conversation_id, participants, created_at}` — participant-only gated, using the same nonexistent-vs-not-a-participant indistinguishability discipline `ListFileAccess` established (§6) — a conversation ID guess must not be distinguishable from "you're not in that conversation."
- `ExportConversation(conversation_id, requesting_subject) -> ciphertext_bundle, format_version` — **restored 2026-08-19 (Constitution Warden gate finding, first draft: the "no export RPC" design left Art. 9 as an unoperationalized assertion rather than a chartered deliverable) — a real, participant-gated RPC (identical authorization/enumeration discipline as `ListMessages`), but honestly, narrowly scoped: it returns the conversation's stored data byte-for-byte as this capability actually holds it** — every message's `ciphertext`/`session_establishment_payload`/`sender`/`sent_at`, plus conversation metadata — **not** a promise that the bundle is decryptable. Because of the ratchet's forward-secrecy design (Cryptography & Keys charter §6), a message's decryption key is not durably retained after use; whether this bundle can be decrypted later depends entirely on whatever key/ratchet state the requester's *own device* still holds, which this capability has no visibility into and makes no claim about. This is "your own stored bytes, verifiably complete and unaltered" (a real, mechanically-checkable Art. 9 deliverable — see §4) — genuinely useful for backup/portability/leaving the platform with your raw data intact — layered underneath, not instead of, the separate, complementary, **recommended** user-facing export: a local, on-device bundling of messages the client has *already decrypted and cached* (§4), which is the only place a guaranteed-readable transcript can exist at all. Both are named explicitly so neither is mistaken for the other's guarantee.

**Consumes:**
- **Identity** — participant `identity_ref`s are opaque references, resolved lazily at read time only when a display-ready identity is needed, matching every other capability's established pattern. This charter's backend never imports Identity's internals.
- **Cryptography & Keys** — consumed **exclusively by the mobile client**, never by this capability's backend service. This is worth stating explicitly because it's a structural first for a backend capability in this codebase: every prior backend capability (Identity, Permissions, Audit, Storage, File Objects) is a normal Go service with real, if narrow, in-process dependencies on its siblings. Conversations' Go backend has **zero** cryptographic capability of its own, by design — it is a dumb, encrypted-bytes relay, which is what makes the "platform cannot read your messages" claim a structural fact rather than a policy promise (§6).
- **Audit / Explainability** — `CreateConversation` and `SendMessage` both emit audit events; per Art. 8, the event records that a message was sent, by whom, in which conversation, when — **never** the ciphertext, never the `session_establishment_payload`, matching Cryptography & Keys' own established audit discipline ("the operation succeeding/failing, never the key material itself").
- **Permissions — corrected 2026-08-19 (Constitution Warden gate finding, first draft: excluding Permissions here didn't survive the same scrutiny File Objects' own, superficially simpler exceptions received) — consumed, following File Objects' own established pattern exactly rather than hand-rolling a parallel participant check.** Registers a `"conversation"` Permissions resource type (single action, `"conversations.access"` — deliberately just one action, not File Objects' `fileobjects.read`/`fileobjects.write` split, since v1's fixed two-party model has no read-only-vs-write-only distinction to express) with a deny-by-default policy at this capability's own construction, mirroring File Objects/Storage's `DefinePolicy`-at-construction discipline (`file-objects.charter.md` §6 point 0). `CreateConversation` bootstraps both participants' access via `Permissions.GrantPermission`: the creator's grant first (establishing implicit ownership per Permissions' first-grantor rule), then the named participant's grant — mirroring `CreateFileObject`'s own two-grant bootstrap exactly (`file-objects.charter.md` §6 point 2). Every other RPC's participant check delegates to `Permissions.CheckPermission` rather than this capability inventing its own parallel decision. This also directly sets up the eventual group-conversation extension (§7) as "grant more subjects," not a retrofit — the concern File Objects itself was built to avoid.
- **Storage — deliberately NOT consumed.** Messages persist in this capability's own store directly (mirroring Identity/Permissions/Audit's own direct-persistence pattern), not routed through Storage's blob substrate — messages are small, high-volume, structured rows, not the large-opaque-blob shape Storage/File Objects exist for.
- **File Objects — not consumed by any RPC in this freeze, named here as the intended future composition point.** Message attachments, when built, should compose File Objects' existing `file_object_id` (shared to the conversation's participants via its existing `SetFilePermissions`) — not a new attachment primitive invented inside this capability. Stated explicitly so a future engineer doesn't reinvent file handling here (Art. 4, 10, 16).

## 4. Constitutional obligations

- **Art. 1 (ownership):** message content is owned by its participants in the strongest available sense — the platform is structurally unable to read it (§6), not merely forbidden to.
- **Art. 2 (files first-class):** N/A this freeze — no file object is created or owned by this capability; attachments are a future composition against File Objects' own already-first-class file objects, not a parallel concept here.
- **Art. 5 (explainability):** `CreateConversation`/`SendMessage` are marked mutating and emit audit events (actor, action, `conversation_id`, timestamp) — content-free per the Audit-consumption note above. Read RPCs (`ListMessages`, `ListConversations`, `GetConversation`, `ExportConversation`) are not individually audited on success, matching the established precedent (Session/Request Auth's `ValidateSession`, File Objects' shared `fileobjects.read` path) — but **every rejection of `GetConversation`/`ListMessages`/`ExportConversation`/`SendMessage` for a non-participant must be audited**, mirroring `ListFileAccess`'s required enumeration-oracle-safe denial audit. **Naming `conversation_id` in these denial events, reasoned through explicitly (Security Steward gate finding, first draft: this parity to `ListFileAccess` was asserted, not argued) rather than assumed safe by analogy:** a conversation ID inherently correlates *two* identities, unlike a file's single-owner shape, so this needs its own argument, not a borrowed one. The argument: correlating a bare `conversation_id` to its actual two participants requires a *separate*, independently-gated call (`GetConversation`), which a non-participant cannot make successfully — Audit's own `Query` is actor-scoped self-only by default (that charter's §6/§7), so a would-be attacker's own audit trail records only their own denied attempts, never the participants of conversations they don't belong to. Naming `conversation_id` in a denial event therefore adds no correlation capability beyond what a successful `GetConversation` call would already gate — the same reasoning `ListFileAccess`'s charter makes for naming `file_object_id`, now actually walked through for this capability's two-identity shape rather than assumed to transfer.
- **Art. 7 (security never reduces ownership):** no plaintext ever crosses to this capability's backend under any convenience justification — a future "let's add spam filtering" or "let's index messages for search" proposal is a charter amendment requiring Security Steward veto review, explicitly, the same standing rule Cryptography & Keys' own charter states for key escrow. This capability's backend has no code path that could decrypt even if compromised (§6).
- **Art. 8 (privacy) — data manifest:** `Conversation`: `conversation_id`, two `participant` `identity_ref`s, `created_at` — purpose: routing and inbox display, unavoidable metadata. `Message`: `message_id`, `conversation_id`, `sender` `identity_ref`, `ciphertext` (opaque, unreadable), `sent_at`, optional `session_establishment_payload` (opaque) — purpose: delivery and ordering; the platform cannot and does not attempt to minimize `ciphertext`'s size/shape further, since doing so would require understanding content it must never understand. `last_message_at` (on `conversation_summary`) is **derived at query time, never persisted** (§3) — not a separate collected field. `ExportConversation`'s response reuses exactly these same already-manifested `Message`/`Conversation` fields — no new collection. No other fields. No read receipts, no delivery receipts, no typing indicators, no message previews are collected or derived server-side in this freeze (§7). **`CreateConversation`'s `participant` field is never validated against Identity's existence (stated explicitly, Security Steward gate finding, first draft: left silent) — it is treated as a fully opaque reference, exactly like every other `identity_ref` this charter and every prior capability's charter handle.** A `participant` value that names no real identity simply results in a conversation no one else will ever authenticate as. This is the deliberate design, not an oversight: validating existence here would create a direct platform-wide identity-enumeration oracle (distinguishable "exists"/"doesn't exist" responses to an arbitrary `identity_ref` guess) with no offsetting benefit, since `CreateConversation` is already bound to `creator == caller` (§3) and needs no cross-check against `participant` to be safe.
- **Art. 9 (export):** satisfied at two complementary layers, both now concrete deliverables, not assertions (Constitution Warden and Security Steward gate findings, first draft — corrected below). **Layer one, this capability's own:** `ExportConversation` (§3) — a real RPC, mechanically satisfying `check-export-paths.sh`'s requirement via a genuine `ExportConversation`/`ExportMessage` Go function pair in `internal/conversations`, each with its own `*_export_test.go`, honestly scoped to "your own stored bytes, verifiably complete," not a decryptability promise. **Layer two, the mobile client's, now a required, test-backed obligation rather than an assumption embedded in a justification paragraph:** the mobile client's local message-history store — the *only* place a guaranteed-readable transcript can exist at all, given forward secrecy (§3) — **must** use Cryptography & Keys' `SecureLocalStore`/`SecureLocalRetrieve` (that charter's §3), the same at-rest guarantee every other locally-cached sensitive value in this codebase uses; a capability engineer implementing local message history in plain `AsyncStorage`/unencrypted SQLite does not satisfy this charter. The on-device export itself must produce a documented, portable, self-contained bundle (mirroring `ExportFile`'s "complete artifact" bar) and require an explicit user-confirmation step before producing it, mirroring `ExportKeyMaterial`'s `user_confirmation` gate (`cryptography-and-keys.charter.md` §3) — not a silent background operation, given the sensitivity of a full plaintext transcript leaving the app's own encrypted-at-rest boundary onto, e.g., a shared file.
- **Art. 10 (modularity):** composes Identity + Permissions + Audit, server-side; Cryptography & Keys is consumed exclusively client-side, never server-side. Permissions is now the sole source of every participant-access decision (§3's `Consumes` correction) — this capability holds no parallel ACL of its own.
- **Art. 16 (consistency):** opaque-reference pattern for `identity_ref` matches Identity/Permissions/Audit/File Objects exactly, now including the explicit no-existence-validation statement above; attachments (when built) compose File Objects rather than reinventing; the enumeration-oracle-safe denial discipline matches `ListFileAccess`'s established precedent, now argued through rather than assumed for this capability's own two-identity correlation shape; the `"conversation"` resource-type/bootstrap-grant design mirrors File Objects' `"file_object"` pattern exactly (§3).

## 5. Experience budget

Zero-config default: starting a conversation with someone whose `identity_ref` you already have should be exactly as simple as File Objects' existing share flow (paste `identity_ref`, tap "Message") — no group setup, no channel configuration, no settings screen required before the first message can be sent.

**Resolved 2026-08-19 (Experience Guardian gate finding, first draft — the two-RPC interface shape was left to collapse into "one tap" without a stated mechanism):** `CreateConversation` is called **lazily**, only at the moment the user sends their first real message to a given `identity_ref` — never merely on entering/pasting the identity_ref or tapping "Message." Concretely: tapping "Message" opens a compose view for that `identity_ref` with no conversation yet created; only the act of actually sending calls `CreateConversation` (idempotent-by-pair, per §3) immediately followed by `SendMessage`, both invisible plumbing behind the single user-perceived action of "hit send." **This structurally eliminates the abandoned-empty-conversation edge case** (a user who pastes an identity_ref, taps "Message," and backs out before typing anything) rather than requiring a special empty-state UI treatment for it: if send never happens, `CreateConversation` never happens, and nothing appears in `ListConversations`. No conversation-level record exists until a message actually exists — matching Storage/File Objects' own precedent that persistence follows a real user action, not an intermediate navigation step. Compose-view state itself (whatever's typed but not yet sent) is transient client-side UI state, not this capability's concern at all.

"Transparent when curious": Cryptography & Keys' charter §6 already committed to "a passive, discoverable indicator (e.g. a changed-key badge on the conversation), never an interrupting modal" for key rotation — this is the first capability where that commitment becomes a real, renderable thing rather than a forward-looking promise, and the mobile implementation must actually deliver it, not silently drop it because "no capability consumed it yet" is no longer true.

"Powerful when needed": N/A / explicitly deferred this freeze — no message search, no reactions, no threading, no scheduled sends. Keeping v1 minimal is itself the correct choice (Art. 13: an excellent minimal default beats a half-built rich one), not a corner cut silently.

**Must be disclosed plainly, not hidden, per Art. 12** (Experience Guardian should judge whether the mobile implementation actually surfaces these, not just whether this charter names them):
1. No message history before a device was added to the identity — inherited from Cryptography & Keys §7's already-disclosed multi-device-sync gap. **Resolved 2026-08-19 (Experience Guardian gate finding, first draft — stated only the desired outcome, not a mechanism):** because §3 deliberately has no server-side message preview, a fresh device's inbox rows carry no history *and* no preview simultaneously — indistinguishable, without a specific affordance, from "you have zero conversations ever." Concrete mechanism required of the mobile implementation: for each conversation returned by `ListConversations`, compare that conversation's `created_at` against *this device's own* `added_at_unix` (already available from Identity's `Device` record, per `identity.charter.md`) — whenever `conversation.created_at < this_device.added_at_unix`, render a distinct, explicit subtitle/banner on that row (e.g. "Messages from before this device was added aren't shown here") rather than the normal empty-conversation state. This is a real, checkable comparison against data both capabilities already expose, not a new field either needs to add.
2. No group conversations yet.
3. Starting a conversation requires already knowing the other party's `identity_ref` — no search/discovery exists on the platform yet (same standing limitation `ShareFileScreen` already discloses for file sharing).

## 6. Threat model

Maximally in scope — this is the platform's first true end-to-end-encrypted, two-party, real-time-adjacent surface.

- **The central claim, stated precisely:** this capability's backend must be *structurally* incapable of reading message content, not merely policy-forbidden. Concretely: the Go service has no dependency, direct or transitive, on any decryption capability; `ciphertext` fields are stored and relayed as opaque bytes; even a fully compromised server (database dump, compromised deploy, malicious operator) yields ciphertext only, mirroring Cryptography & Keys' own "server compromise scenario" commitment (that charter's §6) applied here for the first time to real message content rather than key material.
- **Named, blocking prerequisite — not to be silently rediscovered, per Cryptography & Keys charter §7's own explicit instruction to "check this item first" — corrected 2026-08-19 (Security Steward gate finding, first draft: the proposed fix shape was cryptographically broken, not just unspecified).** `Cryptography & Keys.DeriveSharedSecret` as currently frozen only implements the *initiating* party's half of an X3DH-style handshake (a locally generated ephemeral keypair, used once and discarded, mixed into the root key). This charter's first draft sketched the missing responder-side primitive as the responder simply combining their own long-term static private key with the initiator's public keys — **red-teamed at this gate and found broken: reproduces the correct root key algebraically, but contributes no fresh, single-use secret on the responder's side, meaning a future compromise of the responder's long-term static key would retroactively decrypt every past session that key ever completed as responder.** This is not a minor gap; it is the same class of forward-secrecy defect Cryptography & Keys' own implementation gate already vetoed once for the *initiator's* side (`docs/DECISION_LOG.md`, 2026-07-16), now relocated to the responder's role. **The correct fix requires the responder to contribute a genuine fresh, one-time private value that is destroyed after use — real X3DH's answer is a pre-published, signed, one-time-prekey bundle the responder deletes upon first use** (preserving today's async, single-message-completion property, at the cost of new operational machinery: prekey publishing, rotation, signing against substitution, deletion-after-use discipline, and a defined fallback when prekeys run out) **— or, alternatively, a live round-trip handshake where the responder generates and returns their own fresh ephemeral public key before completion**, which would change `SendMessage`'s current "initiator completes unilaterally from message 1" property into something requiring at least one reply before the initiator's own session is fully established. **Neither option is a simple addition to `DeriveSharedSecret`'s existing three-argument shape, and this charter does not pick between them** — that choice belongs to the Cryptography & Keys amendment itself, drafted and gated on its own merits (including a fresh Security Steward review of whichever construction is chosen), not decided as a side effect of chartering Conversations. This charter's core `SendMessage`/decrypt path remains a hard blocker on that amendment landing, mirroring File Objects' "may not merge until" precedent (`file-objects.charter.md` §6 point 0) — but is now frozen with the *real* shape of the problem named, not a sketch that would have shipped a silent regression if implemented as originally drafted.
- **`session_establishment_payload`'s framing may need to become bidirectional, flagged as open pending the Crypto amendment above (Security Steward gate finding):** if the eventual fix is a live round-trip handshake, the responder's first reply may also need to carry a payload of its own (their fresh ephemeral public key), not just the initiator's first message — this charter's current one-directional wording ("present only on a session-establishing message... from the sender") is provisional, not settled, and should not be read as foreclosing that shape. `SendMessage`'s wire contract (`session_establishment_payload` as opaque optional bytes on any message, sender-agnostic) already accommodates either resolution without a further wire-contract change — only the *usage pattern* is open, not the field itself.
- **Enumeration:** `GetConversation`/`ListMessages`/`ExportConversation`/`SendMessage` for a non-participant must be indistinguishable between "conversation doesn't exist" and "you're not a participant" — same discipline `ListFileAccess` was required to prove test-backed, applied here from the start rather than discovered as a gate finding a second time. `CreateConversation` deliberately does not validate `participant`'s existence at all (§4) — the correct closure of the *adjacent* enumeration risk (learning whether an arbitrary `identity_ref` is registered), rather than something this bullet's indistinguishability requirement needs to additionally cover.
- **`session_establishment_payload` integrity:** the server relays it opaquely and makes no security decision about its contents — if tampered in transit (defense-in-depth: TLS already protects this, but the E2E design must not *depend* on transport security) or corrupted, decryption simply fails loudly client-side; this is a property of the ratchet construction (Cryptography & Keys' responsibility), not something this capability's backend needs to validate or can meaningfully validate.
- **Message ordering/integrity:** server-assigned `message_id`/`sent_at` provide delivery ordering; cryptographic authenticity/integrity of content and replay/out-of-order detection are properties of the ratchet construction itself (each message's AEAD tag and ratchet header), not something this capability's backend adds or could add without seeing plaintext. This capability's obligation is narrower and mechanical: never reorder, never silently drop a successfully-stored message.
- **Local plaintext at rest (mobile client):** the local message-history store this capability's Art. 9 design depends on (§4) must go through Cryptography & Keys' `SecureLocalStore`, not an ad hoc local database — a plain, unencrypted local store would mean this capability's on-device design created *weaker* at-rest protection for message content than a naive server-side ciphertext store would have had, exactly the kind of new risk a "just keep it local" answer could otherwise introduce silently.
- **Denial-of-service / spam / abuse (rate limiting on `SendMessage`, blocking, reporting):** explicitly out of scope for this first freeze, named rather than silently absent (§7).

## 7. Open questions / risks

- **Cryptography & Keys responder-side completion primitive — hard blocker (§6), real design cost, not yet resolved.** Recommended immediate next step after this charter gates: draft and gate the Cryptography & Keys amendment, choosing explicitly between a prekey-bundle mechanism or a live round-trip handshake (§6 lays out both, with their respective costs), before Conversations' capability engineer begins the encrypt/decrypt path — the same sequencing File Objects/Storage already established as precedent, now with the actual cryptographic requirement correctly named rather than a broken sketch.
- **Group conversations** — real, anticipated, deliberately deferred. Will need: a sender-keys-style (or equivalent) group encryption scheme layered on this charter's pairwise foundation, and **extending this charter's now-adopted Permissions-backed grant model to multiple subjects per conversation** (no longer a retrofit onto a hand-rolled fixed-two-party check, since Permissions already owns this decision from v1 — see §3's Consumes correction).
- **Multi-device history sync** — inherited limitation from Cryptography & Keys §7, not solved here, must be disclosed in the UI (§5) rather than presented as a bug.
- **Discovery/contacts** — no search exists; starting a conversation requires out-of-band `identity_ref` exchange, the same standing platform limitation File Objects' sharing flow already carries. Whether a minimal Contacts/Discovery capability should be chartered next is a decision routed back to the Chief Architect, not resolved here.
- **Read receipts / delivery receipts / typing indicators** — deliberately excluded from this freeze's data manifest (§4). If added later, Art. 8's "privacy is the default" strongly suggests read-status-visible-to-sender should default off/opt-in, not on — flagged for whoever charters that extension, not decided here.
- **Message attachments** — deferred; compose File Objects when built (§3), not a new primitive.
- **Real-time delivery transport** (push notification, polling, websocket) — this charter defines the durable storage/relay contract only; how a client learns a new message arrived without polling `ListMessages` repeatedly is an implementation-time transport decision, not a charter-level one, the same way no other capability's charter mandates its own polling cadence.
- **Creator/participant grant asymmetry, flagged non-blocking (Constitution Warden gate finding, round 2):** reusing File Objects' first-grantor-implicit-ownership pattern for `CreateConversation`'s bootstrap grants means the creator, not both parties symmetrically, holds Permissions' notion of "ownership" over the conversation resource — meaning the creator alone could technically revoke the other participant's access, which doesn't match a two-person conversation's intuitively symmetric/joint nature. This RPC set exposes no `RevokePermission`-equivalent action in this freeze, so the asymmetry has no user-visible consequence *today* — flagged here so it isn't silently inherited if a future amendment adds one, rather than solved now.
- **`SendMessage.ciphertext` optionality — resolved 2026-08-19, cross-referenced here per Constitution Warden's finding on the Cryptography & Keys amendment gate (was: "flagged non-blocking, routed to the future Cryptography & Keys amendment").** That amendment chose a prekey-bundle construction specifically because the initiator can complete their full derivation locally from the responder's already-published bundle *before* ever contacting them — so real content rides the first message, and no handshake-only message shape is ever required. `ciphertext` remains mandatory on every `SendMessage` call, unchanged from this charter's original freeze. See `cryptography-and-keys.charter.md` §3/§7 for the resolved mechanism.
