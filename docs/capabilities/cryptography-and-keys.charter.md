# Capability Charter: Cryptography & Keys

## 1. Name and one-line purpose

**Cryptography & Keys** — end-to-end encryption primitives, user-owned key generation and storage, the substrate every other security-sensitive capability builds on.

## 2. Article 17 answer (asked first)

Yes, foundationally. Ownership of communication is meaningless if the platform (or anyone who compromises it) can read the content or impersonate the user. This capability is what makes "user-owned keys" (Art. 7) an engineering fact rather than a marketing claim.

## 3. Interface

**Exposes:**
- `GenerateIdentityKeyMaterial() -> (public_key, private_key_handle, recovery_phrase)` — the single generation event for a root identity key pair. The recovery phrase is a mnemonic encoding of the seed that **deterministically derives** the private key; `public_key`/`private_key_handle` are not a second, independently-generated secret. There is exactly one root secret, with two representations: the opaque on-device handle and the human-writable phrase.
- `GenerateKeyPair()` — used for all *non-recovery-bearing* key pairs a capability needs (e.g. per-device session keys). Private key material never leaves this capability's boundary in plaintext; consumers receive an opaque handle backed by OS keychain / secure enclave where available, or an encrypted local store otherwise.
- `Encrypt(recipient_public_keys, plaintext) -> ciphertext`, `Decrypt(private_key_handle, ciphertext) -> plaintext` — E2E primitives used by Messaging, File Objects, etc.
- `DeriveSharedSecret(their_identity_signing_public_key, their_prekey_bundle) -> {shared_secret, my_ephemeral_public_key}` — the **initiating** party's half of session/channel key agreement. **Amended 2026-08-19 (Conversations charter §6/§7's named blocking prerequisite — see Decision Log):** signature updated from a bare public key to `their_prekey_bundle` (the responder's published `signed_prekey` + optional `one_time_prekey`, fetched by the caller from wherever those are published — see `GeneratePrekeyBundle` below; this capability neither publishes nor fetches bundles itself, see Consumes). **The exact derivation is specified below, not left to implementation discretion (Security Steward gate finding, round 1: this is the load-bearing security property of the amendment, not a commodity substitution the original charter's §7 "exact algorithm choices are an implementation decision" precedent covers).** Returns the caller's own freshly generated, single-use ephemeral public key alongside the derived secret, so the caller's transport layer (e.g. Conversations' `session_establishment_payload`) can carry it to the responder — this capability has no transport of its own and makes no assumption about how that value reaches its destination. **`their_identity_signing_public_key` — corrected 2026-08-21 (key-separation fix, round 2: an earlier pass named this parameter `their_identity_dh_public_key`, which is wrong — the DH-capable key now lives inside `their_prekey_bundle` itself, see below).** This top-level parameter is the responder's Ed25519 *signing* public key (sourced from Identity's `ResolveIdentity`, unchanged by this fix) — the trusted verification anchor for both `their_prekey_bundle.signed_prekey.signature` and `their_prekey_bundle.identity_dh_public_key_signature`, checked before either is used in any DH term.
- `GeneratePrekeyBundle(one_time_prekey_count) -> {identity_dh_public_key, identity_dh_public_key_signature, signed_prekey: {prekey_id, public_key, signature, created_at}, one_time_prekeys: [{prekey_id, public_key}]}` — **added 2026-08-19, closing this amendment's core gap (see §6/§7):** generates a fresh medium-term signed prekey (its public key signed by the identity's long-term signing key, preventing a malicious server from substituting a fake one) plus `one_time_prekey_count` fresh single-use one-time prekeys. All private halves are stored locally via `SecureLocalStore`, indexed by `prekey_id` so `CompleteSharedSecret` can retrieve them later; **only the public halves + signature are returned**, for whatever capability publishes per-identity/per-device public key material to publish on this device's behalf (this capability has no network component of its own — see Consumes). Must be called periodically (rotation for the signed prekey, replenishment for one-time prekeys as they're consumed) — exact cadence/thresholds are an implementation decision (§7), not charter-mandated. **`identity_dh_public_key_signature` — added 2026-08-21 (key-separation fix, round 2, Security Steward finding):** the identity's Ed25519 signing key also signs `identity_dh_public_key` in this same call, the same discipline `signed_prekey` already receives — an unsigned DH-capable identity key would be a substitution surface a compromised publish/fetch path could exploit (see §6's new threat-model bullet for the bounded-impact analysis).
- `CompleteSharedSecret(their_identity_dh_public_key, their_identity_signing_public_key, their_identity_dh_public_key_signature, their_ephemeral_public_key, my_signed_prekey_id, my_one_time_prekey_id?) -> shared_secret` — **added 2026-08-19, the responder's half of session/channel key agreement, structurally absent before this amendment (Conversations charter's named blocking prerequisite).** Looks up the referenced local private prekey material (generated and stored by `GeneratePrekeyBundle`) and performs the responder's side of the identical derivation specified below, arriving at the same shared secret `DeriveSharedSecret` computed. **The forward-secrecy-critical step, stated as a hard requirement, not an implementation nicety: the referenced one-time prekey's private key must be atomically consumed and permanently deleted (§6's "Atomic one-time-prekey consumption" bullet — not merely "before this function returns," which is insufficient under concurrency).** If `my_one_time_prekey_id` is absent (the initiator's fetched bundle had no one-time prekey available — see §6 exhaustion handling), the resulting session has a stated, disclosed weaker guarantee for that specific session, never silently treated as equivalent, and must emit the required audit event named in §6. **`their_identity_signing_public_key`/`their_identity_dh_public_key_signature` — added 2026-08-21, round 4 (Security Steward gate finding: a distinct threat class, not covered by the DH-term-isolation reasoning that governs the rest of §6 — see that section's new "identity impersonation via wholesale fabrication" bullet).** `their_identity_dh_public_key` must be verified against `their_identity_signing_public_key` via `their_identity_dh_public_key_signature` before use in any DH term — hard abort on failure (reusing `signed_prekey_signature_invalid`, same discipline as every other signature check in this contract).

  **The required derivation, specified exactly (Security Steward gate finding, round 1: the charter previously asserted this "composes cleanly" without ever naming which key pairs combine — this is the actual security property, not an interchangeable detail) — the standard X3DH construction, not a variant:** given the initiator's identity keypair `IK_A` and fresh ephemeral keypair `EK_A`, and the responder's published identity key `IK_B`, signed prekey `SPK_B`, and (if available) one-time prekey `OPK_B`:
  - `DH1 = DH(IK_A, SPK_B)`
  - `DH2 = DH(EK_A, IK_B)`
  - `DH3 = DH(EK_A, SPK_B)`
  - `DH4 = DH(EK_A, OPK_B)` — only when a one-time prekey was available and used
  - `shared_secret = HKDF(DH1 || DH2 || DH3 [|| DH4], context)`, where `context` is a **fixed, distinct literal string per case** ("x3dh-4term-with-otp" vs. "x3dh-3term-signed-prekey-only") mixed into the HKDF info parameter — **required domain separation, not optional hygiene:** it ensures a 3-term (exhaustion-fallback) derivation and a 4-term (full) derivation can never be confused with each other or with any other construction this capability might use elsewhere, even if inputs overlapped.

  **`IK_A`/`IK_B` MUST be a genuinely separate, DH-only key from the identity's Ed25519 signing key — required, corrected 2026-08-21 (Security Steward implementation-merge-gate veto, real finding, not a style preference).** A first implementation reused the identity's existing Ed25519 signing scalar for `IK_A`/`IK_B` via a birational Ed25519→X25519 conversion, justified by citing Signal's own XEdDSA construction as precedent. Independently re-verified by Security Steward (spawning an ephemeral crypto specialist for the specific dual-use question): the conversion itself is mathematically sound (confirmed via an independent standalone re-derivation, not the implementation's own unchecked-in script) and DH commutativity genuinely holds across it — **but the underlying design was unsafe regardless, and the XEdDSA citation was factually inaccurate.** Reusing one long-term scalar for both standard EdDSA signing *and* raw X25519 DH against network-facing, attacker-influenced public values (every `DeriveSharedSecret`/`CompleteSharedSecret` call exposes the identity scalar to a counterparty-chosen public key) violates NIST SP 800-57's "one key, one purpose" key-separation principle against this platform's single highest-blast-radius key — a real, citable standard, not house style. XEdDSA is not a counter-example: it starts from an X25519 keypair and defines a *custom* signing algorithm with its own compensating nonce-derivation engineering specifically to make that direction of dual-use defensible; this implementation did the mirror-image thing (Ed25519 → converted-to-X25519, with *unmodified* stock EdDSA used elsewhere) with none of that compensating engineering — the precedent doesn't actually transfer.

  **Required fix:** derive a genuinely separate DH-capable scalar deterministically from the same recovery-phrase seed via a domain-separated KDF — `dh_scalar = HKDF(seed, "ascend-x3dh-dh-key")`, `IK_A`/`IK_B`'s public form = `X25519.getPublicKey(dh_scalar)` — never the signing scalar or a birational conversion of it. **`seed` precisely defined, required (Security Steward gate finding, round 2 on this fix itself — the term was previously used loosely enough to admit an unsafe reading): `seed` means the raw, recovery-phrase-derived bytes fed into Ed25519 key generation, taken *before* RFC 8032's internal SHA-512 hash-and-clamp step — never the already-derived/clamped Ed25519 signing scalar. Deriving `dh_scalar` from the clamped signing scalar instead would make it trivially recomputable by anyone who ever recovers that scalar alone (e.g. via a future EdDSA-specific fault/nonce/side-channel attack that leaks the scalar without leaking the original seed), silently reintroducing the same cross-key-compromise coupling this fix exists to remove, just via a different mechanism than the original birational conversion.** This preserves the charter's original "one root secret, multiple deterministic representations" framing (§3's `GenerateIdentityKeyMaterial` bullet) — no new secret to generate, back up, or lose — while genuinely separating the signing and DH key-usage domains, closing the NIST SP 800-57 violation. **Wire-level consequence, not contained within this capability alone (see the companion Identity charter amendment, `identity.charter.md` §3, gated together with this fix):** `GeneratePrekeyBundleResponse.identity_dh_public_key` and `DeriveSharedSecretRequest`/`CompleteSharedSecretRequest`'s `their_identity_dh_public_key` now carry this X25519 DH-capable public key, **not** the Ed25519 signing public key `GenerateIdentityKeyMaterial`/`ResolveIdentity` return — a real semantic distinction between "the identity's signing key" and "the identity's X3DH key," both deterministically derived from one seed but never interchangeable at the wire level. Since Identity has no way to independently derive this new public value (it requires the private seed), it must be published explicitly via `PublishPrekeyBundle` alongside the signed prekey — see the companion amendment for the specific field added there.
  - `CompleteSharedSecret` computes the identical four (or three) DH terms from the responder's side — `DH(SPK_B_private, IK_A_public)` equals `DH(IK_A_private, SPK_B_public)` by Diffie-Hellman commutativity, and so on for each term — arriving at the same `shared_secret` without either party ever transmitting a private key.
  - **This explicitly supersedes, not extends, the pre-amendment construction** (`ratchet.ts`'s current `staticStaticDh`/`ephemeralStaticDh` two-term scheme) — `DH2` above subsumes what `ephemeralStaticDh` computed; `DH1`/`DH3`/`DH4` are new terms with no prior equivalent. The capability engineer implementing this amendment must rewrite `initRatchetSession`'s DH-term structure to the four-term (or three-term fallback) construction above, not reparameterize the existing two-term one — stated explicitly so this isn't handed to a future engineer as an ambiguous "make DeriveSharedSecret take a bundle now" sketch a second time.
- `EncryptMessage(shared_secret_handle, plaintext) -> {ciphertext}` / `DecryptMessage(shared_secret_handle, ciphertext) -> {plaintext}` — **added 2026-08-23, a new amendment, named "the ongoing-ratchet exposure gap."** `DeriveSharedSecret`/`CompleteSharedSecret` (above) establish a session and return a `shared_secret_handle` — but until this amendment, nothing in this capability's *public* contract ever consumed that handle again. Internally, `ratchet.ts` has long contained a complete, tested, unchanged-since-2026-07-16 symmetric-chain ratchet (`deriveNextMessageKey`/`ratchetAdvance`, its own module comment calling them "the ONGOING RATCHET... unchanged by this amendment" as far back as the responder-completion amendment) and `keyRegistry.ts` has long contained `registerRatchetSession`/`getRatchetSession`/`updateRatchetSession` to hold a session's mutable `RatchetState` across calls — but no exported function ever exercised any of it. Conversations' charter (`conversations.charter.md` §3) states plainly that `SendMessage.ciphertext` is "already encrypted client-side by Cryptography & Keys before this call is ever made" — that sentence had no function behind it. **Discovered 2026-08-23 during the Conversations mobile-client build, before any code was written against it** (the same "check first, don't silently rediscover" discipline this charter's own §7 established for the responder-completion gap) — named and chartered here rather than let a capability engineer freelance a workaround (e.g. misusing `Encrypt`/`Decrypt`'s unrelated multi-recipient sealed-envelope construction, which needs no prior session at all and provides no forward secrecy, or reaching into `ratchet.ts`'s unexported internals directly, an Art. 10 violation). `EncryptMessage` calls `deriveNextMessageKey` on the session's stored `RatchetState`, AEAD-encrypts `plaintext` under the derived message key using a **freshly, randomly generated nonce for every call — required, not implementation discretion (Security Steward gate finding, round 1 on this amendment: promoted out of §7's general "cipher suite is an implementation decision" precedent because a deterministic nonce here — e.g. derived from `sendMessageNumber` — would reintroduce a variant of this amendment's own core defect if a crash/retry ever re-derives the same, not-yet-persisted chain position twice; see the persistence/atomicity requirements below for why that window is real, not hypothetical).** Never `Encrypt`/`Decrypt`'s multi-recipient envelope cipher choice by mere analogy — this is its own stated requirement now. Persists the advanced state back via `updateRatchetSession`, and returns a single self-describing opaque byte string — versioned, carrying whatever the receiving side's `DecryptMessage` needs (at minimum a message-sequence number) — that Conversations relays and never interprets, exactly matching its charter's existing opacity discipline for `ciphertext` (no wire-contract change needed on Conversations' side at all). `DecryptMessage` is the mirror: retrieves the session, derives/verifies against the embedded sequence position, decrypts, advances, persists. A failed decrypt must not advance state, an explicit requirement, not an oversight.

  **Ratchet-session persistence, corrected 2026-08-23, round 2 (Constitution Warden gate finding: the first draft of this amendment claimed `updateRatchetSession` "durably" persists state while `keyRegistry.ts`'s actual backing store is an in-memory-only `Map`, explicitly documented there as "intentionally volatile (cleared on process restart)" — a real, factual error in the charter text, not a style issue, that would have silently destroyed every active conversation's ratchet state on the first ordinary app backgrounding/relaunch, with no repair path, since a consumed one-time prekey cannot be re-derived).** `registerRatchetSession`/`getRatchetSession`/`updateRatchetSession` must be backed by `SecureLocalStore`/`SecureLocalRetrieve` (this same capability's own existing at-rest-encrypted local storage primitive, §3 above), keyed by the session's `shared_secret_handle`, not by `keyRegistry.ts`'s volatile in-process map — the identical at-rest-protection discipline §6 already requires for every other sensitive session value (one-time prekey private material, etc.), since a `RatchetState`'s chain keys are exactly that class of material. **Necessary, disclosed consequence, not an incidental detail: `SecureLocalStore`/`SecureLocalRetrieve` are asynchronous (real OS-keychain `await` boundaries) — `registerRatchetSession` therefore requires `DeriveSharedSecret` itself to become an `async` function**, a real, if mechanical, change to an already-implemented function's calling convention (not its wire semantics — the frozen `crypto.proto` RPC shape is unaffected; only the mobile TypeScript binding's sync/async signature changes). `CompleteSharedSecret` is already `async` and needs no such change. The capability engineer implementing this amendment must update every existing caller of the mobile `deriveSharedSecret` binding (today: only its own test suite, since Conversations' mobile client has not yet been built against it) — named explicitly so this isn't silently missed.

  **Atomicity, required, not assumed (Constitution Warden gate finding, round 2: the identical concurrency-race shape this charter already treated as blocking once, at this exact severity level, for one-time-prekey consumption — see §6's "Atomic one-time-prekey consumption" bullet — left unaddressed in this amendment's first draft).** Concurrent `EncryptMessage`/`DecryptMessage` calls against the same `shared_secret_handle` (a realistic retry/resend/offline-queue-flush scenario, not a contrived one) must not both read the same not-yet-advanced chain key and both derive/persist independently — the second `updateRatchetSession` call would silently clobber the first, reintroducing this amendment's own core same-key-reuse defect via a different mechanism than the one it exists to close. **Required: a per-`shared_secret_handle` in-process mutex**, mirroring §6's existing `Map<prekey_id, Promise>` pattern exactly (`Map<shared_secret_handle, Promise>`) — React Native's single-threaded JS execution makes this sufficient, no OS-level locking required, identical reasoning already established for the one-time-prekey case.

  **Audit posture, decided explicitly rather than left implicit (Constitution Warden gate finding, round 2; scoping per Security Steward gate finding, round 1).** `EncryptMessage`/`DecryptMessage` are **not** marked `// ascend:mutates` and emit **no per-message audit event** — a deliberate call, not an oversight: at the call volume these two functions will see (every single message sent/received), a per-message audit event would either flood the audit trail with an entry per message (in tension with Art. 8's data-minimization principle — the audit trail itself would become a detailed messaging-cadence log) or be quietly rate-limited/dropped in a way that undermines Art. 5's "nothing important happens silently" for the entries that do land. This mirrors `Encrypt`/`Decrypt`'s own already-established no-audit-event precedent (§3 above) — using an established session to move data is not itself a capability-lifecycle event the way establishing, generating, or destroying key material is (`shared_secret_derived`, `prekey_bundle_generated`, `signed_prekey_signature_invalid` remain the audited events for this capability's session-lifecycle surface; they are unaffected by this decision). **Decrypt-failure audit logging is explicitly deferred, not silently absent (Security Steward gate finding, round 1):** a `DecryptMessage` AEAD failure is today indistinguishable from an ordinary out-of-order/skipped message, since no skipped-message-key cache exists yet (§7 item 3, unresolved) — auditing every such failure now would produce routine noise on exactly the flaky-connection profile Ascend's target user is likely to hit, masking the real-tampering signal this discipline exists to preserve. Revisit when §7 item 3 is designed, not before.

  **The specific defect this amendment exists to close, found while chartering the RPCs above, not a hypothetical (Chief Architect finding, 2026-08-23, red-teamed independently by Security Steward at this amendment's own gate) — a same-key bidirectional collision:** `deriveInitiatorHandshake` and `deriveResponderSharedSecret` (`ratchet.ts`) both compute `sendingChainKey = HKDF(sharedSecret, CHAIN_INFO)` — and by X3DH's own DH-commutativity property (the entire point of the construction), both parties arrive at the **identical** `sharedSecret`. Feeding an identical secret through an identical HKDF call with an identical info string produces an **identical `sendingChainKey` on both sides**. Had `EncryptMessage` been implemented directly against the existing, unchanged `RatchetState`/`deriveNextMessageKey` as originally sketched, the initiator's first outgoing message and the responder's first outgoing message (two different plaintexts, travelling in opposite directions) would have been encrypted under the **same derived message key** — a catastrophic key-reuse condition for any AEAD cipher, not a subtle theoretical gap. This was never exercised or caught earlier because no code ever called `deriveNextMessageKey` against a *handshake-produced* `RatchetState` before this amendment — the responder-completion amendment (2026-08-19/20) and the key-separation fix (2026-08-21) both correctly scoped their own work to "the handshake produces the right shared secret," and the ongoing-ratchet module's own header comment explicitly (and, until now, correctly *for its own unchanged scope*) said the amendment need not touch it — but nobody had yet asked "what happens the first time two colliding `sendingChainKey`s actually get used."

  **Required fix:** `RatchetState` gains a second field, `receivingChainKey`, alongside the existing `sendingChainKey`. Both are derived directionally at handshake time via role-labeled HKDF info strings — `HKDF(sharedSecret, "ascend-crypto-v1:ratchet-chain-initiator-to-responder")` and `HKDF(sharedSecret, "ascend-crypto-v1:ratchet-chain-responder-to-initiator")` — with the initiator assigning the first to its own `sendingChainKey` and the second to `receivingChainKey`, and the responder assigning them the opposite way. Both parties can compute both labels locally (each already knows its own role — initiator vs. responder — from which half of the handshake it ran); no new wire field, no new round-trip. `EncryptMessage` always advances `sendingChainKey`; `DecryptMessage` always advances `receivingChainKey` — the two chains never collide because they are never the same derived value again. This directly supersedes `CHAIN_INFO`'s current single, undirected label (`ratchet.ts`) for handshake-produced sessions specifically — `CHAIN_INFO` itself is not removed, since nothing else in this charter currently depends on it existing as a bare label, but its use for a real bidirectional session ends here.
- `RestoreFromRecoveryPhrase(phrase) -> private_key_handle` — re-derives the identity's private key material from the mnemonic on a new device, purely by offline computation. No server involvement, no server-held copy of anything derived from the phrase, at any point.
- `ExportKeyMaterial(user_confirmation)` — explicit, user-initiated export of key material in a portable, documented format (Art. 9) — distinct from routine use, requires deliberate confirmation given the sensitivity.

**Consumes:**
- **Audit / Explainability** — key generation, rotation, and recovery events are audited (the operation succeeding/failing, never the key material itself). `GeneratePrekeyBundle` and `CompleteSharedSecret`'s one-time-prekey deletion are both new events under this same discipline (§4).

**Publishing/fetching prekey bundles is explicitly out of scope for this amendment, named rather than silently assumed solved (2026-08-19):** `GeneratePrekeyBundle` returns public bytes; something must store them somewhere network-reachable so a remote initiator can fetch them, and this capability has no network component of its own by design (Art. 10, §7 of the original charter) and gains none here. The natural owner is **Identity** — it already publishes/resolves per-identity and per-device public key material (`ResolveIdentity`, `BindDevice`'s `device_public_key`) — but this is a **separate, follow-up Identity charter amendment**, not decided or designed by this one. This capability's contract only needs a caller to hand it `their_prekey_bundle`/`their_ephemeral_public_key` as plain input; it remains agnostic to how the caller obtained them. This is a real, named next step (§7), not a gap silently left for an implementing engineer to discover.

This is a foundation-most capability: it consumes almost nothing and is consumed by nearly everything security-sensitive (Identity, Permissions, Storage, File Objects, and now Conversations).

## 4. Constitutional obligations

- **Art. 7 (security never reduces ownership):** no server-side key escrow, ever, under any convenience justification. If a future feature proposes "backup my keys to the cloud for convenience," that is a charter amendment requiring Security Steward veto review, not a default this capability ships with.
- **Art. 1 (ownership):** private keys are generated and remain on-device (or user-controlled secure enclave); the server sees only public keys and ciphertext.
- **Art. 8 (privacy):** no key material, plaintext, or recovery phrase is ever transmitted to or logged by the server. The data manifest for this capability documents exactly zero collected fields beyond public keys. **Amended 2026-08-19:** `signed_prekey.public_key`/`.signature`/`.created_at` and each `one_time_prekey.public_key` are the same category (public key material) already covered by this bullet, not a new one — purpose: lets another identity's device asynchronously establish an E2E session with this device without requiring it to be online at handshake time. **`signed_prekey.prekey_id` and each `one_time_prekey.prekey_id`, named as their own manifest entries (Constitution Warden gate finding, first draft: these were folded into "public key material," which they aren't) — purpose: an opaque identifier, not key material itself, referenced by `session_establishment_payload` so the responder's `CompleteSharedSecret` knows which locally-stored private prekey to retrieve (and, for the one-time prekey, immediately delete after use, §6).** No private prekey material is ever returned by `GeneratePrekeyBundle` or transmitted anywhere. **`identity_dh_public_key` — added 2026-08-21 (key-separation fix, Constitution Warden gate finding: this field was missing its own manifest entry), its own named entry, not folded into "public key material" above since it warrants distinct explanation — purpose: the device's X25519 DH-capable identity public key, deterministically derived from the same recovery-phrase seed as the Ed25519 signing key via a domain-separated KDF (`dh_scalar = HKDF(seed, "ascend-x3dh-dh-key")`), genuinely different bytes from `GenerateIdentityKeyMaterialResponse.public_key`. Returned so the caller (or whatever republishes on this device's behalf, per Identity's companion amendment) can make it fetchable by other identities' devices for X3DH session establishment — the same asynchronous-reachability purpose as the signed/one-time prekeys above, for the identity-level term rather than the per-session ones. **`identity_dh_public_key_signature` — added 2026-08-21, round 2 (Constitution Warden gate finding, round 3: this sibling field was missing its own manifest entry, the identical defect class just fixed for `identity_dh_public_key` itself, in the same bullet) — purpose: proves `identity_dh_public_key` genuinely originated from this identity's own Ed25519 signing key, not a value a compromised publish/fetch path substituted (§6's substitution-threat bullet).** **The ongoing-ratchet exposure amendment's own fields, reasoned through explicitly rather than left silent (Constitution Warden gate finding, round 2 on this amendment: every prior amendment stated this reasoning even when the conclusion was "no new category," this one didn't) — none require a new manifest entry:** `shared_secret_handle` is an opaque, process-local reference in the same never-transmitted, never-logged category as `private_key_handle` (already covered by this bullet's opening sentence and the "Explicitly out of scope" list below); the new opaque per-message envelope (`EncryptMessage`'s return value) is the same category as `Encrypt`'s existing `ciphertext` output, itself already never logged or manifested as a separate field; `receivingChainKey` (the new `RatchetState` field, §3) never leaves this module in any form, exactly like `sendingChainKey` today. **Persisting `RatchetState` via `SecureLocalStore` (§3's persistence fix) does not change this** — it moves *where* this already-never-transmitted material is stored at rest, not *whether* it is collected, transmitted, or logged; the same "encrypted local store, never plaintext on disk" discipline this bullet's opening sentence already requires for all key material governs it identically.
- **Art. 9 (export):** `ExportKeyMaterial` guarantees the user is never locked out of their own cryptographic identity by the platform.

## 5. Experience budget

Invisible by default — a user never manually manages raw keys during normal use. "Transparent when curious": a "Security" screen shows **two genuinely distinct things, specified precisely 2026-08-21, round 7 (Constitution Warden gate finding: the original one-sentence description never distinguished them, and round 6's mitigation claim silently depended on a reading it hadn't earned)** — **(a) the local identity's own device key status** (this device's public key fingerprint, bound devices, matching `ListDevices`' own data), and **(b) per-contact identity-key fingerprint comparison: given a specific resolved contact (any identity_ref the user has `ResolveIdentity`'d, e.g. from an existing or about-to-start conversation), a human-comparable digest of that contact's `identity_signing_public_key`** — this second surface is what "verify" in "for users who want to verify" has always meant, the same way it does in every other secure messenger with a fingerprint/safety-number feature: verifying *who you're talking to*, not your own key against yourself, which is not a meaningful verification at all. **This second surface is the platform's named, deliberate answer to the first-contact TOFU trust gap (§6/§7) — a user who wants stronger-than-default assurance for a specific new contact can compare fingerprints here, out-of-band, before or after messaging begins.** It remains opt-in, never a forced step before a first message can be sent. The recovery phrase is shown once, deliberately, at identity creation, with clear consequence framing (Art. 13 — this is the one place complexity is justified because the stakes are real, not because the default is lazy). **Amended 2026-08-19:** prekey generation, rotation, and replenishment (`GeneratePrekeyBundle`) must be fully invisible, automatic background maintenance — no user action, no user awareness required for the common case. This is not a new user-facing surface; it is machinery the messaging experience depends on silently, the same way TLS session key negotiation is invisible to a browser user. If a "Security" screen ever surfaces prekey status for the curious, that's an addition to the existing discoverable-but-hidden pattern above, not a new one.

**The one-time-prekey-exhaustion case (§6) is the deliberate exception to "no user awareness required," resolved explicitly here rather than left in tension with the paragraph above (Constitution Warden gate finding, first draft: §5 and §6 made conflicting-sounding commitments):** a session established without a one-time prekey has a genuinely different, weaker guarantee (§6) — this is not the routine case "invisible by default" is describing, and must not be silently folded into it. It reuses the **same** passive, non-interrupting mechanism this charter already commits to for key rotation (§6 of the original charter: "a passive, discoverable indicator... never an interrupting modal") as a **second trigger condition** on that one existing indicator, not a new UI concept — Art. 12/13's cognitive-budget discipline is preserved by extending one already-approved affordance rather than inventing a second. A user who never looks stays undisturbed; a user who taps the indicator can discover *why* (key rotation, or this session's weaker exhaustion-fallback guarantee) — genuinely "transparent when curious," not merely logged somewhere only an engineer would look.

## 6. Threat model

This capability **is** the threat model for the rest of the platform; full rigor required, Security Steward gates hardest here and may spawn an ephemeral crypto red-team specialist.

- **Key generation entropy:** must use a cryptographically secure RNG sourced from the OS; no custom entropy pooling.
- **At-rest protection:** private keys stored via OS keychain/secure enclave/TEE where the platform provides one; falls back to a locally-derived encryption key (e.g. from a device PIN/biometric) where it doesn't — never plaintext on disk.
- **In-transit protection:** only public keys and ciphertext cross the network boundary; the transport layer itself should still be TLS as defense-in-depth, not a substitute for E2E encryption.
- **Recovery phrase handling:** generated client-side, shown once, never persisted by the platform in any form (not even encrypted). The phrase is the sole seed of the identity's key material (deterministic derivation — see §3) — there is no separate encrypted key backup stored anywhere, on the server or otherwise, for the phrase to unlock. Losing the phrase together with every bound device means **permanent, unrecoverable loss of identity**, by design; this is the direct consequence of there being no server-held copy of anything derived from it, and it must be stated plainly to the user at generation time (see Identity charter §5), not hidden.
- **Key rotation:** rotating a device or identity key must not silently break other users' ability to verify who they're talking to. The re-verification signal to conversation partners is a passive, discoverable indicator (e.g. a changed-key badge on the conversation), never an interrupting modal — consistent with "transparent when curious" — and feeds Identity's audit trail.
- **Forward secrecy / post-compromise security:** `DeriveSharedSecret` must use a construction (e.g. a double-ratchet or equivalent) such that compromise of a device's current session state does not expose past session content (forward secrecy) and does not permanently compromise future sessions once the device is secured again (post-compromise security). This is distinct from the "server compromise" item below — it covers a compromised *device's* exposure of session content.
- **Server compromise scenario — scoped precisely, 2026-08-21, round 6 (Security Steward gate finding: this original 2026-07-06 line overclaimed unconditionally and had never been checked against the specific first-contact case before now):** even a fully compromised server must not be able to decrypt past or future E2E content — this half holds unconditionally; content encryption never touches the server at all, with or without a real party's private keys, so there is no server-compromise scenario that exposes it. **"Nor mint a valid key on a user's behalf" holds for an *established* relationship** (a compromised server cannot silently substitute a different signing/DH key for an identity a caller has resolved before, without the changed-key-badge indicator firing) **and for tampering with a genuine handshake between two real parties** (§6's DH-term-isolation and wholesale-fabrication-signature fixes, rounds 3-4/5) — **but does not, and structurally cannot, hold for a compromised server lying about an identity's foundational signing key the very first time a caller resolves that identity.** See the dedicated "first-contact trust gap" bullet and §7's tracked open item for the full scoping and the deliberate mitigation-posture decision.
- **Responder-side forward secrecy — the specific defect this amendment exists to fix, stated precisely (2026-08-19, real red-teamed finding, not a hypothetical):** an earlier draft of this exact amendment (chartered as part of the Conversations capability's own gate — see `docs/DECISION_LOG.md`, 2026-08-19) proposed the responder completing the handshake using only their long-term static private key against the initiator's public keys. Independently red-teamed and found broken: it reproduces the correct shared secret algebraically but contributes no fresh, single-use secret on the responder's side — a future compromise of the responder's long-term or signed-prekey private key would retroactively decrypt **every past session that key ever completed as responder**, the same defect class this capability's own implementation gate already vetoed once for the *initiator's* side (2026-07-16). **The fix, as specified above:** `CompleteSharedSecret` must consume a genuine one-time prekey and permanently delete its private key immediately upon successful use. This is the single load-bearing requirement of this entire amendment — an implementation that reproduces the correct shared secret value without also deleting the one-time prekey has not satisfied this charter, even though it would pass a naive "does decryption work" test.
- **Signed-prekey substitution:** a compromised or malicious server (or anyone controlling the publish/fetch path — see Consumes) must not be able to substitute a different signed prekey than the one the responder actually generated, or a man-in-the-middle could establish sessions impersonating the responder. The signed prekey's public key must be signed by the identity's own long-term signing key (already established, Identity-bound material) and that signature must be verified by every initiator before use. **Verification failure, required behavior stated explicitly (Security Steward gate finding, round 1: this was previously unstated) — a hard abort, never a silent fallback:** `DeriveSharedSecret` must refuse to proceed at all (no session, no partial derivation) and must emit a required audit event (e.g. `signed_prekey_signature_invalid`), matching this codebase's established "audit failure paths too" discipline (Constitution Warden, 2026-07-16, `apps/mobile/src/capabilities/crypto/`'s own implementation gate). A caller that skips verification, or that proceeds anyway on failure, has not correctly consumed this capability's contract.
- **`identity_dh_public_key` substitution — the identical threat, now named explicitly for the new key-separation fix's own published value, added 2026-08-21 (Security Steward gate finding on the fix itself, round 2: the first draft of this fix introduced this exact field with no signature, an undisclosed gap).** Reasoned through, not just patched: since `identity_dh_public_key` is server-published/-fetched material exactly like `signed_prekey`, it inherits the identical substitution risk and the identical fix — signed by the identity's Ed25519 signing key at `GeneratePrekeyBundle` time, verified by every initiator before use in any DH term, hard abort on failure. **Bounded-impact analysis, for the record — this is not a confidentiality break even before the signature fix, because of where `identity_dh_public_key` sits in the derivation:** it contributes only to `DH2 = DH(EK_A, IK_B)`; `DH1`/`DH3`/`DH4` still depend on `SPK_B`'s already-signature-protected private key and the initiator's own private keys. A substituted, unsigned `identity_dh_public_key` alone cannot yield an attacker a working shared secret or MITM decrypt capability — it produces a derivation mismatch, i.e. a silently undecryptable session, the same severity class as the already-disclosed, already-tracked "one-time prekeys carry no per-key signature" gap below. The signature requirement closes it anyway, since the fix is architecturally cheap (generated alongside `signed_prekey` in the same call) and this key has no alternate distribution/cross-check path the way the pre-fix design implicitly had (the pre-fix field carried the same value `ResolveIdentity` also returned; post-fix, `identity_dh_public_key` has no such implicit second source). **Verification failure audit event, named explicitly rather than left to implementer discretion (Security Steward gate finding, round 3, non-blocking but closed anyway to match this charter's established discipline):** reuses `signed_prekey_signature_invalid` (§6 above) — a distinct event name isn't warranted, since both are the identical failure class (a required signature over server-published material didn't verify) and this codebase's convention (`ListFileAccess`, `ListFileObjects`) is one shared denial/failure event per failure *class*, not one per field.
- **The INITIATOR's own `identity_dh_public_key` — round 3 vs. round 4, a genuine escalation, not a contradiction: round 3 correctly closed in-flight *tampering* of a genuine handshake, round 4 found a distinct, more severe threat DH-term-isolation does NOT cover.** Round 3 (corrected 2026-08-21, Security Steward gate finding: an earlier draft justified leaving this key unsigned by "the message arrived over an authenticated channel," which does not survive this charter's own declared full-server-compromise threat model) established that a compromised server *tampering with one field* of an otherwise-genuine handshake between two real honest parties is bounded — the substituted key can only break one DH term, degrading to a derivation mismatch, never a working shared secret. **That reasoning is correct and remains true, but round 4 found it doesn't cover a different attack: wholesale fabrication.** An attacker (or a compromised relay acting alone, with no real party's private key ever needed) who generates **both** `IK_A` and `EK_A` from scratch and presents them as a fresh session-establishment message holds 100% of the private material every DH term requires — `DH1` through `DH4` are all independently computable from the attacker's own fabricated keys plus the responder's already-public bundle, no genuine private key required from anyone real. The responder derives a fully working `shared_secret` and believes it belongs to whatever identity `IK_A_pub` is presented as. **This is literally "minting a valid key on a user's behalf" under server compromise — the exact thing this section's own pre-existing opening line already forbids** — not a derivation mismatch, and DH-term-isolation was never the right defense against it (isolation bounds *tampering* with one field of a genuine exchange; it says nothing about an attacker who owns every field). **Required fix:** `CompleteSharedSecret` must verify `their_identity_dh_public_key` against `their_identity_signing_public_key` (sourced by the caller via Identity's already-existing `ResolveIdentity(sender_identity_ref)` — no Identity contract change needed, and no extra round-trip beyond what a client would need for basic sender identity display anyway) via `their_identity_dh_public_key_signature` (the initiator's own, already-generated `GeneratePrekeyBundleResponse.identity_dh_public_key_signature`, included directly in `session_establishment_payload` — §7 item 4, amended) — hard abort on mismatch, reusing `signed_prekey_signature_invalid`.

  **What this closes, and what it honestly does not — stated explicitly rather than overclaimed (corrected 2026-08-21, round 5, Constitution Warden gate finding: the sentence originally here claimed unconditional closure, the identical class of overclaim already caught and fixed once in round 3 for a different field, now recurring at a different trust boundary in the same fix).** This closes fabrication by any attacker who does **not** control `their_identity_signing_public_key`'s value as returned by `ResolveIdentity` — i.e., a compromised *relay/transport* that tampers with or replaces `session_establishment_payload` in transit, which is the threat this fix's own round 4 finding was about. **It does not, and cannot, close fabrication by an attacker who *also* controls Identity's `ResolveIdentity` response itself** — under this section's own declared "even a fully compromised server" threat model, a server that can forge a self-consistent triple (a fabricated signing key, a DH key signed by it, and a matching `ResolveIdentity` response) passes this check trivially, because the check only proves internal consistency between two values the same attacker could both control. **This is not a defect unique to this construction — it is the fundamental limit every E2E messenger with server-mediated key discovery hits** (Signal's own safety-number/TOFU model has the identical residual: it protects against transport tampering and detects *later* key changes, but cannot bootstrap trust from nothing against a server that lies from the very first contact). **The one partial, already-chartered mitigation this platform has:** the passive changed-key-badge indicator (§5, §6's exhaustion-fallback bullet) — once a user has ever established a session with an identity, a *later*, different `ResolveIdentity`/`identity_signing_public_key` response for that same `identity_ref` is detectable and surfaced. **This provides zero protection on first contact with an identity** — there is no prior pinned value to compare against, and this remains a named, open, first-contact-specific gap, not solved by this fix or any other capability chartered so far. Whoever eventually charters an out-of-band identity-verification affordance (e.g. a user-initiated "compare safety numbers in person" flow, the standard real-world answer to exactly this limit) inherits this as the primitive it would close — not something this charter attempts to solve.

  **Mitigation-posture decision, made explicitly rather than left implicit (Chief Architect, 2026-08-21, round 6, per Security Steward's gate finding that this decision belongs to the Chief Architect, not to a guardian):** this platform **deliberately accepts TOFU (trust-on-first-contact) risk for a new identity's first session**, the same posture Signal, WhatsApp, and every other mainstream E2E messenger with server-mediated key discovery ships by default — requiring mandatory out-of-band verification before every new conversation would violate this codebase's own repeated, guardian-approved "zero-config default" commitments (Art. 13; `conversations.charter.md` §5's own "paste identity_ref, tap Message, start talking" experience budget) for a threat that requires an attacker to control the platform's own server infrastructure, not merely intercept traffic. **The already-chartered "Security screen" fingerprint-display path (§5) is hereby named explicitly as the platform's answer to this specific threat**, not merely "for the curious" as its original framing suggested — a user who wants stronger-than-TOFU assurance for a specific contact can compare fingerprints out-of-band (in person, over a separately-trusted channel) at any time, including on first contact, before or after messaging begins. This is opt-in, not a forced step, consistent with Art. 12/13's "powerful when needed, not required by default." No further mitigation is chartered here; this is a considered, disclosed, industry-standard acceptance, not an oversight.
- **One-time-prekey exhaustion — disclosed, not silently degraded, and now operationally detectable, not just narratively disclosed (Security Steward gate finding, round 1):** if an initiator fetches a responder's bundle and no one-time prekey remains (the responder hasn't replenished in time, or many initiators started sessions concurrently), `CompleteSharedSecret` still succeeds using only the signed prekey (the three-term derivation above) — but that specific session has a **stated, weaker guarantee**: no protection against a future compromise of that signed prekey specifically, until it next rotates. This must be surfaced as a real, named tradeoff (consistent with this codebase's "disclose gaps, don't overclaim" discipline, e.g. Audit's own tamper-evidence disclosure), not presented as identical security to a session that consumed a one-time prekey — the dual passive-indicator mechanism in §5 is how a user discovers it; **`CompleteSharedSecret` must additionally emit a required audit event on every exhaustion-fallback session establishment (e.g. `session_established_signed_prekey_only`)**, so this is empirically detectable rather than only theoretically disclosed — necessary given Ascend's own target user (privacy-conscious, often offline/background-refresh-disabled) is precisely the profile most likely to exhaust an unreplenished one-time-prekey pool, making this worth actually measuring, not just narrating. Rotation cadence and replenishment thresholds bound how long this weaker window can persist, but do not eliminate it entirely under sustained load — an implementation decision for the capability engineer, not a charter-mandated number.
- **Atomic one-time-prekey consumption — required, not assumed (Security Steward gate finding, round 1: a real, concrete race, not a theoretical one).** `SecureLocalStore`/`SecureLocalRetrieve` are asynchronous (real `await` boundaries around the underlying OS keychain calls) — a naive lookup-then-delete sequence in `CompleteSharedSecret` has a genuine race window: duplicate message delivery, a retry after a dropped response, or (before the deferred Identity publish/fetch amendment guarantees single-issuance of any one `prekey_id`) two initiators independently fetching and using the same one-time prekey could all reach `CompleteSharedSecret` concurrently for the same `my_one_time_prekey_id`, each reading the still-present private key before either deletes it — silently reusing a "one-time" prekey and quietly reopening the exact forward-secrecy hole this amendment exists to close. **Required: the lookup-and-delete must be atomic per `prekey_id`** — concretely, a per-`prekey_id` in-process lock (React Native's JS execution is single-threaded, so a `Map<prekey_id, Promise>`-based mutex serializing concurrent calls for the same `prekey_id` is sufficient; no OS-level locking is required) wrapping the non-atomic store calls, such that only one `CompleteSharedSecret` call for a given `prekey_id` is ever in that critical section at a time. **The losing concurrent call's required behavior, stated explicitly rather than left undefined:** upon acquiring the lock after the winner has already deleted the entry, it must fail with a specific, distinguishable error (e.g. "prekey already consumed — likely a duplicate message delivery"), never silently succeed with stale data, never hang, and never fall back to a weaker derivation without the caller being told so explicitly.
- **Post-compromise security for the ongoing per-message layer — disclosed, not delivered, by the ongoing-ratchet exposure amendment above (2026-08-23):** `EncryptMessage`/`DecryptMessage`'s directional symmetric-chain fix (above) closes the same-key collision and provides real forward secrecy for the message chain itself (`deriveNextMessageKey`'s HKDF advance is one-way — a compromised later chain key cannot reconstruct an earlier message key). It does **not** exercise `ratchetAdvance` (the DH-ratchet step, already implemented and tested, unchanged, in `ratchet.ts`) anywhere — no periodic DH re-keying happens once a session is established. This means this charter's own §6 "forward secrecy / post-compromise security" requirement (above) is only half-satisfied for the ongoing per-message layer: a device compromise that exposes the current chain key(s) exposes every *future* message on that chain too, until the session is torn down and re-established from scratch, with no self-healing DH step to recover mid-session the way a full Double Ratchet would. **Named explicitly as a real, tracked gap rather than silently shipped as if the existing "forward secrecy or equivalent" line already covered it** — the machinery to close it (`ratchetAdvance`, a working, tested DH-ratchet step) already exists in this codebase and is not itself in question; wiring it into `EncryptMessage`/`DecryptMessage` (deciding the trigger condition — e.g. Signal's own "ratchet whenever the sending party changes" rule — and extending the opaque per-message envelope to carry a DH-ratchet public key when a step occurs) is real, additional design work deliberately not attempted in this first pass, the same "don't let scope grow silently mid-amendment" discipline this charter has held to throughout. Tracked in §7.

  **Mitigation-posture decision, made explicitly rather than left as a bare disclosure bullet (Chief Architect, 2026-08-23, per Constitution Warden gate finding, round 2: this deferral needs the same formal sign-off weight as the TOFU acceptance above, not a lighter-weight §7 footnote, given §6's PCS requirement was previously phrased as an unconditional "must").** This platform ships `EncryptMessage`/`DecryptMessage` with forward secrecy but without mid-session post-compromise self-healing, for this first Conversations release. This is judged acceptable, not indefinitely — unlike TOFU (a fundamental, structurally unclosable limit of server-mediated key discovery), this gap is closable with already-existing, already-tested machinery (`ratchetAdvance`) and no new cryptographic primitive; Security Steward's own gate review on this amendment independently reached the same conclusion (closable, not a blocker, but "high-priority near-term follow-up work, not something that can sit indefinitely" — not a standing acceptance). **The bound on the exposure window, stated so this isn't open-ended:** the gap is closed the moment whoever next charters the DH-ratchet wiring (§7) ships it — tracked as the immediate next priority item for this capability once the current amendment's own implementation lands and Conversations' mobile client is working end to end, not deferred indefinitely alongside TOFU's genuinely-permanent acceptance.

  **Forward-looking requirement on `ratchetAdvance` itself, named now so it is not silently rediscovered later (Security Steward gate finding, round 1: `ratchetAdvance`, `ratchet.ts:259-273`, independently re-derives its own `sendingChainKey` via the same bare, undirected `CHAIN_INFO` label this amendment is fixing everywhere else — its `newRootKey` is identical on both sides by the same DH-commutativity property, so the moment `ratchetAdvance` is wired into `EncryptMessage`/`DecryptMessage`, per the deferred work above, the identical bidirectional-collision defect this amendment exists to close will silently resurface at every DH-ratchet step unless fixed first).** Whoever wires in the DH-ratchet next must also give `ratchetAdvance` the identical directional/role-labeled `sendingChainKey`/`receivingChainKey` derivation from `newRootKey` that this amendment gives the initial handshake-produced state — not a new problem, the same one, at a different point in the session's lifecycle. `ROOT_INFO`'s own use (advancing `rootKey` itself) is unaffected and correct as-is; only the chain-key derivation that follows it needs the fix.
- **Per-device scoping and the multi-device question, named rather than silently resolved:** prekey bundles are generated and consumed per-*device* (a device's private prekey material never syncs to another bound device of the same identity — no key-sync mechanism exists, per this charter's own already-disclosed §7 gap). This means establishing a *new* session with a multi-device identity requires picking *which* of that identity's bound devices to target — this amendment does not resolve that routing question; it is the same disclosed multi-device limitation already named in §7 and inherited by Conversations' own charter (§5/§7), now given a second concrete manifestation rather than a new one. Not blocking this amendment; blocking real multi-device support whenever that's chartered. **Compounding effect, named for whoever charters multi-device routing (Security Steward gate finding, round 1):** independent per-device one-time-prekey pools mean an N-device identity has N independent chances to hit the exhaustion-fallback window above — not a new risk category, but a real amplification worth a forward pointer.

## 7. Open questions / risks

- Exact algorithm choices (e.g. X25519/Ed25519 + AEAD cipher suite) are an implementation decision for the capability engineer once this charter is frozen, not a charter-level decision — but Security Steward should confirm the charter's abstractions (opaque key handles, no plaintext key export outside the explicit `ExportKeyMaterial` path) don't foreclose a secure choice. **Resolved at implementation:** X25519 + XChaCha20-Poly1305 + HKDF-SHA256 (`@noble/*`), see `docs/DECISION_LOG.md` 2026-07-16.
- Multi-device key sync (so a second device can read history) is out of scope for this charter's first freeze — flagged as a follow-up capability question once Identity's device-binding model is built.
- **Resolved 2026-08-19 (was: "New, raised by Security Steward at the implementation merge gate, 2026-07-16"):** the flagged gap — `DeriveSharedSecret` only implementing the initiator's half, with no responder-side completion mechanism — was checked first, exactly as this bullet instructed, when the Conversations capability was chartered and hit it directly. Resolved via this amendment: `GeneratePrekeyBundle`/`CompleteSharedSecret` (§3), using a prekey-bundle construction (not a live round-trip handshake — deliberately chosen, see rationale in `docs/DECISION_LOG.md`, 2026-08-19, "Cryptography & Keys amendment: responder-side prekey completion," so that an initiator can still send real content in the first message to an offline responder, preserving async messaging). A first-draft sketch of this exact fix was independently red-teamed and found to lack responder-side forward secrecy — see §6's dedicated bullet — before being corrected to the design now frozen here.
- **First-contact TOFU trust gap — named 2026-08-21 (rounds 5-6), deliberately accepted, not solved, per the Chief Architect's mitigation-posture decision (§6):** `CompleteSharedSecret`'s signature check (§3/§6) closes fabrication by a compromised *relay*, but not by a compromised *Identity backend itself* lying about an identity's foundational signing key the first time a caller resolves it — no prior pinned value exists yet to detect the lie against, and the changed-key-badge indicator only protects *later* sessions with an identity already seen once. This is the same fundamental TOFU/PKI limit every server-mediated-key-discovery E2E messenger has (Signal's own safety-number model included), not a defect unique to this construction. **Decided, not left open:** this platform accepts this risk by default (same posture as Signal/WhatsApp), names the existing "Security" fingerprint screen (§5) as the opt-in mitigation available to any user who wants it, and does not require out-of-band verification before a first message can be sent. Whoever eventually charters a stronger, structured out-of-band identity-verification affordance (e.g. an in-app "compare safety numbers" flow with its own UI, rather than today's bare fingerprint display) inherits this as the primitive it would build on — a future enhancement, not a currently-required fix.
- **Fingerprint/digest algorithm, named as an implementation-time decision this capability owns, not left to ad hoc per-screen logic (Constitution Warden gate finding, round 8, non-blocking):** §5's local-device and per-contact fingerprint surfaces both need the *same* digest function over a public key, and it must be interoperable — two different devices/users comparing fingerprints for the same key must derive byte-identical digests, or the "verification" compares nothing. A single canonical function (e.g. `FingerprintPublicKey(public_key) -> digest`) should be specified once at implementation time and logged in `docs/DECISION_LOG.md`, the same discipline already applied to every other algorithmic choice in this charter (X25519/XChaCha20-Poly1305/HKDF-SHA256, the X3DH context strings) — not reinvented divergently by whichever screen or future "compare safety numbers" flow needs it next.
- **New, this amendment's own follow-ups, named explicitly rather than left implicit:**
  1. **Publishing/fetching prekey bundles is a separate, required Identity charter amendment**, not designed here (§3's Consumes note) — this capability generates and signs bundles but has no path to make them reachable by another user's device. Recommended immediate next step after this amendment gates, before Conversations' capability engineer can build a working `SendMessage`/decrypt path end to end. **That amendment must also name, explicitly (Security Steward gate finding, round 1, non-blocking here but must not be silently assumed away there):** the brand-new-identity edge case — an identity that has never yet run its first `GeneratePrekeyBundle`/publish cycle (e.g., between account creation and the first background maintenance run) leaves an initiator with nothing to fetch at all, not even the exhaustion-fallback case. Whether that's closed by publishing synchronously at identity/device creation, or handled as a distinct "recipient has no bundle yet" error surfaced to the initiator, is that amendment's decision, not this one's.
  2. **Which of a multi-device identity's devices a new session targets** is unresolved (§6) — inherits, rather than newly introduces, this charter's already-disclosed multi-device-sync gap (previous bullet, now resolved for the *initiator*-only case; still open for routing to a specific responder device).
  3. **One-time-prekey exhaustion's weaker-guarantee window** (§6) is disclosed, not eliminated; if usage patterns make this a frequent rather than rare occurrence, revisit rotation/replenishment cadence as an implementation-time tuning question, not a charter-level one.
  4. **`session_establishment_payload`'s exact contents, resolved as a byproduct of this amendment, not left open:** it must carry the initiator's fresh ephemeral public key, **the initiator's `identity_dh_public_key` (added 2026-08-21, key-separation fix round 3, Security Steward gate finding: the original list omitted this — an implementer had no confirmed source for `CompleteSharedSecretRequest.their_identity_dh_public_key` without it, and no server-mediated fetch path exists or is needed for this value)**, **the initiator's `identity_dh_public_key_signature` (added 2026-08-21, round 4, same finding chain: required so the responder can verify `identity_dh_public_key` genuinely belongs to the claimed sender before trusting it — see §6's "identity impersonation via wholesale fabrication" bullet — the initiator's own already-generated signature from `GeneratePrekeyBundle`, no new signing operation needed to include it here)**, the responder's `signed_prekey`'s `prekey_id`, and the `one_time_prekey`'s `prekey_id` if one was used — all opaque bytes from Conversations' point of view (its charter's existing opaque-payload treatment, §3, needs no further amendment). Because the initiator can complete their own full derivation locally before sending anything, **`SendMessage.ciphertext` does not need to become optional** — the open item Security Steward flagged in Conversations' charter (§7) is resolved by this choice of construction, not deferred further.
  5. **The per-`prekey_id` mutex's scope, named precisely (Security Steward gate finding, round 2):** it serializes concurrent calls within a single JS runtime instance only. React Native supports genuinely separate JS contexts (e.g. Android headless JS for background task processing) with no shared visibility into each other's in-flight state — a future background-message-processing capability invoking `CompleteSharedSecret` from a headless context while the foreground app does the same for the same `prekey_id` would reopen the same race class across contexts. Not concretely reachable today (no headless-JS/background-task capability exists in this codebase, confirmed by direct search) — named as an open risk to close explicitly if/when one is ever chartered, not silently assumed covered by the current mutex.
  6. **Crash-mid-consumption, a distinct risk from the concurrency race, named separately (Security Steward gate finding, round 2):** the mutex requirement (§6) makes prekey consumption atomic against *concurrent calls*; it says nothing about *durability* if the process is killed between reading the one-time prekey's private key and the delete completing. This is a different failure mode than the one the mutex closes and is not resolved by it — flagged for whoever next hardens this path, not solved here.
- **New, the ongoing-ratchet exposure amendment's own follow-ups (2026-08-23):**
  1. **Periodic DH-ratchet / post-compromise security for the ongoing per-message layer is deferred, not delivered (§6)** — `EncryptMessage`/`DecryptMessage` close the same-key bidirectional collision and provide message-chain forward secrecy, but never call the already-implemented `ratchetAdvance`. Whoever picks this up next must decide the trigger condition for a DH-ratchet step and how the opaque per-message envelope carries the new DH public key when one occurs — real design work, not a mechanical follow-up.
  2. **The opaque per-message envelope's exact wire format** (version byte, message-sequence number, AEAD nonce/tag layout) is an implementation-time decision for the capability engineer, mirroring `envelope.ts`'s own precedent of a self-contained, versioned format — not charter-mandated byte-for-byte, the same discretion §7 item 1 already grants the cipher-suite choice.
  3. **Out-of-order / skipped-message handling:** `deriveNextMessageKey` advances one message at a time; a message that arrives after a later one (or is lost entirely) needs either a skipped-message-key cache (standard Double Ratchet practice) or an accepted "this message is now undecryptable" failure mode. Not resolved here — an implementation-time decision, flagged so it isn't silently assumed away. Decrypt-failure audit logging (§3/§6) is explicitly deferred to whenever this item is designed. **The per-message envelope's `sequence_number` header, named as a landmine for this same item (Security Steward implementation-merge-gate finding, 2026-08-23):** `messageEnvelope.ts`'s wire format carries a 4-byte sequence number that is currently **not** bound into the AEAD as associated data — a transport that controls delivery (Conversations' own declared threat model) could splice a different header onto a genuine `(nonce, ciphertext)` pair without invalidating the tag. Provably inert today (`decryptMessage` decodes but never consumes `sequenceNumber` — chain advancement is driven entirely by local per-session state), the identical "correct-today, silently-reopens-a-real-defect-once-wired-in" shape already tracked for `ratchetAdvance`'s bare `CHAIN_INFO` above. **Whoever designs this item must bind `sequenceNumber` (and the version byte) into the AEAD as associated data as part of that work, not discover the gap after the field is already load-bearing** — cheap now, materially more expensive once real messages exist on the wire in the unauthenticated format.
  4. **Exhaustion-fallback handshake replay/dedup, named 2026-08-23 (Security Steward gate finding on this amendment, round 1):** the existing atomic one-time-prekey-consumption requirement (§6) only guards the one-time-prekey-present path. In the exhaustion-fallback (three-term, signed-prekey-only) case, nothing today prevents a replayed `session_establishment_payload` from causing a second, independent `CompleteSharedSecret` call to re-derive the identical initial `RatchetState` a second time under a second, independent `shared_secret_handle` — a session-state-confusion/dedup gap (two handles believing they own the same underlying secret), not a ciphertext-confidentiality break given this amendment's random-per-call nonce requirement (§3). `CompleteSharedSecret` should reject or dedupe a repeated handshake for the same `(signed_prekey_id, initiator_ephemeral_public)` pairing even when no one-time prekey was consumed. Not resolved here — flagged for whoever next hardens the exhaustion-fallback path.
